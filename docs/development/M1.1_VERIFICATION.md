## Implementation and user workflow

The existing Details View gains **Add game** and **Manage selected game**. A native modal dialog keeps keyboard focus inside the editor and returns focus on close. Its contents scroll within a bounded viewport; the virtualized grid and row geometry remain intact.

- Create a required title, optional release date/genre/developer/favorite, named manual source, and optional installation record. A game may be owned without an installation.
- Select a row, open the editor and explicitly save metadata, membership completion, or installation metadata. Add another named manual membership without duplicating the game. Multiple installation records per membership remain supported, with distinct location strings.
- Explicitly confirm installation-record, membership, or canonical-game removal. The confirmation describes the affected metadata. Membership removal deletes only that membership and its installation records; it preserves the game and other memberships. The last membership cannot be removed through this action.
- Canonical removal requires a manually created game with exclusively manual, non-provider memberships. It removes that game's overrides, manual memberships and installation metadata in one transaction. Other canonical games and source catalog records remain. Provider memberships/installations and legacy canonical removal are refused by Rust.
- Successful writes refresh current counts/source options and invalidate bounded pages, clear selection and reset scroll to the beginning, retaining current criteria. An edited item can disappear from its current filter or move in sort order. Failed saves retain draft input and surface errors. A stale revision requires reopening the editor before reapplying the draft.

All installation locations are opaque text. `present` means user-asserted present; `missing` and `unknown` retain their prior meanings. No location is validated through directory traversal, opened, written, launched or deleted. The editor states that deletion removes application metadata only.

## Identity, ownership and provenance contract

The v1 `games → library_entries → game_installations` relationships, independent `library_sources`, stable text IDs and restrictive foreign keys remain authoritative. Creation generates independent 128-bit random identities using bundled SQLite `randomblob`, encoded as 32 hexadecimal characters. DSS UUIDv7 was a proposed implementation choice; this small implementation avoids a new dependency while preserving independent durable identity. Identical titles remain separate canonical games; title matching and automatic merges do not exist.

`games` remains the effective bounded-read projection. `game_field_overrides` durably records explicit values for title, release date, genre, developer and favorite. A row containing SQL NULL is an explicit cleared/unknown value; absence of a row means no user override. Creation and metadata save atomically update both overrides and the projection. Metadata save makes the submitted five fields user-owned, including unchanged/cleared fields. There is no reset-to-provider operation yet.

Future provider writers must store provider values separately, preserve override rows, resolve explicit overrides before changing `games`, and increment the game revision in the same transaction for relevant metadata/membership/installation changes. Provider identity belongs to the existing source plus `external_item_id`, never the title. M1.1 does not implement a provider value store, importer or synchronization framework. Allowed membership and installation operations never modify overrides or canonical IDs; real SQLite tests verify this contract.

`origin='manual'` identifies newly created canonical records. Migrated v1 records remain `legacy`; ownership is never inferred from a source label. Installation `state_origin='user'` distinguishes manual assertions; migrated assertions remain `legacy`. Source catalog rows are retained for reuse after removals. Exact manual source names reuse their stable source ID; newly named sources receive independent IDs. Membership status is per membership, not per canonical game.

## API and transaction boundaries

All three commands are typed, main-window capability restricted, and included in ordinary builds:

| Command         | Request                                      | Result                                                                                                             |
| --------------- | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `manual_get`    | `gameId`                                     | One game, revision/origin, effective metadata, override field names, at most 100 memberships and 100 installations |
| `manual_create` | metadata, source name, optional installation | Stable new canonical ID, after atomic game/override/source/membership/optional-installation commit                 |
| `manual_mutate` | game ID, expected revision, tagged action    | Success after commit; structured failure otherwise                                                                 |

Mutation variants: `metadata`, `addEntry`, `updateEntry`, `removeEntry`, `saveInstallation`, `removeInstallation`, `removeGame`. DTOs reject unknown fields. Rust validates titles/optional values, real ISO calendar dates, source names, statuses, IDs, revisions and bounded related-record counts. SQL values are bound. The frontend validates inputs and bounded response contracts too.

Writes use short `BEGIN IMMEDIATE` transactions and compare expected revision under the writer lock; simultaneous edits cannot silently replace one another. Successful mutations advance revision/update time once. Failed operations roll back all projection, override, source, membership and installation changes. Details are read in one short snapshot transaction. Missing and stale records return `NOT_FOUND` and `CONFLICT`; expected validation remains `INVALID_REQUEST`. Existing readiness/storage errors remain structured, with private SQL/OS details masked by the command boundary. Paths supplied as metadata are never logged by this service.

The editor shares the existing frontend request gate with metadata/pages, including its bounded details refreshes. Aborted old page results are discarded by the existing signal/generation contract. No importer-dependent production cache is added. Counts and pages remain separate bounded queries; concurrent external changes may still surface the established `CHANGED`/refresh path rather than promising a cross-command snapshot. M1.1 UI writes invalidate their generation after commit.

## Remaining limitations and next slice

The focused editor limits relationships and sources to 100, has no source rename/delete UI, and preserves reusable empty source records. Legacy canonical deletion and provider relationship mutation are intentionally unavailable. All saved metadata fields become explicit overrides; provider synchronization/reset, richer metadata, artwork providers and importer conflict resolution are future work. Conflict drafts stay visible but are not automatically merged or durably saved; the error instructs users to copy unsaved changes before closing/reopening. Ordinary selection/scroll resets after mutation; filters remain. No backup/export/settings redesign or installer delivery is included.

Recommended next separately authorized M1 slice: define the first Steam adapter's local identity/provenance/idempotency contract and its validation fixtures before implementation. Preserve explicit overrides and canonical IDs; do not select a provider import by title alone. No M1.2 or other work begins automatically. No commit or push has been performed.
