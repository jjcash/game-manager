# M0.3 Virtualized Details View verification

Date: 2026-10-26. Scope: actual SQLite-backed Details View, bounded data/DOM work, safe development dataset selection and frontend measurements. No M0.4 implementation, commit or push is authorized or performed.

**M0.3 is complete within this scope.** Automated checks, native data/failure runs and the measured 15,000-game release case satisfy this slice's completion criteria. The wider M0 gate and the limitations below remain open.

## Baseline and implementation

The initial working tree was clean. Commit `3feba7d` contains M0.2, including migration version 1, deterministic generator v1 and all six benchmark databases locally. Reviewed root AGENTS, README, status, roadmap, PRD/TAS, relevant DSS ownership/query/migration sections, accepted ADR-003/004, the decision register, M0.2 verification and existing frontend/backend/tests. Explicit M0.3 authorization supersedes historical planning-only statements in AGENTS/specifications. Existing M0.1 probe and M0.2 commands/services remain available.

Library now renders title, nullable release date, source labels/membership count and installation presence/copy count from Rust. One row represents one canonical game; multiple memberships/copies do not duplicate games. Mods and Settings remain labeled placeholders. The view uses the existing dark design, column headings, truncation/tooltips, visible selection, a keyboard-focusable ARIA grid, row/column indexes and status/error messages. No unsupported schema fields, images, game-file access or general sorting interface were added.

The accepted stack adds exact JavaScript versions `@tanstack/react-virtual` 3.14.22, `@tanstack/react-query` 5.104.5 and `zustand` 5.0.16, with pnpm lockfile updates. No new Rust dependency or migration is required. TanStack Virtual's mutable API triggers the React Compiler compatibility advisory even though this project does not configure that compiler. A documented, single-call `react-hooks/incompatible-library` exception covers that API; other rules and the zero-warning command remain unchanged. Rows are manually memoized using stable DTO references and primitive position/selection props; no mutable virtualizer instance is passed into memoized rows.

## IPC contracts

Both new commands are asynchronous, main-window-only, capability-checked Tauri commands. Rust owns database queries. No arbitrary SQL, filesystem, shell, environment or database-path command is exposed to React.

| Command              | Request                                              | Success                                                   |
| -------------------- | ---------------------------------------------------- | --------------------------------------------------------- |
| `library_get_info`   | No arguments                                         | `{ total: number, source: string, diagnostics: boolean }` |
| `library_get_window` | `{ request: { limit: u32, offset: u32, sort: "title" | "releaseDate" } }`                                        | `{ offset: number, items: LibraryRow[], queryMs: number }` |

`LibraryRow` contains exactly `id`, `title`, nullable `releaseDate`, `sourceNames`, `entryCount`, `installationCount`, and `installed`. It excludes paths, developer, genre, favorite, descriptions and artwork. `window()` delegates to the existing M0.2 page service and projects the response; it does not duplicate SQLite query logic. Rust's existing request decoder rejects unknown fields, negative/non-integer unsigned values and invalid sort variants. The service enforces `1 <= limit <= 200`, `offset <= 1,000,000`; the frontend requests 100 rows. Ordering remains `(sort_title, id)` or `(release_date, id)`, ascending, with NULL releases first; the UI fixes title order.

`total` is queried separately, once per view generation, permitting full scrollbar navigation without catalog transfer. `queryMs` covers the Rust page service and projection, including pool scheduling/query/decoding, and excludes IPC serialization/transport. It is not pure SQLite execution time. Frontend request timing spans native invocation through response validation, excludes waiting for the single-request permit, and includes Rust work. These durations overlap and must not be added together.

Errors retain M0.2's `{ code, operation, message }` structure. `NOT_READY` is retried every 100 ms up to 20 times; other failures require explicit retry. Migration/query/path/purpose failures retain their codes, emit structured local diagnostics and mask private details in the UI. `CONNECTION` and `INVALID_RESPONSE` are frontend errors. Empty success is distinct from failure. A page shorter than the known remaining count produces `CHANGED` and asks for refresh.

This milestone has no application writer/importer. Offset pagination is appropriate for arbitrary jumps in these static datasets; it does **not** claim a transactionally consistent multi-page snapshot under external writes. Refresh creates a new query generation. A real revision/notification contract is required before concurrent library mutation is introduced. Opening a different benchmark path requires restarting the native app.

## Fetching, caching and virtualization

TanStack Query owns metadata/page snapshots, errors, retry and cancellation. Query keys include generation and page number. Queries are fresh for the current generation, with automatic focus/reconnect refetch disabled. Only pages intersecting the virtual range are observed/requested; arbitrary jumps do not fetch intervening pages. Inactive pages are evicted in oldest-fetch order after commits, retaining at most six page entries (600 summaries) in settled state. A render transition may briefly include the previous cache plus newly observed viewport pages before pruning; it cannot grow with library length. Inactive entries also expire after 60 seconds. No full-catalog array is assembled.

The shared request gate permits one native page invocation at a time, including across refresh/navigation. Aborted queued entries are removed immediately. Tauri invoke does not physically cancel an already running SQL command: its permit stays held until settlement, then an aborted result is rejected. Query cancellation/generation keys prevent old data from replacing current data. Unmount clears the view's QueryClient and queued work; one already running native request may finish. Metadata requests are separate from the page gate.

Zustand holds only one selection `{id,index}` and a scroll offset. IDs remain selected across page eviction; unloaded keyboard destinations temporarily hold an index until the actual ID arrives. Arrow Up/Down, Home/End and Page Up/Down navigate and scroll. Mouse selection focuses the grid. Navigation away/back restores in-session selection and scroll position while querying a fresh bounded view. Selection is not persisted across process restart.

TanStack Virtual uses fixed **38 CSS-pixel rows**, **8 overscan rows per side**, and ResizeObserver-backed viewport measurement. Mounted rows are approximately `ceil(viewportHeight / 38) + 16`, with boundary clipping and at most one partially visible row. The viewport is constrained to 190–700 CSS pixels; horizontal overflow supports narrower windows. Virtualizer geometry metadata may scale with total count; game records and row components do not. No artwork, variable-height text or animation work is present.

## Development datasets and safeguards

Normal startup retains the M0.2 application database initialization path and never seeds data. Only a build compiled with `--features benchmarks` reads `GAME_MANAGER_BENCHMARK_DB`. The variable selects an existing absolute local SQLite path; without it, ordinary application behavior is retained. A normal build ignores the variable.

`Database::benchmark_view` uses SQLite read-only connections, validates benchmark purpose, exact migration versions/checksums/success flags, supported generator/complete metadata and matching canonical count. It never runs migrations, creates a missing file, changes journal mode or writes the selected database. Application-purpose databases are refused. All six sizes are supported: 500, 2,000, 5,000, 12,320, 15,000 and 25,000. Missing/inaccessible/incompatible data yields a visible backend error and no fallback. Restart after correcting the configured path. Backend diagnostics contain the local failure; successful development diagnostics show source path and actual count.

The native benchmark runner uses the already generated seed-42 files and a separate WebView profile under ignored results. SHA-256 before/after protects the measured main databases. Neither real user databases nor game installations are benchmark targets.

## Instrumentation and method

Instrumentation is enabled only by Rust debug builds or explicit `benchmarks` builds. Ordinary optimized application builds do not render diagnostics or collect request/frame/profiler samples. The diagnostics component updates itself once per second without rerendering the table. Request, Rust query, React render and frame samples each retain at most 1,024 values. Request/query distributions include successful, non-cancelled responses only; abandoned native work still holds the gate but is not included in these latency distributions. Percentiles, including the reported median/p50, use nearest rank. Frame sampling is opt-in, stops on unmount, and excludes hidden-document samples. It reports requestAnimationFrame intervals, p95/p99/max and counts above 50 ms; it does not estimate achieved FPS. React Profiler actual render durations and commit counts require development React; optimized builds correctly return no samples. `performance.memory`, when present, is a browser-specific heap estimate; unavailable values remain explicitly unavailable.

`initialInfoMs` and `firstUsableMs` begin at Library component creation, including backend readiness retries. First usable is a committed view with data, not a native process/window-start stopwatch or paint trace. Frame intervals include driver/idle time; they do not alone prove smooth physical scrolling. Process-tree memory is collected externally using Windows process metrics; private bytes are committed private memory, and summed working sets can duplicate shared pages. Point samples do not establish leak-free long sessions.

Runner: `benchmarks/frontend.ps1` and Node-stdlib `benchmarks/frontend.mjs`. It attaches to explicitly enabled **loopback** WebView2 remote debugging, drives the actual bundled frontend/native IPC, and writes ignored JSON. Normal startup never enables debugging. It tests 25 wheel events (38 pixels, approximately 70 ms apart), 100 successive-frame long-distance jumps, 20 distributed windows waited through actual data arrival, End, mouse/Arrow Up selection, Mods/Library return, emulated viewport/scaling, and selection/scroll restoration. A separate missing-database launch verifies the native error state; the native retry click was attempted but blocked by unavailable automation geometry. Page rejection/retry is covered by frontend tests, and storage failures by Rust integration tests. Physical scrollbar dragging, native border resizing and actual Windows scale changes require separate evidence.

Environment: Windows 11 Pro 10.0.26200, Ryzen 5 4500 (6 cores), 64 GB installed reference RAM (66,898,684 KiB visible). E: is the M0.2 reference NVMe SSD; no HDD/reduced-memory result is inferred. Node 26.12.1, pnpm 12.15.0, Rust 1.99.1 Windows MSVC. Optimized native build uses opt-level 3, LTO, one codegen unit, panic=abort; the frontend uses Vite production React unless explicitly noted. Fixture generator v1, seed 42, schema 1, directory `E:\dev\game-manager\benchmarks\data\m0.2-2026-10-25-01`. No controlled filesystem-cache purge; repeated process runs retain OS caches. Normal IDE/Windows activity remains uncontrolled. 64 GB is not a minimum requirement.

## Limits and recommended M0.4 work

No search, filters, general sorting UI, artwork, store import, jobs, mod deployment, real-game access, cloud/mobile, tools or extension architecture is included. The count is static within a query generation; add revisions before mutation/import work. Deep OFFSET queries remain a measured prototype choice, with keyset/indexed-position alternatives available if later measurements justify them. Refine cache/concurrency/overscan only against measured workloads. Keep Rust query time, IPC duration, React rendering, frame pacing and process memory separate.

M0.4 should be separately authorized and scoped against the roadmap: define query/revision behavior for future search/filter/sort, reuse the bounds and stale-work tests, and retain the M0.3 native scenarios as a regression baseline. HDD, lower-memory hardware, controlled cold-start/paint tracing, long-duration memory trends, physical scaling and concurrent I/O remain future validation. Do not infer production readiness or full M0 completion from this view. Stop before implementing M0.4.
