# M0.7D - Whole-process startup profiling and optimization

Verification date: 2026-10-27. **M0.7D is complete within the measured synthetic investigation scope. The one-second warm target is not met consistently, no production startup optimization is adopted, and the overall M0 gate remains open.** No commit, push or M0.7E work is performed.

## Exact timing definitions and uncertainty

- **Process creation:** Windows `Process.StartTime` from a retained native handle. `createdUtc` retains fractional milliseconds; the runner's numeric epoch truncates to integer milliseconds, adding up to one millisecond to joined durations. No pre-process launcher work is included.
- **Earliest Rust entry:** first statement in `main`; CRT/loader work preceding `main` is outside it. `run-entry` remains available for historical compatibility.
- **Native milestones:** opt-in benchmark stderr JSON records UTC `SystemTime` and process-local monotonic `Instant` elapsed time, anchored at the first mark. Monotonic differences distinguish context generation, runtime build, setup, directory resolution, artwork initialization, asynchronous database work, pool construction/connection PRAGMAs, identity/migration validation and state publication. Milestones bracket operations including scheduling/delivery; they are not pure CPU timers. Detailed marks are buffered (maximum 128 pending events) and flushed by a post-startup artwork-stats request or normal exit. Abrupt termination before flush can lose buffered timing evidence; initialization errors retain their independent existing diagnostics. Legacy-mode runs preserve M0.7C's two synchronous JSON writes and separately record their completion, while buffered profiling and native-timing-off controls remove those writes from the critical path. Do not attribute observer removal to production optimization.
- **Backend publication:** the once-cell contains success or a preserved failure. It is not automatically success; real metadata/window IPC verifies readiness. The desktop identity probe deliberately confirms IPC only.
- **Window construction:** ordinary runs retain the configured Tauri window. Locked Tauri 2.12.5 source creates configured windows in internal `app::setup` before application setup; `runtime-built` to `setup-entry` brackets this path and other internal setup work. Separate `-ProfileStartupWindow` runs set only the benchmark context's `create` flag false and call `WebviewWindowBuilder::from_config(...).build()` at the start of setup, bracketing that entire synchronous call. This changes internal asset-setup ordering, so those runs are profiling controls, not ordinary-path before/after timings. Native HWND creation and internal WebView2 environment/controller subphases are not independently timestamped.
- **First window visibility:** external `IsWindowVisible` polling retains last-absent/first-present UTC bounds. A nominal 10-ms sleep does not guarantee a 10-ms bound; raw brackets retain scheduling/polling delays. Visibility does not mean painted pixels. Visibility-to-rows is `[rows - visibleUpper, rows - visibleLower]`, calculated per launch before aggregation.
- **Navigation and frontend:** browser `performance.timeOrigin` anchors Navigation Timing; Tauri page-load callbacks are separate event-delivery observations. `gm:frontend-entry` marks the main module body after static imports have evaluated, not the first JS byte. Shell readiness is the existing React layout-effect commit. Navigation/resource loading, module evaluation, React work, layout and presentation are not interchangeable.
- **Metadata/page:** first native command-entry/completion spans include actual backend work; browser metadata/page invoke distributions include transport/callback work. Initial filtered-count service excludes the subsequent global counts/source queries. The parser preserves the first attempt rather than later diagnostic probes; raw marks retain every attempt.
- **Usable rows:** unchanged M0.7C layout-effect condition: current successful non-placeholder metadata and real row data for every visible virtual item, with at least one visible item for these populated fixtures. Empty-library correctness is tested separately and excluded from process-to-rows distributions. No fake-ready, placeholder-only or rAF substitute is used.
- **Visible thumbnails:** existing maximum recorded ready timestamp among successfully loaded visible images, separately from rows; invalid/missing synthetic artwork may remain a placeholder. This is image readiness, not display time. Zero-worker runs have no image-ready value.
- **Clock joins:** same-host Windows UTC and browser timeOrigin/now join the process epoch. UTC clock adjustment, independent clock implementations and browser quantization remain uncertainties; native within-process phase differences use monotonic time. A post-startup host-before/browser-clock/host-after observation retains a transport bracket, not a proven exact synchronization bound. Shell commits and rAF do not establish first paint, physical input latency, compositor/GPU presentation or achieved FPS.
- **Resources:** age-validated per-PID private bytes/working sets are post-driver points after startup settling, not startup peaks or hard memory bounds. Native `TotalProcessorTime` at collection includes post-startup time and excludes child CPU. Exact startup CPU, DLL/module-loading, disk-read, thread scheduling, security scanning and WebView2 internal CPU attribution are unavailable without a usable system trace.

## Candidates and selected changes

No production startup optimization is adopted. The selected change is bounded, opt-in measurement infrastructure plus recovery/regression probes. Normal libraries remain asynchronous, unseeded, and gated on the actual database result.

| Opportunity                                                                                  | Measured evidence and decision                                                                                                                                                                                                                                                                                          |
| -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Defer synchronous artwork/configuration/directory work                                       | Approximately 3-4 ms application setup in the clean window profiles; ownership/source validation and temporary-file recovery remain mandatory. No evidence of a material whole-process benefit justifies changing this order.                                                                                           |
| Move database initialization before window construction                                      | Database task about 21-39 ms versus 717-917-ms window construction in reused-profile controls. Some overlap may be possible, but moving path resolution/state/initialization earlier changes lifecycle/error ordering and does not remove the dominant aggregate. No broad startup refactor is justified in this slice. |
| Skip/reorder SQLx migrations, identity, count or FK/WAL checks                               | Rejected. Mandatory validation and storage correctness remain intact; benchmark checks must not be weakened to improve timing. No extra connections or parallel migration work.                                                                                                                                         |
| Remove redundant initial metadata queries or add caches                                      | Initial metadata command is about 2-8 ms in the profile controls. No new count cache, query/index change or unproven optimization is adopted.                                                                                                                                                                           |
| Change WebView arguments/security, reuse global environments or construct a fake ready shell | No safe measured candidate with preserved behavior is established. No security protection/runtime feature is disabled, and no fake-ready boundary is introduced.                                                                                                                                                        |

Existing Rust tests verify pending state, persistent initialization failure, migration rollback/checksum/newer-schema failures, exclusive locks and per-connection FK enforcement.

All completed timing, profiling, recovery and regression processes close normally with exit zero. The interrupted recovery-wait pilot and heavy stderr profiling pilot remain excluded/retained as described above.
