# M0.5 — Bounded synthetic artwork and thumbnails

Date: 2026-10-26. **M0.5 is complete within this synthetic-prototype scope.** Automated checks, normal production builds/launch, native artwork and contention measurements are verified; broader M0 goals and the limitations below remain open. Scope is M0.5 only. No commit, push, importer, M0.6, provider, real-game scan or mod operation is included.

## Baseline and architecture

Started with a clean working tree at `2cd0173`, which merges M0.4 (`b86b26f`). Reviewed AGENTS, README, PROJECT_STATUS, ROADMAP, relevant PRD/TAS/DSS and ADR-004 sections, M0.3/M0.4 evidence, Rust storage/query services, Tauri capabilities, React virtualization, request gating, caching and native benchmark transport. Historical planning-only language in AGENTS/ADRs does not override this explicitly authorized milestone or PROJECT_STATUS.

The existing SQL, schema, indexes, metadata request gate, 100-row windows, six-page cache, fixed 38-pixel rows, eight-row overscan, selection and controls remain. Artwork has its own service and admission. No SQL optimization is hidden in this milestone. The compact 48×27 CSS-pixel column reserves its geometry immediately; sources never reach React.

Request flow:

1. Only mounted virtual rows subscribe. Visible rows have priority zero and overscan rows priority one. There is no distant artwork prefetch.
2. A shared frontend scheduler batches effects for 16 ms, deduplicates game IDs, prioritizes visible subscribers and admits two native requests. Released queued work is removed immediately. Running work retains admission until settlement and cannot notify released subscribers.
3. `artwork_get_thumbnail({id})` accepts a canonical synthetic game ID, validates exact seed/prefix/ASCII ordinal/range and maps it to a deterministic shared source. No path, URL, filename, transformation or SQL is accepted from React. The explicit main-window command permissions are generated by the existing build mechanism. No filesystem plugin, asset protocol or broad filesystem URL capability is enabled; the existing data-image CSP is sufficient.
4. Rust admits two distinct source jobs with no backend work queue. Duplicate source jobs share a watch result, with at most eight admitted waiters per source. Work runs through `spawn_blocking`, independently of SQLite and the library gate. Dropping a waiter does not cancel ownership of an admitted worker or leak a slot.
5. Rust validates the controlled source, reads bounded bytes, fingerprints them, checks the memory and derived caches, validates format and dimensions, decodes/resizes and emits a 64×36 PNG data URL. Missing/corrupt/inaccessible assets return artwork status and an immediate lightweight placeholder; they never fail a library query.
6. React validates response shape and bounded PNG data URLs. Stable memoized rows/images reuse the same source strings. Released/changed identities cannot display stale results. Refresh clears the frontend cache and revalidates mounted artwork. Browser PNG loading uses asynchronous decoding and load/error events; no claim is made that browser internals never decode a reused URI again.

The focused Rust `image` dependency enables only PNG/JPEG, without a general media framework or image-provider stack. `base64` serializes small thumbnails through existing IPC. Cargo.lock records the exact resolution. Decoder API/limits and Tauri command behavior were checked against [image ImageReader](https://docs.rs/image/0.25.10/image/struct.ImageReader.html), [image Limits](https://docs.rs/image/0.25.10/image/struct.Limits.html) and [Tauri commands](https://v2.tauri.app/develop/calling-rust/).

## Ownership, cache policies and limits

| Resource                   | Enforced policy                                                                                                                                  |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Source formats             | PNG and JPEG only; magic-byte detection, no extension trust                                                                                      |
| Source encoded size        | 8 MiB; bounded read also checks growth beyond the limit                                                                                          |
| Source dimensions          | At most 4,096 per axis and 4,194,304 total pixels, checked before full decode                                                                    |
| Decoder allocation setting | 64 MiB per decoder; image documents allocation limits as best effort, while dimension limits are strict                                          |
| Thumbnail                  | Exactly 64×36 RGB PNG, at most 16 KiB; displayed at 48×27 CSS pixels                                                                             |
| Native artwork jobs        | Two distinct active jobs, zero queued jobs, at most eight waiters per source                                                                     |
| Frontend artwork           | Two active requests, 32 queued distinct IDs, visible priority; obsolete queued work removed                                                      |
| Native result cache        | 128 data URLs, LRU; maximum encoded payload implied by count/thumbnail cap is about 2.7 MiB of ASCII, excluding allocation overhead              |
| Frontend result cache      | 128 results, maximum 22,000 characters each (at most about 5.4 MiB if represented as two-byte strings, excluding object overhead)                |
| Frontend freshness         | Successful results revalidated on subscription after five seconds; failure results after two seconds; explicit refresh clears cache immediately  |
| Derived disk cache         | At most 256 indexed files and 4 MiB, reserved before publishing; oldest indexed entries evicted; startup enumeration order is not persistent LRU |
| Temporary files            | At most two 16-KiB writes; recognized interrupted writes removed during next service open; unknown/redirected content preserved and refused      |
| Diagnostics                | At most 1,024 request samples and 32 recent artwork records in a diagnostics snapshot; benchmark frame rings 4,096 and long-task/spike rings 128 |

Both source identity and transformation version are in derived keys. The bounded source bytes are fingerprinted on every backend request, so even a same-length/same-name replacement invalidates native results. This noncryptographic fingerprint is a disposable-cache revision mechanism, not a security/content-authentication claim. Older memory variants of a source are removed; old disk variants expire by capacity. A source modified while continuously mounted is revalidated on refresh or a later subscription, not watched continuously. There is no importer/writer revision contract yet.

The fixture root contains `originals/`, `thumbnails/`, `temporary/` and a completion marker. Only the latter two directories are automatically reclaimed. Original source images remain untouched by cache eviction. No installation, database backup, mod package, deployment backup or recovery journal belongs to this cache. Normal optimized startup has no fixture source and never generates artwork or seeds a library. Only an explicit benchmark build honors `GAME_MANAGER_BENCHMARK_ARTWORK`; the thumbnail service is implemented for this synthetic prototype, not claimed as production provider/import functionality.

Canonical containment checks refuse linked/redirected sources, cache entries and directories. The selected root is trusted application-controlled storage; this is not a sandbox against a hostile same-user process racing filesystem replacement. There are no user-supplied paths over IPC. Cache startup refuses unknown files rather than deleting uncertain content. The directory index and all retained data stay bounded independently of 25,000 rows; rapid jumps discard intermediate queued consumers and may leave at most two obsolete native jobs finishing. Browser decoded-image/cache internals and process allocator retention are outside application cache accounting and must be assessed with measurements.

## Deterministic disposable fixtures

Generator version 1 uses procedural gradients/block noise, PNG and JPEG qualities 45/70/90. Typical original dimensions are 320×180, 640×360 and 960×540, with 2,048×1,024 large valid files and 4,097×1,024 rejected files. Missing (multiples of 17), corrupt (19), unsupported GIF-signature (37) and oversized (31) cases have deterministic precedence. Twenty percent of game indices map into a shared 32-source set; others wrap through 1,024 sources. Repetition exists even at 500 games. No commercial artwork or network image source is used.

The marker records version, game count and seed. Canonical IDs use the existing SQL generator's seed and ordinal. Six SQL dataset sizes are supported, including the four required here. Generation creates a new directory exclusively and writes its completion marker last. A partial failed generation is preserved for inspection and cannot be mistaken for complete data.

From the repository root, with Rust/pnpm on PATH:

```powershell
cargo build --manifest-path apps/desktop/src-tauri/Cargo.toml --release --features benchmarks --bin artwork-fixtures --bin library-bench --locked
foreach ($size in @(500, 12320, 15000, 25000)) {
  ./apps/desktop/src-tauri/target/release/artwork-fixtures.exe generate "E:\dev\game-manager\benchmarks\data\artwork-$size" $size 42
}
cd apps/desktop
pnpm tauri build --no-bundle --features benchmarks -- --locked
cd ../..
./benchmarks/frontend.ps1 -DatabaseDirectory E:\dev\game-manager\benchmarks\data\m0.2-2026-10-25-01 -ArtworkDirectory E:\dev\game-manager\benchmarks\data -ArtworkScenarios -Runs 2 -ResultsDirectory E:\dev\game-manager\benchmarks\results\m0.5-native-01
./apps/desktop/src-tauri/target/release/library-bench.exe query-measure --database E:\dev\game-manager\benchmarks\data\m0.2-2026-10-25-01\synthetic-v1-seed-42-25000.sqlite3 --artwork E:\dev\game-manager\benchmarks\data\artwork-25000 --iterations 50
```

Cleanup is an explicit operation against a marked, canonical `benchmarks/data/artwork-NAME` root. It validates the resolved absolute root and directory inventory before recursive removal, refuses redirects/unknown content and cannot target an installation or normal data root. It deletes disposable originals as well as derived files only because the caller explicitly requests fixture cleanup:

```powershell
./apps/desktop/src-tauri/target/release/artwork-fixtures.exe clean E:\dev\game-manager\benchmarks\data\artwork-500
```

Choose new roots/results for a new run or explicitly clean/regenerate fixtures. Generated images, databases, profiles, screenshots and raw benchmark reports stay under ignored `benchmarks/data/` and `benchmarks/results/`.

## Known limitations and recommended M0.6

This is the synthetic-thumbnail prototype: one fixed RGB landscape variant, 1,024 possible original source slots with deliberate repetition, and no production asset registry/provider/import integration. Title-ordered sampling has strong alias correlation; separate ordinal saturation probes cover eviction/churn. One benchmark process owns a root; concurrent independent processes or external writers are not coordinated by this prototype. The controlled-root path checks are not a security sandbox against hostile same-user filesystem races.

Application-owned caches/queues and source dimensions/bytes are bounded. `image` allocation limits are best effort, and WebView caches/allocators are not a hard application process-memory budget. Short-run stabilization does not replace hours-long or reduced-memory validation. HDD, physical Windows scaling, controlled OS-cold/native process-start timing and lower-memory hardware remain unmeasured here.

The unchanged installed/not-installed/combined queries remain expensive at 25,000 and worsen under continuous artwork in several paired cases. Periodic memory observation changes some recorded tails; all comparisons identify their instrumentation. Long frames remain unexplained after an approximately aligned V8 CPU profile, and a long interval also occurred without periodic memory sampling. No achieved FPS or root-cause claim is made.

Recommended M0.6, only after separate authorization: a synthetic background-import/load simulator with bounded admission, progress and safe cancellation, measuring interactive SQL/artwork competition. Include measured thumbnail worker-count/backoff/priority experiments. Keep M0.4 stress-count optimization a separately scoped proposal; no new index/count cache/FTS switch is introduced here. Deeper renderer/native tracing and longer memory/hardware validation still need their own evidence. No importer or M0.6 implementation is started automatically.
