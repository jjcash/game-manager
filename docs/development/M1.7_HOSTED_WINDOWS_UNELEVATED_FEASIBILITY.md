## What the handle assertion measures

[`no_privileged_handle_inheritance_and_bounded_cleanup`](../../apps/desktop/src-tauri/tests/standalone_launch.rs) launches the current Rust test executable as an exact single-test subprocess. Within that subprocess, [GetProcessHandleCount](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesshandlecount) receives `GetCurrentProcess()`. It measures all executive-object handles owned by that Rust process, including fixture/runtime/database activity. It does not count the PowerShell wrapper's handles, C# helper's handles, or handles owned by the synthetic executable.

The original loop called `f.add()` before every preparation/launch/wait. That method performs profile creation and details reads through a separate production `Database` pool. The launcher itself uses `f.connection`, a dedicated `SqliteConnection`. The pool is lazy, with minimum 1 and maximum 4 connections. Serializing tests and using a fresh exact-test process excluded other test cases, but did not exclude this pool's own asynchronous connection activity.

## Correction and resource invariant

The only Rust change is the resource test:

1. Retain the native unrelated-inheritable-event negative sensor and ordinary `Command` positive control unchanged.
2. Configure the repeated profile before measurement and explicitly await closing the separate fixture pool.
3. Keep the already-open dedicated connection for the complete preparation/revalidation/native-creation path.
4. Run all 20 launches, requiring **exactly `before + 1` immediately after creation** and **exactly `before` after every wait/drop**.
5. Require final equality, replacing the old end-only `after <= before + 2` assertion.

No allowed count was increased, no assertion/test was removed, and no launcher warmup was added. Reusing the configured profile removes metadata-mutation pool activity, while every measured iteration still executes the complete launch path. Other native tests retain profile mutation/staleness coverage. Exact equality after each iteration catches a single retained handle immediately, a stronger launcher-resource invariant than tolerating two after the entire loop.

Ten fresh-process repetitions (`corrected-1.txt` through `corrected-10.txt`) passed, each `93 -> 93` over 20 launches. A deliberate temporary replacement of `drop(thread)` with `mem::forget(thread)` made iteration 0 fail: observed 101 versus expected 100, exit 101 (`injected-thread-leak-verified.txt`). The injection was restored; test-support source has no final diff. This demonstrates that the revised sensor still detects an actual native ownership defect.

Ownership review of the unchanged [test-only launcher](../../apps/desktop/src-tauri/tests/support/standalone_launch.rs): token, attribute-only directory and NUL handles use Rust RAII; initialized attribute storage deletes its native list on exit; its borrowed handle array outlives the list; the primary thread handle drops immediately; the returned process handle drops after bounded child completion. Attribute allocation is memory, not a process handle. No production launcher or new process-management service was added.

## Fixed-purpose CI helper and token gate

The [workflow](../../.github/workflows/ci.yml) changes only the Rust invocation/comment. The [PowerShell wrapper](../../.github/scripts/Invoke-M17UnelevatedTests.ps1) compiles the [C# helper](../../.github/scripts/M17UnelevatedTests.cs) with the existing Windows .NET Framework compiler and warnings as errors. No new package, dependency download, action, privilege grant or runner configuration is introduced.

The helper retains this fail-closed sequence:

1. Query/log the parent token.
2. [CreateRestrictedToken](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-createrestrictedtoken) with `LUA_TOKEN | DISABLE_MAX_PRIVILEGE` (`5`), explicitly disabling Administrators (`S-1-5-32-544`) and LocalAccountAndAdministrator (`S-1-5-114`). Set only the new token's integrity to Medium; never write `TokenElevation`.
3. Require primary-token type, `TokenElevation=0`, exact Medium SID `S-1-16-8192`, administrator groups absent or deny-only without enabled/default-enabled bits, and no enabled privilege other than `SeChangeNotifyPrivilege`.
4. [CreateProcessAsUserW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessasuserw) starts the fixed helper executable suspended, without inheriting native handles. Open/query the **actual suspended process token**, applying the same checks before `ResumeThread`.
5. The resumed helper queries/checks its own actual process token before any probe, compiler or test work. Reject unknown phases/result paths; accept no caller-selected executable or command.
6. Require harmless probe exit 17 and exact independent stdout/stderr sentinels. Then compile/run ordinary synthetic prerequisites, including the same MSVC manifest switches; the administrator-manifest prerequisite is compiled but not executed.
7. Require the dedicated native command to report all 12 tests, zero failures/ignored/filtered tests, then run unchanged `pnpm test:rust` (the full all-feature Rust suite).

The API documents preservation of token type and an assign-primary privilege exception for a restricted version of the caller's primary token. Quota privilege may still matter and the API may temporarily enable an already-held necessary privilege. These facts support the candidate; they do not prove GitHub's particular elevated token will filter successfully. Error 1314 is not worked around.

Local candidate, pre-resume actual child and inside-child checks report primary type 1, elevation 0, Medium integrity, both administrator SID attributes `0x10` (deny-only), and only enabled `SeChangeNotifyPrivilege`. The local parent already has elevation 0. Fault-injected diagnostic copies rejected verification before resume and inside the probe child (both exit 1); prerequisites/native tests did not run. No fallback to elevated fixtures, linked-token assumption, UAC change, credentials, desktop ACL modification, arbitrary command surface, native-test exclusion or production IPC was introduced.

Token/process/thread handles and unmanaged token-query/SID buffers retain explicit ownership. Failure while suspended terminates only the directly owned child and waits for it before explicit native-handle release. If termination cannot be confirmed, cleanup failure is logged and handles are retained until helper exit; this does not claim the process was cleaned up. Normal process/thread handles are closed after signaled completion. Forced termination of the helper itself cannot guarantee execution of its cleanup code.

A second cleanup attempt can add another bounded wait. Unconfirmed termination is reported, not silently treated as success. Forced workflow cancellation, host failure and abrupt wrapper termination cannot guarantee scratch/descendant cleanup. Managed exception paths perform bounded direct-child cleanup; complete descendant cleanup is deliberately not promised. The existing CI job/runner teardown is the final safety boundary.

## Environment inheritance decision

Keep NULL `lpEnvironment`: Microsoft documents that it inherits the calling process's environment. Subsequent `.NET Process` commands likewise inherit the restricted child's block; this is compatible with Rustup/Cargo and MSVC. This helper changes a token, not an identity/profile/environment boundary.

Ordinary necessary configuration includes Windows `SystemRoot`/`WINDIR`, user/profile/AppData and temporary directories, `PATH`/`PATHEXT`/`ComSpec`, and Rustup/Cargo homes/toolchain/target settings when configured. MSVC/SDK `INCLUDE`, `LIB`, `LIBPATH` and installation/version/architecture variables may be required when a developer shell supplies them. Rust flags and Cargo configuration variables can also affect compilation. Which are essential varies with Rustup, linker discovery and runner setup; successful local compilation is not an exhaustive minimum-environment proof.

An ignored diagnostic copy compared a digest of 29 ordinary Windows/Rust/MSVC variables between parent and each restricted phase, logging only equality, never values or digest. The probe/prerequisite/native-phase comparisons passed. Actual Rust/MSVC compilation passed under that environment. The prerequisite Rust fixture now explicitly verifies its reported `SystemRoot` against its immediate parent's value. Compiler internals were not instrumented to dump their environment.

Repository-configured workflow permissions are `contents: read`; checkout uses `persist-credentials: false`; there is no `secrets` expression, secret environment assignment, credential logon, publishing or deployment. This is a configuration review, **not proof that a hosted runner or local caller has no authentication material**. Injected environment credentials, action-runtime authentication or same-user credential files may still be accessible. This investigation did not inspect credential files, and no full environment/secret values were printed.

`PATH` chooses the first existing rooted `rustc.exe`, `cargo.exe` and `pnpm.cmd`; Rustup, linker selection, DLL/runtime settings and compiler flags remain caller-controlled. Resolving a full executable path avoids later ambiguous search but does not certify that tool. The only `cmd.exe` invocation is the fixed, validated pnpm path plus `test:rust`; no caller-supplied shell command is accepted. A hand-maintained minimal environment risks omitting MSVC/SDK or Rustup configuration and is not justified by this CI feasibility task. Full inheritance is acceptable for this fixed workflow with no configured secrets, **not a sandbox for untrusted repository code**. Future secret injection requires revisiting that decision; token filtering must never be described as credential isolation.

## PowerShell cleanup and exit handling

Scratch is a freshly created GUID-named child of the resolved system temporary directory. Before recursive deletion the wrapper requires exact parent equality (not a prefix match), the precise generated-name grammar, and a walk that rejects root/descendant reparse points without traversing them. Only that verified directory can be removed, using literal paths. Successful cleanup verifies absence, including executable/log files. This is not adversarial same-user race protection between validation and deletion.

The wrapper holds the native `Process` association so short-lived `Start-Process` executions retain their exit code. A missing exit code throws instead of being interpreted as success. During implementation an initial local copy returned a blank code; that failure is retained as `corrected-wrapper.txt` and was corrected before the final candidate. Result codes are cached before output/cleanup so diagnostics cannot erase an already observed failure.

The original child/test result is always printed. A cleanup failure prints that result plus the cleanup error. A failed child keeps its exact nonzero code; a successful child plus cleanup failure returns 1. Diagnostics with an exclusively locked scratch file verified `0 -> 1` and preservation of `37 -> 37`. The deliberate residues were removed after releasing the locks. Separate checks rejected an outside-parent directory and a child junction; an outside sentinel remained intact. No deletion permissions were broadened. Sudden OS/runner termination may leave scratch; that limitation is explicit.

### Supported behavior versus hypothesis

Microsoft documents [CREATE_NO_WINDOW](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags) as suppressing the console window/console handle for a console application, and `CREATE_SUSPENDED` as preventing the primary thread from running until resume. Neither flag combination is documented as universally invalid for restricted tokens. With no new-console/detached flag, console applications normally [inherit their parent's console](https://learn.microsoft.com/en-us/windows/console/creation-of-a-console).

The hypothesis is that the hosted restricted child's initialization is sensitive to the console arrangement selected by `CREATE_NO_WINDOW`. This is a hypothesis, not a documented explanation for this particular NTSTATUS or proof of a Windows defect. No third-party anecdote is used as evidence of the cause.

Window-station/desktop access is a separate possible initialization constraint. The API documents required access and describes NULL `lpDesktop` inheritance; Windows also documents [process window-station connection](https://learn.microsoft.com/en-us/windows/win32/winstation/process-connection-to-a-window-station) and [thread desktop connection](https://learn.microsoft.com/en-us/windows/win32/winstation/thread-connection-to-a-desktop) rules. The candidate leaves `lpDesktop` NULL, does not name `winsta0\default`, and does not alter any ACL, session, profile, UAC setting, privilege or credential.
