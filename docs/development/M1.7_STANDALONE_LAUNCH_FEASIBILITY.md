## 2. Threat model and exclusions

The threat model was written in proposed ADR-011 before candidate code. A local authenticated desktop user deliberately chooses a configured executable. Stored configuration is metadata; the backend owns authoritative lookup, context validation and execution. The frontend cannot supply raw launch paths, command lines, working directories or environments. The application must be unelevated.

The selected executable gets ordinary user privileges. Its malicious/compromised content, DLL/runtime loading, subsequent child processes and independent requests for elevation are not sandboxed or certified. A compromised application/OS, privileged attackers and adversarial same-user file replacement are outside an executable-integrity guarantee. Stale metadata/frontend state, detectable edit/delete races, cross-game identities, unsupported configuration, accidental privilege/handle inheritance and unintended interpretation remain in scope.

Windows follows junctions, symlinks and other reparses. Neither lexical containment nor file metadata establishes filesystem-object confinement, trust, physical local-volume provenance or immutable identity. A local-drive spelling may resolve through a mapped drive/reparse to other storage. Initial verification is on local NTFS; other mappings/filesystems are not certified. No bespoke confinement framework is required by this execution model. ADR-008's Steam confidentiality boundary is neither imported nor superseded.

## 3. Three distinct contracts

| Concept              | Meaning                                                                                                                      |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Valid stored profile | M1.6 configuration/identity constraints pass; existence, trust and readiness remain unknown                                  |
| Prepared decision    | An internal coherent database snapshot matches the request and supported context; references/configuration resolve lexically |
| Process created      | Windows returned success and an owned process handle/PID; initialization, gameplay and subsequent success remain unknown     |

Even zero child exit is not evidence of gameplay. No session, playtime, achievements, attachment or process supervision is implemented.

## 4. Future request, authorization and revision contract

The test-only request has `gameId`, `profileId`, `expectedProfileRevision`, `expectedGameRevision`, with unknown fields rejected. IDs use the existing 32-character lowercase hexadecimal convention. No second identity/revision scheme or extra installation token is introduced. Installation/membership/source are derived through the persisted chain, never selected independently by launch IPC.

A single indexed join reads one profile and its installation, membership, source, canonical game and optional default; a separate singleton query checks application purpose. Both occur inside the same read transaction. Exact game/profile revisions and matching game association are mandatory. Initial execution supports user-owned standalone profiles bound to manual-source Windows installations. Stored user profiles on provider installations remain valid M1.6 metadata but are unsupported for execution. Detection-state assertions do not prove availability; filesystem checks decide observable availability.

The preparation instant is the successful joined read plus configuration/lexical validation in that snapshot, before transaction completion publishes the internal `Prepared`. `Prepared` is private-field, non-cloneable and consumed by execution. It is never returned to JavaScript. Preparation performs no executable content reads or execution.

Execution requires an explicit simulated user attempt; cancellation refuses before any spawn. A future deliberate Launch action would authorize one contextual attempt, through a narrow local-window capability, not startup/edit/default/restore or a persistent frontend boolean. A compromised same-origin frontend cannot be distinguished cryptographically from a human gesture by this candidate; compromised application code is outside the trust model. Real UI/capability admission remains M1.8 work.

## 5. Freshness and maintenance boundary

Immediately before execution, `BEGIN IMMEDIATE` reserves the writer, repeats all context checks and compares the observed record fields to preparation. Profile saves advance the profile revision; installation/default and other game edits advance the existing game revision. A defensive comparison also catches an installation field changed without revision advancement. A stale profile, game, default, installation or deleted/unrelated profile fails closed. Duplicate labels/targets remain separate IDs.

The writer reservation spans revalidation, filesystem validation and synchronous native creation. Cooperating SQLite writers cannot commit in that interval. There is no await/cancellation point between the final native decision and spawn. The transaction is read-only: dropping it queues rollback/release; no post-spawn commit failure can turn a created child into a failed launch and cause a retry. Subsequent commands and repeated launches verify connection reuse.

Readiness/stopping are explicitly tested with a narrow admission-state harness. Production's actual maintenance guard is **design-only** here: it must close admission and drain an admitted, bounded launch operation before restore/pool shutdown, spanning final readiness through spawn. Run blocking filesystem/native creation away from the UI thread and preserve current job/pool limits. No real service, Tauri command or scheduler is connected in M1.7. Direct same-user database tampering/ABA and executable replacement are not solved by revision checks.

## 6. Reference resolution and executable policy

Reuse public M1.6 `PathRef`/`Configuration` validation. Preserve saved strings without trimming, canonicalizing, expanding, rebasing or mutating them. Relative components are validated before Windows component-aware `PathBuf` assembly; root/drive/prefix/parent components cannot replace the installation root. A relative target or working directory requires a nonempty recorded location that passes the same conservative drive-absolute/backslash grammar. Missing/empty/unsupported location fails explicitly. Schema v4 normally forbids NULL locations; corrupt missing relationships also fail the join.

Absolute references use exactly their saved path. A usable installation location is unnecessary for an absolute executable with omitted/absolute working directory; the installation record and relationship must still exist. There is no process-CWD dependence, PATH search, extension guessing, automatic discovery or directory fallback. Drive-relative, UNC/device namespaces, parent traversal, slash aliases and reserved components are rejected by the existing grammar.

Only explicit `.exe` extensions, case-insensitively, are admitted. Batch, PowerShell/shell scripts, documents, shortcuts, DLL entry points and URI handlers are refused without shell fallback. This does not prevent a deliberately selected executable from itself implementing a shell/interpreter or malicious actions.

## 7. Filesystem and working directory

Immediately before creation, executable metadata must indicate a regular file. The working directory is opened for `FILE_READ_ATTRIBUTES` with `FILE_FLAG_BACKUP_SEMANTICS` and read/write/delete sharing; handle metadata must indicate a directory. This catches denied attribute access without enumeration, content reads, creation or exclusive locks. These are availability/type checks, not PE validation, executable trust or an object-identity pin. Windows decides executable format, execute access, elevation requirement and loader availability.

Explicit absolute/relative working-directory references resolve by the same rules. Omission uses the resolved executable's **lexical parent**, even if a reparse points elsewhere. This launch-time default never changes the persisted profile. Invalid, missing, denied or non-directory locations fail. No directory is created automatically and Game Manager's CWD is never implicitly inherited.

There is a gap between metadata/directory validation and path-based `CreateProcessW`; the directory handle does not bind the process API to that object. Another process may replace files/reparses during it. No executable bytes, hashes, signatures or persistent native identities are inspected.

## 8. Literal arguments and Windows encoding

Windows receives a single mutable UTF-16 command line. The candidate encodes the documented standard Windows C/Rust-runtime convention: every argument is quoted, embedded quotes are escaped, and runs of backslashes before quotes or a closing delimiter are doubled. Argument zero is separately quoted from the absolute executable; `lpApplicationName` independently specifies the full executable. Nothing is concatenated into a shell command or expanded.

Native Rust children report their actual `std::env::args().skip(1)` vector. Tests compare exact ordered values for zero/one/multiple arguments, empty strings, spaces, embedded quotes, backslash/quote and trailing-backslash combinations (runs 0–15), Unicode/emoji, tab/newline, shell metacharacters, 128 empty arguments and four 4096-unit arguments. NUL, 129 arguments, oversized individual/aggregate values fail. The shell-sentinel argument remains literal and creates no sentinel.

M1.6 allows 128 strings, 4096 UTF-16 units each and 16384 total. Actual encoded lines additionally must fit 32767 units including executable, separators, quotes and terminating NUL. Four maximally long all-backslash strings are valid stored metadata but exceed that native envelope and are rejected before execution. Programs using nonstandard parsers, wildcard expansion or raw command-line conventions are not certified; no provider-specific raw mode is implemented.

## 9. Process mechanism, privilege and environment

Rust 1.99.1's stable `Command` does not expose disabling arbitrary inheritable handles or a handle allowlist. Source/API review and a native positive control confirm that an unrelated inheritable event reaches a `Command` child even when its three streams use NUL. The narrower native requirement justifies direct Win32 instead of standard `Command` for the candidate. See the [pinned Rust Windows process implementation](https://github.com/rust-lang/rust/blob/1.99.1/library/std/src/sys/process/windows.rs) and [CommandExt API stability](https://doc.rust-lang.org/std/os/windows/process/trait.CommandExt.html).

`CreateProcessW` receives a non-NULL full executable application name, separately encoded command line, explicit working directory, default process/thread security attributes and NULL environment. Exact creation flags: `CREATE_NO_WINDOW | CREATE_UNICODE_ENVIRONMENT | EXTENDED_STARTUPINFO_PRESENT` (`0x08080400`). No shell, ShellExecute, UAC prompt, token replacement, suspended/detached/breakaway mode or fallback is used. Primary references: [CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw), [creation flags](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags), [attribute/handle list](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute) and [C runtime argument parsing](https://learn.microsoft.com/en-us/cpp/c-language/parsing-c-command-line-arguments?view=msvc-170). Native Rust observations establish the tested runtime contract; documentation alone does not certify every executable.

The current process token is queried with `TOKEN_QUERY`; an elevated token or failed query rejects execution. The test host is unelevated. A synthetic embedded `requireAdministrator` manifest returns error 740 without a successful process or fallback. No elevated process is deliberately created for testing; the elevated-parent refusal branch/token-query failure is source-reviewed rather than exercised under an elevated session. This is not a promise that the selected program cannot later request privileges itself.

The ordinary parent environment is inherited for compatibility, with no user-supplied map or expansion. The fixture verifies inherited `SystemRoot`, without recording a full environment or reading accounts/credentials. Environment can contain secrets or alter DLL/runtime lookup; a production process should not carry application secrets in that environment. No sandbox or child-environment confidentiality guarantee is claimed.

## 10. Handles and lifecycle

A newly opened read/write NUL handle supplies all three standard streams. `STARTF_USESTDHANDLES` plus `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` permits only that handle; `bInheritHandles=TRUE` is required for the allowlist. An unrelated inheritable event is excluded, with a separate positive sensor proving it would signal under ordinary `Command`. Fixture output markers do not reach the runner and stdin reports no input. No parent console or internal IPC stream is intentionally inherited.

Rust RAII owns token/directory/NUL handles and initialized native attribute storage. The primary thread handle is immediately closed. The process handle is returned internally to synthetic tests for bounded waiting, then released. The recommended production behavior is to return the created PID and drop that handle immediately, with no worker/waiter, polling, tracking or automatic termination. PIDs are reusable diagnostics, not later attachment/kill authority.

Cancellation before creation rejects. Cancellation/handle release after creation cannot undo the launch and never silently kills it. A real synthetic launcher-parent exit and a separate immediate handle-drop test both allow children to finish. No application kill-on-close job is introduced; external parent-job/OS policies remain outside the verified lifetime contract.

## 11. Synthetic environment and containment

Tests live only in `src-tauri/tests/standalone_launch.rs`, its support module and `tests/fixtures/standalone/child.rs`; production never imports them. Existing dependencies and real application migrations/manual APIs create disposable persisted fixtures. The harmless Rust child is compiled with the installed Rust compiler into each owned temporary root, with spaces and Japanese characters in its executable path. No fixture binary, PDB, database or result is tracked.

The child reads only its CWD's synthetic control file, reports PID/CWD/own executable/arguments and `SystemRoot`, optionally signals the test's event, and writes relative phase/report/exit files. Controlled exit codes and up to 3000 ms sleep are supported. A four-second in-process watchdog bounds failed stream tests; successful exit ends it. No network, game inspection, account access or arbitrary file target is implemented. Test compiler/linker/ACL tools and a test-host subprocess are development tooling; every candidate execution target is a compiled fixture. No personal game/Steam/Epic files were accessed.

The native matrix requires a genuinely unelevated Windows test host with the documented Rust/MSVC prerequisites. It fails closed on an elevated host rather than executing elevated fixtures or silently ignoring safety tests. CI privilege configuration and a new hosted run are not certified by local evidence.

## 13. Preserved development failures

The first native run had 4 passes and 6 failures. NULL standard-handle fields produced an actual character stdin handle and blocked the Rust fixture before reading input completed. Seven children from that run and one from each of two diagnostic reruns were terminated only after verifying their exact synthetic executable paths and recorded test-parent PIDs. No real program was terminated. Phase files located the stall. The design was corrected to valid NUL streams with a native handle allowlist; a bounded watchdog was then added to the fixture. The original no-input and bounded-exit assertions remain.

The invalid text executable returned 216 rather than expected 193; the test now requires failed creation with either documented invalid-format/machine loader code, preserving the no-fallback assertion. The denied-working-directory fixture initially demonstrated that metadata plus CreateProcess can accept a directory whose ACL denies access; the candidate gained an attribute-only directory open, and the original failure expectation now passes. An embedded manifest build initially conflicted with the linker's default asInvoker snippet; `/MANIFESTUAC:NO` suppresses only that generated snippet before embedding the synthetic requireAdministrator manifest. No test elevated the caller.

A default concurrent-test run observed total process handles 183→186 despite a serial native run at 181→181. Process-wide counts include other Rust test runtimes. The resource test now runs in an exact single-test subprocess, retaining the same threshold and repeat workload and adding the positive inheritance sensor. No assertion was relaxed to hide a native-handle leak. Earlier passing/failing attempts remain in ignored local results where captured; first-run/diagnostic console results are described here rather than misrepresented as raw retained logs.

Final native API review caught an attribute-list lifetime ordering issue: Windows requires the handle-array storage to remain alive until attribute-list destruction. The array is now declared before the RAII attribute list so the latter drops first, including on error. The native matrix, full suites and both Clippy configurations were repeated after this correction.

Initial inspection also encountered unsupported PowerShell brace expansion, an incorrect pnpm PATH candidate and an inapplicable permissions glob. Corrected read-only commands used the documented pnpm `bin` location and actual generated capability layout. PowerShell redirection may label compiler progress as `NativeCommandError`; actual exit codes and completed summaries determine success.

## 14. Performance and maintenance observations

Preparation does not scan the library or call the editor's relationship-list API. Primary-key/foreign-key joins fetch one contextual record. No browsing SQL, query/filter/sort behavior, row geometry, worker/pool policy, benchmark generation or ADR-007 exception changes. The native boundary has one small argument encoder, one snapshot-based preparation/revalidation path and scoped Windows resources, without an adapter/process-manager/security framework.

Synthetic targets/databases were on C: NTFS temporary storage; the repository/reference fixtures are on E: NTFS. This does not certify a physical storage model or minimum system. Warm-cache samples exclude compilation and one warmup; preparation and revalidation-plus-creation are separate intervals. Child initialization/exit is excluded from creation timing. No competing build/test ran during this cohort; ordinary background activity was uncontrolled.

## 18. Final recommendation and stop

**A. Proceed to M1.8 production standalone launch, only after separate authorization.** Deterministic resolution, tested literal arguments, explicit application selection, no implicit shell/elevation fallback, effective stale-context rejection, native failures, bounded resources and a maintainable candidate are demonstrated within the approved synthetic environment. No unresolved critical native safety failure remains in that scope.

Review proposed ADR-011 and carry its explicit limitations into M1.8. Production work must implement the real one-attempt UI/IPC authorization and maintenance-admission guard, integrate a bounded blocking operation, return creation-only results and add production-specific tests. None of that is implemented by M1.7. Reparse/content integrity, custom parsers, elevated hosts, external job policies and broader platform certification remain limited as described above; no sandbox or gameplay claim is justified.

Steam remains deferred; M0 E1–E5 remain unchanged. No commit, push, merge, production integration or subsequent milestone was performed. Stop for review.
