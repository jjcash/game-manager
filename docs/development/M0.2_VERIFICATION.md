## Schema and migrations

Embedded migration: `apps/desktop/src-tauri/migrations/0001_library.sql`. SQLx records version 1 and the migration checksum in `_sqlx_migrations`. The build script tracks migration-directory changes so embedded migrations rebuild when SQL changes.

| Table                | Prototype responsibility                                                                                                                   |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `games`              | Stable canonical ID, display/sort title, nullable ISO release date, genre, fictional developer, favorite, UTC creation/update milliseconds |
| `library_sources`    | Stable source ID, type, display name; no credentials or adapter implementation                                                             |
| `library_entries`    | Canonical game/source association, namespaced external item ID, completion status, added timestamp                                         |
| `game_installations` | Entry-specific copy, root reference, platform/version, present/missing/unknown state                                                       |
| `database_metadata`  | Singleton application/benchmark purpose and synthetic generator version, seed, size, completion marker                                     |

All domain tables are STRICT, with text primary keys, explicit foreign keys, restrictive deletion, boolean/state checks, source/item uniqueness, and per-entry installation-reference uniqueness. A title is deliberately not a uniqueness key. Multiple sources and copies retain separate identities. Indexes cover `(sort_title, id)`, `(release_date, id)`, entry-to-game lookup, source/item uniqueness, and `(entry_id, detection_state)` installation lookup.

Deliberate simplifications: flat nullable genre/developer and favorite fields are synthetic prototype metadata, not a production provider/override schema. Manual entries use an explicit source instead of a null source. Text IDs permit future production UUID selection; the generator uses stable seed/ordinal IDs. No launch profiles, imported playtime, tags/collections joins, provenance resolution, FTS, mod/deployment, trainer, job or cloud tables exist. Summary grouping is canonical-game grouping only, with no configurable grouping UI. `installed` means at least one recorded `present` copy; no filesystem detection is performed.

## Initialization, paths and read services

Rust opens the database asynchronously after Tauri setup. The shell and unchanged `app_get_status` probe remain independent of readiness. A shared once cell records initialization success or structured failure; queries return `NOT_READY` while initialization runs and preserve a terminal error afterward. Initialization examines identity before applying migrations or changing journal mode. Unrecognized files, corrupt files, wrong-purpose databases, dirty/checksum-mismatched migrations and unknown newer migration versions fail without deletion or automatic replacement.

The normal default is Tauri's per-user local application data root, `%LOCALAPPDATA%\io.github.game-manager.desktop\database\library.sqlite3`. Optional `GAME_MANAGER_DATA_DIR` chooses an absolute initial installed root; there is no automatic relocation or portable mode. Relative, parent-traversing, UNC and Windows device paths are rejected. Mapped network drives and reparse-point storage topology are not comprehensively detected; use a known local filesystem. Benchmark paths are separately mandatory CLI arguments, reserved with create-new semantics. Existing files and orphan WAL/SHM/journal files are refused; no overwrite switch exists. Measurement also rejects empty/unrecognized files rather than initializing them.

Initial measured configuration: maximum four connections, minimum one, per-connection foreign keys, WAL, FULL synchronous durability, five-second busy timeout, ten-second pool acquire timeout, 2 MiB suggested page cache per connection, 64 cached statements, and 1,000-page automatic WAL checkpoint. The generator is the only implemented writer and commits batches sequentially. There is no claim of a production write scheduler or concurrent-import tuning. Full integrity/foreign-key scans are explicit validation operations, not mandatory startup scans. Closing all benchmark connections checkpoints WAL before file-size measurement; copying a live main database alone is not a backup mechanism.

Read-only Tauri commands `database_get_status` and `library_get_page` are restricted to the local main-window capability. They return typed Rust DTOs; no arbitrary SQL/path/shell input is exposed. Status includes schema/SQLite version, purpose, pool/WAL/FK settings and counts. Page requests accept only title/release-date ascending sorting, `limit` 1–200, and `offset` 0–1,000,000. Dates with unknown release values sort first. Both orders end with the stable ID tie-breaker. A materialized indexed page is selected before relationship summaries are calculated; no full library is returned to React. Empty canonical games return an empty source label. Offset navigation intentionally trades O(offset) index traversal for simple arbitrary page positions at prototype scale; keyset/revision behavior remains later work. New commands are tested through Rust/service/serialization checks; the existing frontend does not invoke them yet.

Local startup errors are serialized as JSON to stderr. IPC preserves error code/operation while masking private SQLite/OS details. A persistent diagnostic log and database recovery screen are not implemented; the shell remains the M0.1 placeholder interface.

Configuration references: [SQLx connection options](https://docs.rs/sqlx/0.9.0/sqlx/sqlite/struct.SqliteConnectOptions.html), [SQLx migrations](https://docs.rs/sqlx/0.9.0/sqlx/migrate/struct.Migrator.html), and [SQLite WAL constraints/checkpoints](https://sqlite.org/wal.html). SQLx 0.9's direct migrator entry point is used to avoid its generic Acquire lifetime limitation in a spawned Send future; dependency upgrades must revalidate this call.

## Generator and reproducibility

The `benchmarks` Cargo feature enables the development-only CLI and synthetic module; the normal desktop build omits them. Generator version 1 uses SplitMix64 with wrapping arithmetic and seed/ordinal IDs. All data is fabricated, including five weighted synthetic sources, composed Unicode titles, eight genres, 60 studios, favorites, four completion states, varied release dates from 1985–2025 with unknown values, installed/uninstalled games, missing copies, multi-source ownership and multiple copies per entry. Canonical titles are unique by construction within all supported sizes; the schema still allows distinct canonical IDs with tied titles.

Each bulk transaction contains at most 250 games and their related entries/copies. Partial generation preserves prior committed batches, rolls back the failing batch, and keeps the dataset incomplete. Incomplete datasets cannot be measured or automatically reseeded. `synthetic://` installation references never trigger filesystem access. Equal seeds compare equal across all logical game/source/entry/installation fields; database bytes and SQLx execution timestamps are not promised identical.

From the repository root:

```powershell
./benchmarks/run.ps1 -DatabaseDirectory E:\dev\game-manager\benchmarks\data\run-01 -Seed 42 -Iterations 50
```

Use a new directory. See [benchmark commands and methodology](../../benchmarks/README.md) for individual `generate` and `measure` commands. Generated databases and machine reports are ignored by Git.

## Limits and next recommended scope

These are database-only results. No scrolling, frontend IPC throughput, frame time, full application startup, memory stability, artwork, search/filtering, or concurrent job/import target has been demonstrated. HDD, controlled OS-cold, lower-memory, sustained concurrency, disk-full and process-kill migration testing remain unperformed. The verified migration failure tests cover transactional SQL failure and compatibility/dirty/checksum handling, not every hardware/power-loss condition. Only the initial schema migration exists; future data-transforming migrations need separate backup/upgrade validation.

M0.3 should connect typed frontend IPC to the existing bounded summary service, add the virtualized Details View with bounded row/data caching, readiness/error handling and title/release sorting, then measure row mounting, frame time and memory at 12,320/15,000/25,000 games. Resolve pagination/revision behavior as that view requires. Search/filtering, artwork, import jobs and real integrations remain separately scoped later work. No M0.3 implementation was performed.
