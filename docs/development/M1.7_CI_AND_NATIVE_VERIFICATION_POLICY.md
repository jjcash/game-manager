# M1.7 CI and native verification policy

## Acceptance gate

M1.7 cannot receive final milestone acceptance or release approval unless both the required hosted **Windows quality checks** and the local native security verification below pass against the intended source tree. GitHub Actions checks frontend quality, formatting, all-target Clippy, an optimized Windows build, ordinary Rust tests and documentation tests; it compiles `standalone_launch` but does not execute it. Native Windows security execution is not continuously tested by GitHub Actions. The existing required check remains **Windows quality checks**; a local pass is not a GitHub status check and branch protection does not enforce this manual gate. No self-hosted runner is available. This limitation is an accepted infrastructure tradeoff, not evidence of weaker launcher security or a change to its threat model.

If local verification is unavailable or fails, milestone and release approval remain blocked until it passes or the user explicitly approves a documented policy exception. Preserve failures. For future launch-related milestones, repeat local native verification when execution behavior or security boundaries change. Re-run it after launch-related source, test infrastructure or relevant dependency changes. A different tree cannot reuse local evidence. If a merge changes the commit SHA but not the tree, record and compare both tree IDs; if contents change, re-run affected verification. Hosted CI must also pass for the intended revision under the existing ruleset.

The milestone owner or release maintainer performs the verification, records a concise dated evidence entry in `docs/development/M1.7_STANDALONE_LAUNCH_FEASIBILITY.md` (or the relevant future milestone/release report), and checks it during acceptance. Include operator, start/end timestamps and timezone, commit and tree IDs, clean status, OS/build, Rust/Cargo/MSVC versions, prerequisite and elevation checks, command, complete outer summary, handle-recovery result, cleanup findings, hosted run URL/revision/result, and any failures or exceptions. Do not commit generated executables, private paths, personal data or bulky raw logs. Keep failure evidence in a suitable private location and record a sanitized summary and location in the report. Evidence entries made after testing change the tree. For the final tree, retain the signed or attributable verification record outside that tree and reference its location from the release or milestone record; do not claim that an earlier tree is the final one. Record the final commit and tree in that external record, avoiding a circular in-tree identifier.

## Procedure

From the repository root in an ordinary interactive Windows desktop PowerShell session, using the supported Windows MSVC Rust toolchain and installed project prerequisites:

1. Run `git status --short --branch`, `git rev-parse HEAD`, and `git rev-parse 'HEAD^{tree}'`. Confirm the intended revision and a clean working tree, including untracked files; resolve or explain any modifications before testing. Final acceptance requires evidence for the exact intended tree, not an unexplained modified checkout. Record both IDs and status. Do not test personal games.
2. Confirm the process is unelevated: inspect `whoami /groups` and the current Windows principal; administrator role must not be enabled, the integrity label should be Medium, and the test's own token elevation check must pass. Do not run an elevated shell. Record `Get-CimInstance Win32_OperatingSystem | Select-Object Caption,Version,BuildNumber,OSArchitecture`, `rustc -Vv`, `cargo -V`, and the MSVC compiler/toolchain version (for example `cl` in a developer environment). Use the pinned Rust toolchain configured for the project.
3. Ensure `rustc` and the MSVC linker/toolchain work, locked dependencies and built frontend assets required by the Tauri test build are present, and the ordinary user can create, execute and remove disposable files in its temporary directory. The fixture compiler invokes `rustc` and Windows resource tools as described by the test source; confirm their availability through the fixture's actual compilation. Use only the test-owned temporary fixtures; do not use real installations.
4. Record start time, then run exactly:

   ```powershell
   cargo test --manifest-path apps/desktop/src-tauri/Cargo.toml --all-features --locked --test standalone_launch -- --test-threads=1 --nocapture
   ```

   Record end time and exit code. Require the outer summary `12 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out`. Internal exact-test child summaries may report filtering; they do not replace the outer summary. Confirm the exact handle-recovery assertion passed and record the printed before/after counts over 20 launches; do not relax the assertion.

5. Inspect test-owned processes and temporary fixture locations for surviving children or unintended residue. Record the method and result; do not kill or delete anything of uncertain ownership. Record failures as failures. Recheck source status and identity to confirm no source changed during the run.
6. Record the evidence as above. Review the hosted run and source-tree comparison before milestone or release approval. Earlier local results on a different tree are historical evidence only.

`pnpm test:rust` remains the full local suite. The old restricted-token helpers are historical investigation artifacts, not a supported fallback. ADR-011 remains proposed until separately approved; production launching remains disconnected, and M1.8 remains unauthorized.
