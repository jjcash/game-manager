# M1.3C — Isolated Windows metadata reader feasibility

Date: 2026-10-28. **B. Defer Steam local discovery.** An actual isolated Rust native candidate was exercised, but the mandatory security gate did not pass. Required symbolic-link fixtures are unavailable in this unelevated environment; successful root replacement after approval was not demonstrated. No safe reader or supported production configuration is certified. M1.3 remains incomplete.

Feature expansion stopped at this gate. Parser integration, representative scan benchmarks and production integration were not undertaken. The failed test remains failing; it was not converted into a pass or silently skipped.

The initial working tree was clean on `feat/m1.3C-B`. Both HEAD and local `main` were `ea616e963f7a73d29fa194b10fcc69028e71b71e`, the merge of PR #17 containing accepted ADR-008. Created `feat/m1.3c-native-reader` from that commit. No fetch, reset, history rewrite, commit, push or merge was performed. No untracked investigation evidence existed at the initial status check, and existing ignored evidence was preserved.

Reviewed AGENTS, README, PROJECT_STATUS, ROADMAP, relevant PRD integration/evidence requirements, TAS trust boundaries, DSS identity/override rules, MDRS external ownership/read-only detection, ADR-007/008, M1.2/M1.3/M1.3A/M1.3B reports, parser fixtures/contracts and the Windows reparse probe. The current explicit authorization supersedes historical planning-only statements in AGENTS. The production schema still consists of migrations 0001 and 0002; application schema remains v2. No Steam command exists in production registration or capabilities. ADR-007 and exceptions E1–E5 are unchanged.

## 2. Accepted model B boundary

[ADR-008](../decisions/ADR-008-steam-local-discovery-threat-model-b.md) authorizes eligible metadata names beneath an approved native root identity, not exclusive historical provenance. Deliberate sensitive-object substitution or hard-link manipulation by another same-user process is outside the confidentiality guarantee. Malicious metadata, accidental path widening, static reparses, unsupported objects, observed replacements and ordinary updates remain in scope. Observed multiple links must be rejected before content reads. Nothing here establishes model A, account ownership, freshness, payload integrity or launchability.

## 3. Observed Windows/filesystem environment

Rust 1.99.1, Cargo 1.99.1, `x86_64-pc-windows-msvc`; Windows 11 Pro 10.0.26200. The process has medium integrity, with Administrators deny-only; the candidate also checks `TokenElevation` and refuses elevation. Disposable reader fixtures were created on C:, observed as healthy fixed NTFS. E: was reported as fixed NTFS by the environment query but was not used for reader fixtures.

This is an observed experiment environment, **not a passed supported-Windows matrix**. No FAT/ReFS, removable media, actual network share, offline device, alternate Windows build or actual Steam installation was tested. No elevation, Developer Mode change or privilege enablement was attempted.

## 4. Native mechanism and exact flags

The test-support module uses SDK bindings from `windows-sys` and narrowly located unsafe calls. No hcsshim source was copied; [Microsoft's safe-file implementation](https://github.com/microsoft/hcsshim/blob/838c2196b8c53438d6d5b8d9e6ae1dd756800395/internal/safefile/safeopen.go) was reviewed only as the earlier design reference, not a safety proof.

| Operation                     | Candidate API/policy                                                                                                                                                         |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Resolve selection anchor      | `QueryDosDeviceW` for exactly the requested drive, fixed-size 512-WCHAR output; require current target `\Device\HarddiskVolume` plus ASCII decimal digits                    |
| Open anchor/components/leaves | User-mode `NtCreateFile`, `OBJECT_ATTRIBUTES.RootDirectory` for relative components, `OBJ_DONT_REPARSE` = `0x1000`; no case-insensitive flag                                 |
| Disposition/options           | `FILE_OPEN` = 1; `FILE_OPEN_REPARSE_POINT` = `0x200000` and `FILE_SYNCHRONOUS_IO_NONALERT` = `0x20`; null EAs/security descriptor/allocation size; non-inheritable handles   |
| Rights                        | `FILE_READ_ATTRIBUTES` = `0x80` and `SYNCHRONIZE` = `0x100000`; add `FILE_LIST_DIRECTORY` / `FILE_READ_DATA` = 1 only for metadata enumeration / content-capable leaf opens  |
| Sharing                       | `FILE_SHARE_READ                                                                                                                                                             | FILE_SHARE_WRITE | FILE_SHARE_DELETE` = 7; no exclusive reader locks |
| Type/volume                   | `GetFileType`, `NtQueryVolumeInformationFile(FileFsDeviceInformation)`, `GetVolumeInformationByHandleW`, `GetDriveTypeW`                                                     |
| Identity/attributes           | `GetFileInformationByHandleEx`: `FileIdInfo`, `FileBasicInfo`, `FileStandardInfo`, `FileNameInfo`; `GetFileInformationByHandle` for enumeration-compatible 64-bit file index |
| Enumeration                   | `GetFileInformationByHandleEx(FileIdBothDirectoryInfo)` against retained `steamapps`; aligned 64 KiB batches, explicit flexible-entry bounds checks                          |
| Content                       | Synchronous `ReadFile`, at most 16 KiB per call, on the validated retained leaf handle                                                                                       |
| Cancellation                  | Exact dedicated thread handle passed to `CancelSynchronousIo`; token checks between operations and actual thread join before completion                                      |

The [NtCreateFile documentation](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntcreatefile) describes directory-relative opens and existing-file/share options. Its directory-option compatibility list omits `FILE_OPEN_REPARSE_POINT`: the candidate therefore **does not request `FILE_DIRECTORY_FILE`** and validates the resulting directory type before using it. It similarly validates leaf type before reading. Informational success statuses are rejected and owned successful handles are released.

[OBJECT_ATTRIBUTES](https://learn.microsoft.com/en-us/windows/win32/api/ntdef/ns-ntdef-_object_attributes) documents no-reparse behavior; the user-mode NtCreateFile page's narrower attribute list remains a documentation discrepancy. Actual ordinary/junction cases accepted or refused this combination on the observed build. That evidence does not resolve all reparse tags, symlinks or Windows versions. No unchecked fallback was added.

[CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) was reviewed for sharing, directory and reparse semantics; ordinary path-based opens are used by synthetic fixture construction, not by candidate traversal. No canonicalize/reopen or lexical-prefix confinement is used.

## 5. Root acquisition and approval

An uppercase drive-absolute ASCII request, at most 240 bytes and 32 components, is the deliberately narrow initial input. Empty, dot/dot-dot, separators inside components, ADS, trailing dots/spaces, non-ASCII and device/UNC/drive-relative forms are refused. The DOS device mapping is a selection request, not approval. Its validated direct kernel volume name is opened independently; the code rejects mapped/SUBST-shaped targets rather than following them. Actual SUBST/mapped-device fixtures were not exercised.

The acquired anchor must report disk type, NTFS and fixed drive category; removable/remote/virtual-volume characteristics are rejected. Every path component is opened relative to the preceding owned handle, checked for regular directory attributes, exact returned long component name and same volume identity. The chain remains owned by `Acquired`. A global active-session guard bounds acquisition to one session.

The test-only explicit `approve` consumes `Acquired` plus its reviewed identity and returns an otherwise unconstructible `Approved`. Wrong identities and cancelled tokens fail; dropping/rejecting releases the capability. There are no serialized grants or frontend booleans. This establishes a harness ownership pattern, not a production picker or unforgeable user-interface consent protocol.

## 6. Handle-relative access and identity

Approval revalidates the retained component chain, then opens literal `steamapps` relative to the acquired root. Only native enumeration supplies candidate leaves. Each leaf open is relative to the retained `steamapps` handle. Validation uses native volume/file IDs. Returned-name checks are intended to reject aliases, but native short-name and case-collision fixtures have not established that guarantee.

The scan consumes approval on success and failure. Before enumeration batches/leaf access and after observations, the chain and `steamapps` are re-observed through retained parents. Identity mismatch refuses the operation rather than selecting a replacement. Before-approval root replacement was exercised successfully inside the combined test; its after-approval portion failed to construct the replacement. No after-approval replacement guarantee is inferred from that failure.

## 7. Reparse handling

Actual junction fixtures at the selected root, an ancestor, `steamapps` and an eligible leaf were refused without content reads. A junction replacing `steamapps` during enumeration also refused the scan. Directory and file attribute validation rejects the reparse bit and unrecognized attribute combinations, including offline/recall, sparse and encrypted metadata. No recursive traversal is implemented.

The separate symbolic-link fixture creation failed with **Win32 1314**, before its security assertions could run. It remains explicitly ignored in ordinary test runs and is not counted as a pass. Running it explicitly with `--ignored` returns failure. Other reparse tags were not exercised. ADR-008 retains [M1.3B's requirement](M1.3B_STEAM_DISCOVERY_DECISION.md#required-native-verification-and-maintenance-cost) for a capable symlink test environment; this missing gate contributes directly to deferral.

## 8. Hard links and accepted limitations

Before content-capable opening, an attribute-only handle is validated using [FILE_STANDARD_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_standard_info): regular type, not delete-pending, exactly one observed link, nonnegative size at most 65,536. The content-capable handle is separately opened, revalidated and retained. Link count is checked again before each actual `ReadFile`.

Unlocked and exclusively held external sentinels, hard-linked to `appmanifest_10.acf`, were both rejected with zero content-capable attempts and zero content reads in the scanner path. A link added after a content-capable open but before `ReadFile` also produced zero reads. Removing the extra link allowed the next independent scan. These are observed-count checks, not provenance proofs or defenses against deliberate adversarial link-count races.

## 9. Allowlist and parser integration

The native wrapper requires exact lowercase ASCII `appmanifest_([1-9][0-9]{0,9})\.acf` with nonzero u32 range. Unsupported entries never become leaf-open requests. Enumeration rejects case variants and denies repeated AppIDs rather than choosing a silent winner; no short names are used for opens. Synthetic ADS, Unicode lookalikes, overflow/zero/leading-zero/signed IDs, traversal, namespaces and extra suffixes were exercised as described below.

**No parser is connected to the candidate.** Security tests compare synthetic bytes, not Steam classification. Filename/body agreement, hostile manifest fields, malformed/truncated KeyValues and duplicate/conflicting body AppIDs therefore remain **unverified in this candidate**, despite unchanged M1.2 contracts passing separately. The existing parser's broader case normalization is not used to implement the stricter native allowlist. No ownership inference, binary parser, index expansion or metadata-driven I/O was added.

## 11. Replacement and ordinary-update evidence

Actual synthetic leaf replacement between enumeration/open, between the first/second observations and after the second observation yields incomplete records. Growth beyond 64 KiB at the before-read boundary is rejected. A same-object ordinary in-place rewrite between observations recovers through exactly one retry. Equality includes volume/file identity, 64-bit index, size, last-write/change timestamps, link count and bytes. Repeated content observations charge the same byte budget. Equal observations do not establish an atomic Steam transaction or defeat adversarial ABA histories.

The combined root-approval test confirms cancellation, wrong-identity rejection, one active capability and before-approval root replacement. Its after-approval rename fails with **Win32 5, access denied**, while a descendant `steamapps` handle is retained. Both cross-parent and same-parent fixture attempts were retained. The second attempt did not resolve the gap. This is **not a demonstrated unauthorized read**, nor proof that all root replacements are impossible. The required successful after-approval replacement/detection case remains unverified. The final test logs identify the failing phase explicitly.

## 12. Cancellation and resource cleanup

An actual level-1 NTFS oplock was requested asynchronously by the synthetic fixture using `DeviceIoControl(FSCTL_REQUEST_OPLOCK_LEVEL_1)` and a retained OVERLAPPED/event. The candidate worker was confirmed outstanding after the oplock-break notification. `CancelSynchronousIo` completed its blocked NtCreateFile with `STATUS_CANCELLED` before the fixture released the oplock; observed completion was approximately 5–6 ms in the recorded gates, one accepted cancellation request. The actual thread was joined. Fixture event/buffer/owner storage remained live through I/O completion.

The candidate has a single dedicated worker, owned handles, one active acquisition, cancellation checks between batches/opens/reads and a joining worker destructor. Cancellation is tested at six scan stages and through 20 repeated worker cancellations; explicit finish and destructor cleanup return worker/handle counters to zero. Peak outstanding candidate workers is asserted as one.

[Microsoft's cancellation guidance](https://learn.microsoft.com/en-us/windows/win32/fileio/canceling-pending-i-o-operations) and [CancelSynchronousIo](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-cancelsynchronousio) require waiting for actual completion; a cancellation request does not itself complete I/O. The worker checks a nominal 30-second deadline and repeatedly requests cancellation while joining. It never detaches, but there is no proven hard completion bound if a driver does not complete cancellation. Blocked directory enumeration, attribute/volume queries and reads were **not** independently cancellation-tested. Thus the complete required blocking-operation/cancellation contract is not established. No general driver-failure guarantee is claimed.

## 13. Performance and resource observations

No representative or larger scan benchmark was run because the security gate failed. No new M0 target or exception is introduced. Native security tests completed in roughly three seconds per full target, including fixture processes; this is test duration, **not scan latency**.

Small-case evidence: 36 manifest bytes for two stable observations; retained-handle high water 10 in the acquisition/oplock gates; zero handles after joined completion; one candidate worker maximum in repeated cancellation tests. Oversized and multiple-link leaves are rejected before reading. A directory of 1,000 nonmatching names hits a reduced 100-entry test budget, rather than bypassing enumeration accounting. Empty/missing/directory leaves and reduced byte/record/time budgets are exercised.

Configured limits are 25,000 eligible records, 50,000 examined entries (with one terminal over-limit observation), 128 MiB aggregate read input, 64 KiB per manifest, two observations and at most one retry (up to four observations), 16 KiB chunks and 30 seconds nominal work. The code's buffer instrumentation accounts for a 64 KiB enumeration allocation and a conservative 147,458-byte content-buffer capacity calculation; these are **code accounting, not measured process memory**. Temporary name-query storage, stack, maps, names, allocator overhead and result-consumer memory are additional. RSS/peak working set and OS handle counts were not sampled. No release-scale resource guarantee is certified.

## 16. Remaining risks

This candidate is **not safe to wire into production**. Required symlink and successful post-approval root replacement coverage is absent. Complete native cancellation/deadline behavior, all object/alias/path types, full resource accounting and parser integration remain unverified. User-mode flag documentation is inconsistent and executable results cover one Windows build. The API is test support, not a hardened public session interface. In particular, attribute queries and revalidation failures need a complete invalidation/error audit before any reuse outside the consuming scan path. There is no persistent grant, native picker, preview paging, account access or imported record path.

## 17. Maintenance-cost assessment

The candidate already requires roughly 900 nonblank Rust lines plus roughly 700 lines of native fixtures without parser integration, production consent or IPC. The unsafe operations, native layouts, flexible enumeration buffers, per-operation cancellation, exact-name policy and replacement coverage require continuing review. Binding changes and supported Windows/filesystem changes would require rerunning native security fixtures, including privileges unavailable here. The current partial evidence does not justify that continuing cost for installed-app metadata convenience. This is not proof that a smaller maintainable solution is impossible.

## 18. Final recommendation and stop

**B. Defer Steam local discovery.** The candidate fails the required verification gate; native compatibility, replacement and cancellation coverage are insufficient. Preserve the experiment and raw failures for review, retain manual offline library use, and choose a separately authorized non-Steam task from the existing roadmap. Do not integrate this reader, resume M1.3, add imports/accounts/other storefronts or start another investigation automatically. M1.3 remains incomplete. No commit, push, merge or subsequent milestone is performed.
