Verification: 2026-10-27–28 (America/Sao_Paulo); continued 2026-10-28.

**Recommendation: conditional M0 closure with documented exceptions, pending explicit user approval. M0 is not closed by this report.** Stop the synthetic SQL/startup optimization program. ## Writer-acquisition investigation

M0.7E's first reverse-pass temporary-candidate 25k/write process failed after four **unfiltered** probes, before filtered queries/DOM windows: `POOL_EXHAUSTED`, processed 64, committed 0. Its separate closed audit found integrity ok, no items/commits/interrupted runs. The unchanged-settings repeat and adjacent current baseline passed. The candidate is not production. These facts neither prove pool exhaustion nor blame its presence predicate.

M0.7E's completed native groups retain acquisition p95 up to **37.835 ms count / 4.780 ms page**, versus maximum diagnostic acquisition p95 **0.242 ms** in its isolated relationship matrix. The failed attempt's foreground acquisitions peak around **2.4 ms**. These workload-specific successful samples do not provide the failed writer's occupancy or wait cause; pressure is not silently treated as zero.

Source inspection establishes three different waits: writer serialization mutex, **250-ms Tokio timeout around `pool.acquire()`**, and SQLx pool **10-s acquisition timeout**. The configured SQLite **25-ms busy timeout** and **four transaction attempts** concern SQLite locking, distinct from waiting for a pool handle. Connection opening/PRAGMAs can occur inside acquisition; these boundaries must not be conflated. A Tokio deadline measures elapsed opportunity to complete, including worker/connection handshake and task delivery, rather than active SQL or known occupancy. Four connections are a maximum, not proof of four active connections. SQLx acquisition can discard an in-progress connection on cancellation; pool `size - idle` can include opening/returning/testing work, not just queries. Locked dependency source documents these semantics.

The locked SQLx `pool/inner.rs` path first awaits a permit, then checks an idle connection or opens one; health checks/worker delivery and asynchronously returning connections can therefore contribute even without four long-running SQL statements. Its own elapsed timeout maps to `PoolTimedOut`. The synthetic job maps any inner acquisition error to `POOL_CLOSED`, so neither existing synthetic string should be treated as a precise SQLx diagnosis. No inner ten-second timeout was observed here. Tokio polling/timer delivery is not a hard real-time wall-clock guarantee. Shared CPU processing uses `spawn_blocking`, and the CPU permit is released before batch acquisition; foreground SQL does not wait for that CPU budget. Code inspection finds no circular lock dependency explaining the historical event. These are possible boundaries/mechanisms, not attribution of that event to ping, opening, occupancy or starvation.

The two CPU/artwork resource permits, four SQLx connections and Tokio executor workers are different limits. Only the isolated test runtime explicitly uses two Tokio executor workers; production scheduler/runtime policy is unchanged.

Added only test code in `jobs/acquisition_tests.rs`, selected by `cfg(test)` under the existing benchmark-only jobs module. No pool, timeout, scheduler, SQL, native DTO, cache or production policy changes.

- Deterministic occupancy control: hold both shared worker permits until the running ledger checkpoint is durable; retain/read from all four pool connections; release processing; wait for the 64-record processed batch. Two forced guard failures and two cancellation controls per invocation. Observe bounded executor-heartbeat samples (at most 500) and occupancy; release all holds; require terminal status, zero items/commits, integrity/FKs and successful subsequent 128-record job. Close, reopen/audit the fixture and verify no interrupted run. A slow final checkpoint while connections remain deliberately held is expected; it resolves on release, not a demonstrated deadlock.
- Natural concurrency control: two Tokio runtime workers, four concurrent actual count-query tasks (each capped at 4,096), sixteen writer jobs, 2,048 committed records, 32 successful batch acquisitions. Exact ledgers, integrity/FKs, released workers/scheduler and pool close are asserted. This smaller 500-game fixture isolates resource behavior; native 25k controls provide scale, not an interchangeable timing cohort.
- Pilot: **13,239 reads**, writer acquisition max **2.029 ms**, pool size/idle **4/4** at end. Forced occupancy elapsed observations **259.508 / 280.439 ms**, heartbeat maxima **15.933 / 16.239 ms**; these start after observing processed=64, not exact acquisition-entry measurements. Timer granularity/task delivery explain why a nominal 2-ms heartbeat is not a 2-ms scheduling guarantee. They do not explain the historical incident.
- Existing pool wait rings contain **successful acquisitions only**. Failed waits are absent: a low foreground/success p95 cannot exclude a writer deadline failure. The injected timeout control correctly reports Failed/`POOL_EXHAUSTED`, never Completed; cancellation with release before deadline reports Cancelled without commits. No timeout is extended and no assertion weakened.

Eight **final serial invocations** pass both tests: **131,072 actual reads, 16,384 committed natural-control records, 256 batch acquisitions**, maximum successful wait **6.796 ms**. They also pass **16 forced guard failures, 16 cancellation controls and 32 subsequent 128-record recovery jobs**. Forced-failure observations span **252.428–280.324 ms** after observing processed=64; bounded heartbeat maximum is **17.701 ms**. Instantaneous end samples sometimes show three idle connections while drop-return work is pending; the strengthened control reacquires **all four** before a timeout-bounded close, establishing recovery of every slot in these runs. Closed audits preserve exactly **512 recovery items/commits, zero interrupted runs and integrity ok** per forced-control fixture. The pilot and eight earlier passing invocations remain separately retained; the statistics here are only the final eight, not pooled across different test revisions.

Four fresh **25k/write native replays** use the historical temporary candidate, current artifact, current artifact, historical candidate order, with the original twenty-iteration deep/IPC settings and new isolated roots. The historical executable is SHA-256 `34027DF8B975EFFB3A81F792BE10BD4CE13FF1E2F05C642B38A5C63680520DE2`; it is used only to reproduce the incident, never selected for production. All **480 paired metadata/page probes and 480 canonical loaded-window observations** pass, with a job active in **100% of sampled native probes**. Each process completes a 100,000-record job and preserves a separately cancelled valid prefix; all four closed audits pass. There is **no unexpected acquisition failure**. Maximum successful foreground acquisition is **0.3873 ms count / 1.2824 ms page**. Retained writer rolling-window p95 ranges **0.0520–0.2183 ms**, maximum **1.5759 ms**, n=128/process (two last-64 rings, not every batch). These successful-only samples cannot retrospectively explain the original failed wait. Capture buffers and event recording remain bounded by the established driver.

**Historical cause remains unestablished.** Forced occupancy reproduces the failure class, not evidence that M0.7E had that occupancy. No deadlock, persistent starvation, connection leak or invalid prefix has been demonstrated under the bounded controls; this is finite negative evidence, not a proof of absence. A failed synthetic job is recoverable by a fresh explicit job; no automatic replay or claim that the failed job resumes is made.

Disposition: **defer pending real-world evidence**. Preserve the original failed run and repeat provenance. On another unexpected acquisition guard failure, preserve the closed fixture, exact run/request/build/worker/load history and successful/failed timing distinction; collect a bounded benchmark-only occupancy/acquisition-entry/outcome plus executor-heartbeat ring before further repeats. Never log credentials/full library content, auto-delete failures, silently retry as success or increase capacity/deadlines to mask recurrence. Reopen as a correctness task if the pool fails to recover after load releases, cancellation/shutdown cannot reach a safe boundary, ledgers disagree, or the failure repeatedly occurs with representative bounded release-scale work. Production import jobs require a separately designed error/retry/durability contract; this synthetic label is not its approved API.

## Exit recommendation and reopening conditions

Approve or reject the proposed conditional gate policy explicitly. Until approval, **M0 stays open** and ADR-007 stays Proposed. If approved, the next separately authorized task should be a small **M1 core library foundation** slice: persisted manual library identity/entry/installation work with bounded queries, provenance/user override tests and restart behavior. Initial Steam import remains in M1's roadmap but requires its own scoped authorization; no provider, importer, mod work or later milestone begins here.

Reopen an exception for a reproducible representative 15k user workflow with consequential waiting/freezing and an evidenced cost-effective remedy; incorrect identities/search/filter/order/stale results; unbounded pages/caches/decoders; unreclaimed sustained memory/paging/resource exhaustion; writer deadline recurrence with failed recovery or invalid prefixes; or real supported relationship/artwork distributions materially unlike the fixture. Record workload, timing endpoint, artifact and fresh-process controls before proposing changes. Do not reopen solely because an already documented synthetic budget is still missed.

Unavailable hardware/presentation/cold-start checks remain an explicit release-validation backlog, with procedures above. Validate cached details, real imports, backup and deployment safety in their own implementation milestones. Obtain a documented successful Windows GitHub CI run before treating local checks as CI evidence. Conditional M0 closure cannot close those future release obligations.
