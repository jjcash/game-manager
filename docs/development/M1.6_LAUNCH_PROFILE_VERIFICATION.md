## 2. Persistent contract and identity

`Game → LibraryEntry → GameInstallation → LaunchProfile` remains authoritative. A profile stores one required installation ID; game and membership are derived through existing relationships. No redundant editable game/membership binding exists in storage. Requests carry the selected game ID and must match that chain. Profile IDs are independently generated 128-bit random values encoded as 32 lowercase hexadecimal characters, using the established SQLite randomblob convention. Duplicate/copy always allocates another ID; names, paths and targets never establish identity.

User provenance is explicit and currently the only permitted stored provenance. Provider profiles, imports, provider override persistence and adapter frameworks are unsupported. User configurations can reference read-only provider installation metadata without transferring its ownership or permitting edits/deletion. Future provider support needs a separate schema/override contract.

Bindings, profile IDs and provenance are immutable. SQL triggers also refuse installation/membership reassociation while profiles exist, including malformed direct SQL. Installation location, platform, version and presence edits retain profile IDs, revisions and literal target references. Metadata and group changes do not rewrite profiles or defaults. No current stored configuration certifies future launch readiness.

## 3. Migration and schema v4

`0004_launch_profiles.sql` is additive; migrations 0001–0003 remain byte-for-byte unchanged. `launch_profiles` holds configuration, revision and creation/update millisecond timestamps, with a restrictive installation foreign key and `(installation_id,id)` index. Tagged references use separate constrained kind/value columns; optional working-directory kind/value must both be NULL or both present. Arguments use a JSON array, preserving order and empty strings without a child-row ordering protocol. SQLite checks supported kinds, user provenance, basic lengths, JSON array shape/count, nonnegative revisions and valid ID syntax; Rust checks literal argument members, aggregate bounds and lexical references. No generic execution/provider framework is introduced.

`game_launch_defaults` holds zero/one explicitly selected profile per game. Restrictive foreign keys plus insert/update same-game triggers prevent invalid defaults. It contains no automatic selection rule. There is no production launch command, launch engine, executable discovery or game-directory access.

Populated-v3 migration and blocked-v4 rollback tests retain IDs, revisions, relationships and group assignments, verify no partially created profile table/history remains, then reopen successfully after removing the disposable blocker. Frozen generator-v1 migrations remain isolated at v1.

## 4. Target-reference representation

DTOs tag references as `{kind: "installationRelative" | "absolutePath", value: string}`. Stored values are preserved exactly, without trimming, rebasing, normalization or environment expansion. Each reference has 1–2048 Unicode scalar values, with no control characters. Only backslash separators are supported. Components cannot be empty, `.` or `..`, end with ASCII dot/space, contain `< > : " / | ? *`, or use reserved device stems CON/PRN/AUX/NUL/CONIN$/CONOUT$/COM1–9/LPT1–9, including superscript ¹/²/³ variants.

Relative values have no root, drive prefix, UNC or device namespace. All dot traversal is refused, including internal `a\..\b`, a deliberate conservative subset rather than normalization. Absolute values require an ASCII drive letter followed by `:\`; UNC, drive-relative, rooted-without-drive and verbatim/device namespaces are unsupported. A drive root such as `C:\` is lexically permitted, including for an explicit working directory. Targets are not required to end in `.exe` or to exist.

**Lexical configuration validation is not launch-safety validation.** No target or working directory is opened, resolved, searched, inspected or executed. A future launching milestone must separately validate installation context, resolution, Windows process argument encoding and authorization. This contract does not certify filesystem confinement through junctions or symlinks.

## 5. Literal arguments and working directory

Arguments are an ordered array of at most 128 literal strings. Each permits at most 4096 UTF-16 code units; the aggregate permits at most 16384 units. NUL is rejected. Spaces, quotation characters, Unicode, control characters other than NUL and intentional empty arguments remain data. JSON storage text is bounded to 131072 characters, including escaping overhead. No shell string, interpolation, command interpretation or environment expansion is performed.

The optional working-directory reference uses the same lexical grammar. SQL NULL / DTO null means omitted and remains distinct from any explicit value; persistence invents no working directory. UI arguments are edited as a JSON string array with an example and bounds, avoiding whitespace splitting that loses empty arguments or quoting boundaries.

## 6. Revisions and concurrency

`manual_mutate` gains one narrowly typed nested `launchProfile` action with create/save/duplicate/remove/setDefault operations. Existing capability and maintenance admission checks remain in effect; no new permission or unrestricted IPC endpoint is needed. `manual_get` includes profiles and the explicit default only for the selected game's bounded editor.

Profile create starts revision 0; every configuration save requires the exact profile revision and increments it once under `BEGIN IMMEDIATE`. Duplicate checks its source revision, copies its literal configuration and installation binding, then creates an independent ID/revision 0. Removal also checks the exact profile revision. These operations do not require an otherwise unrelated game revision and do not advance it, except removal of a current default, which atomically clears that selection and advances the game revision. Requests still verify the profile's current game association under the writer lock.

Default selection/replacement/clearing requires the exact game revision. Selection additionally requires the chosen profile's current revision and same-game association. Success advances the game revision in the same transaction. Removal of a default selects no replacement. Ordinary installation, grouping and manual changes retain their existing game-revision contract. Conflicts surface without automatic retries; failed operations roll back without revision advancement or partial writes. Future launch preparation must check both profile and current game/installation context.

## 7. Deletion and relationships

The UI explicitly confirms profile removal. Default removal clears its selection atomically. Installation, membership and manual canonical deletion refuse while affected profiles remain, with instructions to remove those profiles explicitly. SQL restrictive foreign keys supply another guard. Existing last-membership, provider/legacy and manual-only canonical restrictions remain. There is no broad profile cleanup cascade, implicit retargeting or default fallback. Groups own no profiles and cannot select defaults. All deletion is application metadata only.

## 15. Limitations

Standalone user configuration only; no executing, target resolution/existence checks, launcher adapters, provider profiles/import, discovery, process/session tracking, mod functionality or defaults inferred from names/paths/order. Reference grammar deliberately supports a conservative local-drive/backslash Windows subset. No reassociation or bulk profile cleanup. The editor caps total profiles at 100 per game. JSON argument editing preserves boundaries but is a compact initial configuration workflow. Backup format/size/local hard-link storage and recovery-retention limitations from ADR-009 remain.
