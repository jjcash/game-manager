# M1.3A — Windows metadata reader security investigation

Date: 2026-10-28. **Stop: a safe, maintainable reader has not been established.** No application-facing capability, reader implementation or Steam discovery workflow is added. The native probe below is an API experiment, not the production-candidate reader required for an M1.3A success. M1.3 remains incomplete.

## Threat model

Untrusted Steam metadata and a local actor able to rename or replace filesystem entries can supply hostile paths or change objects concurrently. The safety property is that no content outside the native directory identity explicitly approved by the user is opened for reading. A selected path is a request to establish a root, not an authenticated identity. A Steam-reported library path is only a candidate and confers no grant. A grant must bind a successfully opened root identity to a limited read capability, and revalidation must refuse replacement rather than silently rebind. Manifest names must come from controlled enumeration and an exact filename policy. Manifest fields, including installation paths, never become filesystem operations.

An attacker controlling the operating system, kernel, filesystem implementation or privileged filters is outside this threat model. Network, mapped, device and reparse-backed paths and filesystems without a demonstrated safety contract must fail closed. No particular Windows version or filesystem is yet supported by a production reader. A local fixed NTFS volume is the initial experiment target; no elevation or access to real Steam files is needed.

## API investigation

- [NtCreateFile](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntcreatefile) documents relative names against `RootDirectory`, existing-file opens, access masks and share flags. Its user-mode attributes description lists zero or `OBJ_CASE_INSENSITIVE`. The general [OBJECT_ATTRIBUTES](https://learn.microsoft.com/en-us/windows/win32/api/ntdef/ns-ntdef-_object_attributes) definition describes `OBJ_DONT_REPARSE` as a no-reparse policy. That discrepancy and the behavior of a retained parent concurrently converted or replaced are not resolved here. Empirical results are not a universal API guarantee.
- `FILE_OPEN_REPARSE_POINT` opens the reparse object rather than following it; it is not by itself a guarantee about every ancestor. The NtCreateFile directory-option compatibility list does not explicitly include this flag. [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) documents `OPEN_EXISTING`, directory backup semantics, reparse behavior and read/write/delete sharing. Read/write/delete sharing allows compatible concurrent access and replacement; it does not produce a stable snapshot.
- [File identity](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfileinformationbyhandle) and [volume information from a handle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getvolumeinformationbyhandlew) can distinguish observed objects and filesystems. [FILE_STANDARD_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_standard_info) supplies link count, type and size. [GetDriveTypeW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getdrivetypew) reports drive categories; a drive letter alone is not proof of confinement or local identity. [Reparse point operations](https://learn.microsoft.com/en-us/windows/win32/fileio/reparse-points-and-file-operations) describe inspection and opening reparse objects. These checks do not independently close a check/use race.
- Reviewed Microsoft's [hcsshim safeopen.go](https://github.com/microsoft/hcsshim/blob/838c2196b8c53438d6d5b8d9e6ae1dd756800395/internal/safefile/safeopen.go) as an engineering reference. It uses a root handle, relative NtCreateFile and `OBJ_DONT_REPARSE`; its root acquisition and broader operational contract do not establish this project's approval and hard-link policy. Its [MIT license](https://github.com/microsoft/hcsshim/blob/838c2196b8c53438d6d5b8d9e6ae1dd756800395/LICENSE) requires notice retention if copied. No upstream code or dependency was copied or added.

## Native experiments and gap

The tracked test-only `apps/desktop/src-tauri/tests/windows_reparse_probe.ps1` uses a small C# FFI probe, not the Rust application. Run it with `powershell -NoProfile -ExecutionPolicy Bypass -File apps/desktop/src-tauri/tests/windows_reparse_probe.ps1`. It creates a uniquely named disposable temporary directory and removes it afterwards. This host reported Windows build 26200.9711 and the temp volume as local fixed NTFS. These observations do not establish a supported version matrix.

An ordinary relative file open returned success. A relative name through an intermediate junction returned `STATUS_REPARSE_POINT_ENCOUNTERED`; a sentinel outside the root was simultaneously held without sharing. A hard link inside the root to that sentinel instead returned `STATUS_SHARING_VIOLATION`: the no-reparse-only operation attempted to open the sentinel object and the test's exclusive handle prevented that read-capable open. No sentinel content was read by the probe. This demonstrates why reparse refusal alone cannot be the reader's hard-link policy; it does not prove a later link-count check is race-safe. Creation of the leaf symbolic-link fixture was unavailable under this account; that case was not tested. The first probe run produced the correct statuses but failed its assertion due to PowerShell's signed interpretation of a hexadecimal constant; the unsigned comparison was fixed and the final run passed.

The experiment deliberately does not validate selected-root ancestors or approval identity, perform bounded or double reads, enumerate `steamapps`, detect replacement, read a synthetic manifest, test cancellation/cleanup under load, or test concurrent rename, in-place updates, malformed paths, unsupported volumes or special files. Its root is a disposable fixture opened with ordinary CreateFileW; it must not be used for untrusted production paths. The sentinel lock prevents a successful read-capable open, but does not instrument all possible metadata-only opens. None of the required production-reader security tests passed, because no such reader was implemented.

## Decision, residual risk and alternative

A possible design would acquire each component from a trusted volume anchor using retained handles, validate root and volume identity, open only exact leaves, reject reparse objects and multiple links before content reads, then revalidate identity, size, timestamps and two bounded observations. The atomicity of approval acquisition and the hard-link/check-to-read transition under a hostile concurrent actor remains unproven. Checking a link count after opening a file with content-read access would already be too late for the stated property. Restricting shares to suppress races could interfere with Steam and requires its own compatibility proof. It is not sufficient to add a warning or infer safety from the small probe.

The existing lockfile contains transitive Windows bindings but no direct Windows API dependency. A small direct binding may be feasible; however, selecting APIs, supported OS/filesystem scope, identity and race semantics and maintaining adversarial tests impose meaningful ongoing cost. This investigation did not establish a sufficiently defensible complete implementation to justify registering or shipping one. This is a current evidence/design gap, not proof that the problem is impossible. The probe does not include a scanner or a fallback.

Recommend investigating an explicit individual-file selection workflow separately: the user chooses each exact manifest through a trusted native picker, and the application receives or opens a narrowly scoped file object with a clearly reviewed consent and identity contract. This removes automatic directory enumeration and Steam-supplied root traversal, but does not automatically solve hard links, replacement, filesystem trust, picker/path races or stable read checks. It would reduce usability for large libraries and may require one approval per file; it is not implemented or approved by this recommendation. If a full root reader is pursued instead, first resolve its native contract and produce a candidate plus actual sentinel and race tests before resuming M1.3 integration.
