## 2. ADR-011 constraints

M1.8's irreversible success means only successful `CreateProcessW`. It cannot establish initialization, a game window, survival, human activity, whole-session identity or a successful handoff. Its identifier/revision-only local IPC, coherent lookup, writer-reserved final validation, unelevated direct creation, literal argument encoding, NUL-only handle inheritance and sanitized results remain unchanged.

ADR-011 expressly requires immediate process-handle release and no background waiter. Tracking cannot silently reinterpret that contract or reopen its diagnostic PID. [ADR-012](../decisions/ADR-012-bounded-standalone-session-observation.md) is **Proposed**, explicitly requesting a restricted duplicate from the creation handle for a later observation owner. ADR-011 itself is unchanged and remains authoritative until separate acceptance. No production source imports this experiment.

## 3. Native approaches and actual candidate

The tested approach owns a bounded wait set using `WaitForMultipleObjects`, with `WaitForSingleObject(0)` to classify only its retained handles after a wakeup. A manual-reset stop event occupies the first slot, plus at most **two** process handles. Tests supply restricted non-inheritable duplicates with only synchronize/query-limited rights. The candidate has no spawning, PID reopening, scanning, kill, database or Tauri function. It returns bounded terminal batches and retains no history. One test-owned thread demonstrates active-wait interruption; the primitive itself creates no threads.

Creation FILETIME is read from the retained handle; PID is read from that same object. `Instant` marks adoption and elapsed observations. A signaled process is terminal before its exit code is read, including code `259`. Already-exited children do not acquire a fabricated alive observation. All closings happen on the wait owner after native waits finish. A stop signal conservatively wins a simultaneous exit; an exit is not claimed without observing it.

Microsoft documents [wait handle lifetime and limits](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitformultipleobjects), [native process timestamps](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes), [exit-code ambiguity](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getexitcodeprocess), and [process termination/child survival](https://learn.microsoft.com/en-us/windows/win32/procthread/terminating-a-process). The experiment stays well below the native wait-object maximum and never closes a handle beneath an active wait.

Rejected on design grounds, not claimed as experimentally compared: PID polling/reopening (identity race), global snapshots/ETW/WMI (scope/privacy/resource cost), job supervision (intrusive lifecycle and handoff semantics), thread per game (unnecessary scaling), and registered wait callbacks (unregister/callback ownership complexity at a two-slot bound). There is no general process manager or provider investigation.

## 5. Confidence-aware session model

Use independent lifecycle, observation and attribution fields rather than a single boolean `playing`:

| State/evidence              | Classification                          | Permitted claim                                                                                     |
| --------------------------- | --------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Launch requested            | Application event                       | One explicit attempt was admitted; process may never be created.                                    |
| Native process created      | Native observation                      | Windows created the requested process, preserving M1.8 semantics.                                   |
| Direct child observed alive | Native observation                      | Exact retained process was nonsignaled at a sample, not initialized/visible/played.                 |
| Direct child exited         | Native observation                      | Exact process signaled; numeric exit and native time may be recorded.                               |
| Observation interrupted     | Observer event                          | Coverage ended through cancellation/shutdown/failure; actual game end unknown.                      |
| Possible process handoff    | Inference requiring additional evidence | A supported explicit adapter signal could suggest transfer. Fast exit alone leaves handoff unknown. |
| Session outcome uncertain   | Conservative inference                  | Whole-game session/actual gameplay cannot be established from these process facts.                  |

Transitions: requested → created → alive (optional) → direct-exited; interruption can end coverage after creation at any point. Immediate exit skips alive. Creation failure ends the attempt without a session-alive claim. Handoff assessment and uncertain outcome are orthogonal: direct exit can coexist with a possible/unknown handoff and uncertain session outcome. Observation failures after creation cannot undo successful creation. Duplicate delivery uses a stable attempt/session key and never relaunches.

**Process lifetime** is the native creation-to-exit interval of that exact child. **Observed activity duration** must be labelled as process observation: the monotonic adoption-to-terminal-observation window includes detection lag; the last-confirmed-alive sample is only sampled process-liveness evidence. Neither proves interaction, rendering, foreground activity or uninterrupted human play. **User-attributed playtime** requires explicit user attribution or separately validated game-specific evidence. It must remain null/unknown here, not implicitly zero, and must not feed an automatic total. Imported provider totals remain separate (DSS).

`Instant` supports nonnegative elapsed measurements within one observer run. UTC wall timestamps locate events for history and backup but may jump backwards/forwards. Do not derive elapsed gameplay from their subtraction, application uptime, a saved PID, restart downtime or time until a launcher exits. Native FILETIME endpoints are useful process facts, not a monotonic playtime clock. Windows sleep/suspend, idle time and clock adjustment are untested here; later policy must explicitly handle them before attributing playtime. Persist elapsed evidence and UTC endpoints separately, allowing unknown/inconsistent wall endpoints without invented correction.

## 6. Handle ownership, shutdown and lifecycle recommendation

The test harness creates synthetic children with Rust `Command`; it duplicates their real creation handles into the candidate. M1.8 production direct Win32 creation, security flags and inherited streams are exercised only by unchanged historical targets. The experiment validates process observation, not a replacement launcher or production handoff implementation. The candidate never receives PID-only authority. The harness retains independent child handles for survival assertions, and only it opens known synthetic descendants/parent-survivors for verification. Parent-survivor reopening compares creation time; that harness convenience is not a production recovery recommendation.

For later production: reserve an optional observation slot before launch without holding maintenance or CPU budget; retain a restricted duplicate immediately from successful creation; transfer it through a bounded ownership mailbox while the launch operation owns admission. Release the writer/launch permit after existing final-validation/creation cleanup, never at game exit. Observation refusal/failure must leave the already-created game running and launch success intact. A transfer failure drops its handle and produces uncertain/unavailable observation without retrying.

One dedicated wait owner, maximum two live entries and one control event, avoids a permanent polling thread per game. A bounded transfer/control protocol remains M2.2 work: the experiment tests between-wait adoption/cancellation and cross-thread stop, not simultaneous production admission/transfer. Normal observing must not consume `Budget`'s two CPU-worker permits or hold a SQLx connection. Native callbacks/threads do no database writes. Terminal delivery occupies at most its two existing slots until short persistence finishes or explicitly becomes uncertain; no independent unbounded queue.

Restore/shutdown order proposed: close launch/observation admission → drain short in-flight creation/transfers → signal/join observer and release handles → brief bounded terminal writes if database readiness permits → existing maintenance/pool shutdown. Never wait for game exit. No writer or maintenance reservation spans observer lifetime or joins. Stop/transfer failure disables observation without blocking the existing restore protocol indefinitely. A game remains externally running. On manager failure there may be no terminal delivery; unfinished durable rows become interrupted on restart, without attaching by PID. Stale generation completions after restore are rejected before any write to the replacement database. Existing launch admission, SQLite timeout/pool limits, backup/restoration and artwork admissions are unchanged by M2.1.

## 7. Persistence feasibility proposal only

Native results support durable **process-observation evidence**, not automatic playtime. A minimal future schema could use one `local_session_observations` row per explicit attempt, independent of imported playtime. This is a design sketch, **not a migration or accepted SQL**:

| Field/group                                                                                          | Proposed contract                                                                                                                                                                                                                            |
| ---------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`, `attempt_id`                                                                                   | Independent opaque 128-bit IDs; attempt unique for idempotent delivery, never derived from PID/title/path.                                                                                                                                   |
| `game_id`, `installation_id`, `launch_profile_id`                                                    | Stable authoritative identities; enforce same bound chain. Retain revisions captured at request for provenance, not execution authority. Initially restrict deletion while history refers to them; later explicit export/delete is separate. |
| `requested_at_utc_ms`, `created_at_utc_ms`, `last_observed_at_utc_ms`, `observation_ended_at_utc_ms` | Separate nullable event endpoints; interrupted rows do not fabricate game end. UTC wall values are not duration arithmetic.                                                                                                                  |
| `lifecycle`, `observation_reason`, `confidence`, `handoff_assessment`                                | Constrained small enums distinguishing requested/created/direct-exited/interrupted, process-only evidence, unknown handoff and uncertain whole-session outcome.                                                                              |
| `observed_elapsed_ms`, `last_alive_elapsed_ms`                                                       | Checked nonnegative within-run monotonic measurements, optional when no usable sample; no downtime added.                                                                                                                                    |
| `native_created_100ns`, `native_exited_100ns`, `exit_code`                                           | Optional numeric process evidence. PID need not be persisted; if retained diagnostically, never attachment authority. Handles are in-memory only and never serialized.                                                                       |
| `attributed_playtime_ms`                                                                             | Nullable and left unset by automatic process observation. Future user attribution needs separate provenance. No derived total update in initial observation scope.                                                                           |
| `revision`, `observer_run_id`                                                                        | Conditional updates and runtime generation reject duplicates/stale completions. Database lifecycle generation stays in memory and invalidates queued writes at restore.                                                                      |

Proposed constraints: unique `attempt_id`; nonnegative elapsed values; last-alive elapsed ≤ observation window; conditional native endpoint fields; bounded enums; exact identity relationships; terminal transitions guarded by `WHERE id=? AND observer_run_id=? AND lifecycle IN (...) AND revision=?`. A repeated identical completion is a no-op; a conflicting terminal completion is surfaced, never accumulated twice. Suggested indexes: `(game_id, requested_at_utc_ms, id)` for keyset history pages and a partial unfinished index for reconciliation. No session join/projection/index change to existing library browsing is needed.

A future recording sequence must tolerate the non-atomic spawn/database boundary: a short committed requested row can precede existing writer-reserved creation; release launch resources, then conditionally record created/terminal evidence in brief transactions. Crash before/after creation can leave only requested, and a later failed write can lose observation evidence. That row is uncertain on restart, never safe to retry as launch. Recording failure must not turn successful creation into failed execution. This requires new production failure tests, not an assumption that SQLite makes spawning atomic.

Propose at most two active/terminal-pending ownership slots and a **10,000-row history cap**. At the cap, pause new recording and preserve existing personal history; launching remains available. Export/deletion requires an explicit later workflow, with no silent FIFO pruning. This bounds new storage without treating history as cache. Reconciliation uses the unfinished index with a bounded read (limit three detects violation of the two-slot invariant); unexpected excess fails observation closed and requires a bounded repair, not full startup process/library scanning. Restart marks unfinished coverage interrupted at the last known observation, with actual end unknown; no automatic reattachment.

Migration strategy if separately approved: add a new application migration after v5 (tentatively v6); retain unchanged historical SQL/checksums and exact v2/v3/v4/v5 validators, add an exact new schema validator, and migrate only owned active copies. Extend existing backup/restore regressions to empty/populated history, unfinished rows, duplicates and repeated restore. Frozen benchmark schema stays v1. Backups contain unencrypted activity metadata; restore replaces history, never merges, replays completion or reattaches to processes. Older snapshots have no such history and must not fabricate it. Restored active rows are interrupted under the new runtime generation. No migration, table, retention operation or session write exists in M2.1.

Privacy: local identity/timestamp/confidence evidence only; no paths, arguments, environment, input, window titles, executable scanning, telemetry or broad permissions. PID/FILETIME are diagnostic rather than persistent authority. History export/deletion and disclosure of activity in unencrypted database backups need product wording during persistence implementation.

## 9. Preserved contracts and limitations

Application schema **v5**, exact v2/v3/v4/v5 database-only backup compatibility, six frozen generator-v1 datasets, library queries/cache bounds, ADR-007 E1–E5, M1.8 creation-only semantics and M1.9 durable artwork code remain unchanged. No additional native user-interface smoke is needed for a test-only feature; no new production interaction is claimed. No expensive 15k/25k browsing benchmark is repeated because no production browsing/scheduling code changes, and there is no performance-improvement claim.

Coverage limitations: one Windows desktop/NTFS/toolchain; finite synthetic runs; no forced actual PID reuse, sleep/resume or clock-jump experiment, physical OS crash/power failure, real games or generic handoff attribution. Parent tests use a synthetic manager and hard `exit(73)` without destructors, not an actual Game Manager crash dump. Rust unwind recovery does not imply destructor execution under release panic-abort; the hard-exit case covers OS handle release instead. No actual `WAIT_FAILED` on a pending valid process wait is forced; invalid identity input, panic and hard-exit paths provide failure coverage without unsafe close-during-wait behavior. A real production transfer queue, completion persistence, maintenance integration and UI remain future work. Short CPU counters can quantize to zero and do not prove zero overhead/leak freedom or lower-memory certification.

## 11. Feasibility recommendation and cost-benefit stop rule

**A. Proceed to M2.2 production standalone session observation**, only after separate user authorization and acceptance/revision of Proposed ADR-012. This is a recommendation, not the start of M2.2 or automatic ADR acceptance. Proceed with bounded **direct-process observation** and explicit uncertainty; no generic handoff tracking or automatic user-playtime totals. Keep persistence a separately verified part of the authorized scope, never an implication of the native prototype.

The inexpensive retained-handle wait primitive answered the native feasibility questions without new dependencies, process scanning or production changes. Generic whole-session/gameplay attribution remains unsupported and is deliberately outside this recommendation. Stop investigating global handoff discovery now: no demonstrated requirement justifies broader privileges, a supervision framework or open-ended native work. Reopen only for a concrete supported game/adapter with explicit handoff evidence or a reproducible failure of bounded ownership. M2.2 must validate the narrow transfer/maintenance/persistence races listed above before production completion. Stop M2.1 after implementation, verification and this recommendation.
