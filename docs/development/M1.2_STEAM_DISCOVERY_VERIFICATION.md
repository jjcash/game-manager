# M1.2 — Steam Local Discovery Contract and Fixtures

Date: 2026-10-28. **M1.2 is complete within its contract/fixture scope.** Evidence review, an executable offline contract and synthetic fixtures are verified. **No production Steam reader, importer, account integration, Steam UI, migration or application write path is added.** No real Steam metadata, account, registry installation or game directory was inspected. A small M1.1 modal keyboard-boundary correction discovered during regression verification is documented in section 14.

The finding is deliberately limited: approved local manifests can supply **client-reported installation records**. They cannot certify the selected account's ownership, physical payload integrity, completeness of an uninstalled library or current family access. Binary/cache support should not be built merely to imply otherwise.

The clean branch `feat/m1.2-steam-discovery-contract` began at `3ab1a1c6abaf7a6bcd1da6245aa237634a2a4b8a`, identical to `main` and `origin/main`, merging M1.1 commit `3002205`. Inspected v1/v2 migrations; canonical/source/membership/installation identities; override rows and projection writes; revision-checked manual transactions; deletion guards; bounded query/search/source/global-presence behavior; command capabilities; fixture and ordinary-build isolation. M0 remains conditionally closed under ADR-007 with E1–E5. M1.1 identity/persistence semantics, source ownership, schema 2 and query policy remain unchanged. The sole runtime change handles modal Tab boundaries; no Steam runtime code is introduced.

The executable contract is an integration-test module under `src-tauri/tests/support`, not a stub connected to the application. Installed discovery here means **a stable approved manifest reports an installed app**. It does not mean the game payload was inspected, executable is launchable, account owns it or the manifest cannot be stale. The proposed label is “Steam reports installed · ownership unknown,” not “owned and verified.” Apps may be games, tools, servers or soundtracks; without validated type metadata the preview must not invent a game-only filter. Selection is explicit, initially unchecked.

Uninstalled full-library discovery is **unsupported**. Cache-only fixtures show why useful hints cannot be turned into complete/account-owned library claims. The chosen cache policy is deliberately stricter than the upstream exporter's user-facing “visible library” description: no validated account-scoped live catalog is available in the selected sources.

## 4. Classification contract

Keep independent axes; do not encode ownership in completion_status or the three installation-state values.

| Classification                      | Required evidence                                                                                                                         | M1.2 local output                                                                                                                                                     |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Confirmed local installation record | Stable, valid approved manifest; matching nonzero canonical-decimal u32 AppID; safe directory component; recognized installed flag subset | `ClientReportedPresent`, always qualified as client metadata and potentially stale. No physical verification.                                                         |
| Locally cached/library-visible      | Distinguish a mere cache candidate from a validated account-scoped library snapshot                                                       | Numeric cache directory yields only `CacheCandidate`, not verified current visibility. Stronger library-visible label is reserved until a source can substantiate it. |
| Account-owned                       | Credible entitlement evidence bound to an explicitly selected account and observation time                                                | **Never emitted** by selected local parsers. Reserved for a future separately approved evidence source.                                                               |
| Shared/family-accessible            | Credible owner/access distinction for the selected account                                                                                | **Not distinguishable here**. Family hints remain uncertain; never translate LastOwner or cache inclusion into this label.                                            |
| Ownership unknown                   | No sufficient entitlement evidence, even if installed/cached/account-selected                                                             | Every current local observation.                                                                                                                                      |
| Potentially stale                   | Caches/manifests may outlive the event/account/context they describe                                                                      | Every local observation retains this qualifier; stable bytes are not semantic freshness.                                                                              |

The conservative installed subset accepts FullyInstalled (4), optionally UpdateRequired (2) and AppRunning (64). Other/missing/unknown/contradictory flags yield installation **unknown**, preserving the candidate with a warning rather than asserting present or missing. This is intentionally narrower than Playnite's general bit check. Name is optional: use `Steam app <AppID>` with explicit fallback provenance; it is not verified provider metadata. Names containing control characters or exceeding the existing 200-character contract also fall back.

Cache disappearance never revokes ownership/membership. A missing manifest can only propose “Steam no longer reports this installation” after a complete, successful scan of the relevant approved roots and explicit later review; inaccessible/unapproved roots, truncated files, cancellation and concurrent changes make absence inconclusive. Any later accepted change affects provider installation metadata only, preserving canonical IDs, memberships and user-owned records. No real installation is removed.

## 5. Account context and multi-account safety

| Situation                                                  | Contract                                                                                                                                                                     |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Steam not running                                          | Existing approved metadata may be read later; account/session state remains unknown. No requirement to start Steam.                                                          |
| Steam running/reported logged in                           | Running is not authentication evidence. Shared reads must coexist with updates; no process inspection/injection or authenticated calls.                                      |
| One locally known account                                  | Directory existence or a MostRecent marker is still insufficient to select it implicitly.                                                                                    |
| Multiple accounts / previous account / account switch      | Require explicit context selection or explicit “continue without account attribution.” Never relabel account A's source as B, copy A's entitlements to B or delete A's data. |
| Families / one installation accessible to several accounts | Keep the client installation separate from account entitlement/access. Locally accessible does not mean personally owned.                                                    |
| Incomplete/stale library cache                             | Retain uncertainty and prior catalog data. No missing-owned-game, revocation or ownership downgrade inference.                                                               |

The test fixture's `UserSelected` context means a user's choice, **not authentication or an entitlement grant**. Symbolic account labels are never SteamIDs. A zero/one/many-candidate list does not select itself. The proposed first production source is account-neutral and requires confirmation of that limitation; it does not read account files at all. If account-bound discovery is added later, require explicit selection of the actual stable SteamID64 and a separate evidence/permission design; user confirmation alone still cannot manufacture ownership evidence.

## 6. Source keys, canonical identity and refresh

Proposed version-1 provider contract:

These are eventual persisted importer keys. The recommended M1.3 preview itself creates no catalog/source bindings.

- Provider namespace: `steam`; adapter contract version: `1`.
- Client-scoped source key: `steam.local.v1/client/<application-assigned-client-id>`. The client ID is persisted by the application, independent of folder index/path, title, display name, process or last account. Existing library_sources.id remains an independent stable ID; source_type is `steam`, never `manual`.
- External item ID: canonical decimal AppID (`1..=4294967295`), separate from every local Game/Entry/Installation ID. No leading zeros, signs, mod/shortcut IDs or title matching.
- Reserved later account source key: `steam.account.v1/account/<SteamID64>`. Its scope is explicit and cannot be changed in place when accounts switch. It is not created from initial local evidence.
- Canonical association: reuse an unambiguous established `(steam, AppID) → game_id` mapping. If none exists, propose a new independently identified canonical game. An identically titled manual game stays separate unless a later explicit association workflow is approved. Conflicting existing mappings require review; never pick by title or overwrite a mapping.
- One client/AppID membership can have observations/installations in multiple approved library roots. Duplicate records for the same root/component coalesce; different roots remain distinct observations. Conflicting fields in the same logical placement require review, not an invented extra physical copy or silent winner. AppID grouping does not prove physical-file identity.
- A later catalog writer must persist source bindings and provider identity mapping with membership creation atomically. Unique `(source_id, external_item_id)` already supports idempotent membership upsert; it is not by itself a cross-source canonical mapping.

Renamed provider titles keep all IDs. Root order changes and repeated scans cannot create new client identities. Explicit root rebinding/movement requires fresh permission and identity review, not automatic relocation. A changed install-directory component is a metadata proposal for that logical client/root/AppID installation, not permission to touch a game directory. Duplicate approved paths/aliases require native physical-root identity checks; ASCII lexical candidate deduplication in the harness is not that proof.

If future account memberships refer to the same app, the established Steam mapping can retain one canonical game. The physical installation remains attached once to the client membership; account entries do not each clone that installation. Existing source filtering with **global canonical installation presence** already supports this separation. Source/account removal, ownership revocation, user-directed merging and provider uninstall behavior need their own later explicit operations.

## 7. Overrides, effective values and proposed schema work

Keep the four layers distinct:

1. Canonical Game ID and explicit Steam mapping identify the app; provider title is not identity.
2. A provider-value store retains observed Steam values and evidence separately.
3. An existing game_field_overrides **row** wins, even when value is SQL NULL or unchanged.
4. games remains the effective Library projection used by current indexed/paged queries.

M1.1 creation/save writes all five supported overrides: title, release_date, genre, developer and favorite. Thus accepting an unchanged title or leaving an optional field blank on save still makes it user-owned. Importers must test **row existence**, not `COALESCE(value, provider_value)`. Explicit cleared genre/date/developer must stay NULL; false favorite must stay false. Required title validation remains intact. Account/source refresh never deletes override rows or rewrites manual memberships/installations.

Initially only a valid manifest title is a proposed provider field; a missing title is a separately marked display fallback. No release date/genre/developer is invented from unrelated fields. Favorite and completion remain user data. Missing provider fields do not clear previous observations. A provider rename can update games.title/sort_title only when there is no title override; projection, provider value, relationships and revision changes must commit atomically. A manually saved fallback title stays overridden until the user explicitly changes/reset policy later. No reset-to-provider workflow is implemented here.

Schema v2 is insufficient for persistent Steam import: it lacks provider bindings/canonical external mappings/value provenance, and its CHECK constraints only allow game origin `legacy|manual` and installation state_origin `legacy|user`. **Do not insert Steam data as manual/user or silently redefine legacy to mean provider.** The current frontend DTO validator also accepts only these existing values.

For a later separately authorized catalog-write milestone, propose a narrow forward migration, not an implementation in M1.2/M1.3 preview:

| Proposed addition                                                                                        | Purpose                                                                                                                   |
| -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Steam source binding keyed by source_id, unique versioned scope key/client ID                            | Stable source scope and approved-root configuration reference; no credential fields                                       |
| DSS-style game_external_ids `(provider_id, external_id)` unique with game_id FK                          | Explicit canonical Steam identity shared across client/account sources                                                    |
| DSS-style game_metadata_values `(game_id, source_id, field)` with value, observed time and evidence kind | Keep provider title/fallback observations separate from user overrides; no generic synchronization framework              |
| Minimal source-entry/install observation provenance                                                      | Last seen, scan completeness, evidence/version and unknown ownership; do not overload completion or installation presence |
| Explicit `provider` game origin and `provider` installation-state origin; typed frontend support         | Preserve existing ownership semantics rather than falsely marking imported data user-owned                                |

Extending existing inline SQLite CHECKs may require carefully tested table replacement; it must preserve IDs, FK references, indexes, defaults and restrictive deletion behavior. It is **not** a harmless ALTER-column assumption. Before adopting a numbered migration, validate populated-v2 upgrades, rollback after every DDL/data step, newer-schema rejection, unrelated/manual-data preservation, explicit NULL precedence, repeated import/restart and concurrent edits. Keep generator-v1 fixtures/migration history frozen. No migration file, provider tables, source rows or provider framework is added now; accepted DSS direction does not pre-approve untested DDL.

## 8. Read permission and filesystem contract for a future reader

The following is a design/exit requirement, not a claim that the fixture harness implements native confinement:

1. Start only after a deliberate local-Steam action. Probe only fixed noncredential registry path values, or let the user choose a client root. Read no Steam account/config file before a corresponding explicit grant.
2. Bind approval to native directory identity and a metadata-only capability in Rust. Library paths found in VDF are **candidates**, never grants. Each additional root needs review/approval before opening anything there. Frontend booleans/path strings cannot forge a grant.
3. Read only an approved root's `steamapps/libraryfolders.vdf` where appropriate and exact `steamapps/appmanifest_<AppID>.acf` leaves. Enumerate one metadata directory level; never recursively descend into common, music, workshop, shadercache, userdata or arbitrary cache/config trees. An installation component is validated text for display/proposal, not a path to traverse.
4. Deny relative/drive-relative, UNC/device namespaces, ADS, traversal, invalid/reserved components and deceptive trailing names. Treat drive-letter aliases/case as lexical hints, not physical confinement. Use local-volume and file-identity validation; reject unsupported mapped/reparse/linked/special objects. Microsoft documents [Windows naming rules](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file); the fixture policy is intentionally conservative.
5. Production must establish handle-relative/no-reparse ancestor and leaf access, or an equivalently demonstrated native guarantee. A string-prefix test, canonicalize-then-open sequence or leaf-only reparse check is insufficient against ancestor replacement. Reject hard-linked metadata when provenance cannot be confined. Validate this on disposable Windows junction/symlink/rename fixtures before exposing any scanner command. M1.2 models leaf proofs only and does not certify this prerequisite.
6. Open existing regular metadata files for read only; allow compatible Steam read/write/delete sharing so atomic replacement need not block. No create/write/repair/delete flags, attribute changes, installation checks or locks that impede Steam. Windows [CreateFileW sharing semantics](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) require deliberate implementation, not assumptions about a generic filesystem open.
7. Bound each read; compare trusted file identity, size/time and two bounded byte observations. Truncation/replacement/differing bytes fail that record. At most one bounded retry in a future reader; otherwise warn/incomplete. Equal reads do not prove a Steam transaction, correct entitlement, freshness or resistance to every ABA writer pattern. Preview approval must revalidate evidence before any eventual catalog commit.
8. Never read passwords, session/access tokens, auth databases, cookies, broad config stores or game executables; never write Steam files, inject processes, call internal authenticated interfaces, initiate downloads/installs/updates or launch anything. Do not log account identifiers/full local paths or unknown field values; show approved-path context only where necessary in the local review UI.

Validated parser limits: manifest 64 KiB; folder index 2 MiB; 32 roots; depth 16; 4,096 bytes per token; 32,768 key/value pairs. The test accepts a generated 25,000-AppID folder index and rejects excess budgets. Only quoted UTF-8 text KeyValues with optional BOM, whitespace, line comments and supported escapes is accepted; duplicate keys (ASCII-case-insensitive), includes/directives, bare-token extensions and malformed input fail explicitly. No include resolution or silent partial text parse is permitted.

Proposed scan limits, to benchmark in M1.3: one active scan, sequential/bounded reads with cancellation checks, 25,000 records and 128 MiB aggregate metadata input, 100-row preview pages. Retain bounded Rust-side state with shared root references, never a full frontend library array or decoded artwork. Current tests validate finite byte/record limits, not a production RSS/latency guarantee or a new M0 policy.

## 9. Future preview and commit protocol

1. User chooses local Steam discovery and reviews its installed-app/unknown-ownership boundary.
2. Show root/account context. With no verified account source, require explicit continuation without attribution; if later account hints conflict, require selection/confirmation, never use directory or recency alone.
3. Approve client/additional metadata roots; scan only supported records with bounded work and cancellation. Steam may remain running. Files changing or missing produce scoped warnings.
4. Display a paged preview containing AppID, proposed title/fallback, installation-evidence label, unknown ownership, stale/incomplete warnings and source scope. Keep valid rows despite individual failures. Unknown app types remain explicit and initially unselected.
5. Allow deliberate selection. A later association UI must distinguish established exact mapping, proposed independent canonical creation, manual same-title records and conflicting mappings. No automatic fuzzy/title merge.
6. M1.3 recommendation stops at read-only review: close/cancel discards preview state and grants; there is no commit button implying implemented import.
7. A separately authorized importer can later accept selected proposals using opaque snapshot/item references and expected game revisions, revalidate source scope/file proofs and commit short parameterized SQLite transactions outside scanning. Create required canonical/binding/value/membership/installation records atomically; resolve overrides before updating games; bump each affected revision and invalidate bounded Library generations after commit. Do not alter pool/query policies or add importer-dependent caches.
8. Suggested eventual batch cap is 100 selected items. Cancellation before commit writes nothing; current batch failure rolls back fully. Earlier committed batches remain explicitly reported, with resumable/idempotent source keys; never claim all-or-nothing for the whole scan. A manual edit during preview yields conflict/review rather than blind retry. Partial warnings never authorize deletion or revoke ownership.
9. Manual refresh is another deliberate scan. Missing cache or unavailable folders preserve prior catalog facts with warnings. Only a complete relevant scan plus explicit later approval can update provider installation metadata to missing. No silent canonical/membership removal, filesystem uninstall or account reassignment.

## 10. Fixture inventory and test evidence

All fixtures are authored synthetic data, not sanitized real captures. [Fixture README](../../apps/desktop/src-tauri/tests/fixtures/steam/README.md) lists each file and provenance. The four ACF files, three folder VDF files and four JSON matrices cover valid/unnamed/incomplete/truncated manifests; multiple/duplicate/hostile roots; cached uninstalled candidates; duplicate IDs; unknown entitlement; account/family/switch ambiguity; missing files; path attacks; changing/partial/oversized/special-file observations; and unsupported/changing binary headers. Account labels are fictional, LastOwner is zero, and no artwork or binary cache body is included.

The **17 Rust contract tests** separate text parsing from inference/snapshot policies. Additional generated inputs test filename/ID agreement, flags, Unicode, malformed IDs/escapes/UTF-8/directives/duplicate keys, depth/pair/token/root/stream budgets, a 25k index, exact-key grouping/association, all five M1.1 override rows including NULL/unchanged values, retained valid preview rows and cancellation without commit. Snapshot cases model identity/mtime/length/byte differences and reparse/nonregular rejection; they do not perform live I/O or simulate a complete Windows kernel security boundary.

Known binary magic values are recognized only to return **known but deferred** (appinfo 39/40/41, packageinfo 39/40). Unknown versions and short headers fail safely. Even a recognized v41 header with a hostile offset is never followed. No source-format success is interpreted as ownership evidence, and no authentication/client state is inferred from the test fixtures.

## 11. Cost-benefit assessment

| Mechanism                                     | Complexity / maintenance                                                                 | Coverage benefit                                                        | Decision                                                                                    |
| --------------------------------------------- | ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Fixed root candidates + approved folder index | Low parser complexity; medium Windows approval/confinement work                          | Multiple local libraries                                                | Implement safe reader only in separately authorized M1.3; no automatic path grants          |
| Bounded text manifests                        | Low-medium format cost; medium partial-update/safety work                                | Client-reported installed apps, optional name/build hint                | Best initial capability; explicit unknown type/ownership/staleness                          |
| Numeric cache directories alone               | Low extraction cost, uncertain layout/account semantics                                  | Candidate IDs for some cached uninstalled apps                          | Fixture/research only; insufficient for initial import claims                               |
| Binary appinfo/name/type resolution           | Medium-high format, string-table/offset/bounds and maintenance cost; source can be large | Better names/type filtering and cache candidate display                 | Defer until privacy/safety/real coverage benefit is measured; do not add a large parser now |
| Packageinfo/license inference                 | High semantic risk, no account ledger established                                        | No demonstrated reliable account-owned coverage                         | Reject as ownership mechanism                                                               |
| Account/local/shared caches                   | Medium-high privacy and compatibility cost, incomplete/stale attribution                 | Optional later account/activity context                                 | Defer; never infer entitlement from mere inclusion                                          |
| Public/store metadata or Web API              | Networking, rights/rate/visibility/auth considerations                                   | Public metadata could improve naming; keyed ownership APIs are separate | Outside current offline/credentials-free boundary; not required for core use                |

No credible selected local source establishes complete current account ownership. That limitation is acceptable and preferable to an entitlement claim derived from a cache. ## 12. Recommended minimal M1.3 scope
