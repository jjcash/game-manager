## Implemented semantics

| Control          | Meaning                                                                                                                                                                                                                                                                                     |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Title search     | Literal contiguous substring of display `title`; trims leading/trailing Rust Unicode whitespace, preserves internal whitespace. Empty/whitespace-only search imposes no title predicate.                                                                                                    |
| Case and Unicode | SQLite built-in LIKE folds ASCII A–Z. Non-ASCII text matches exact code points; no Unicode normalization, accent removal or full Unicode case folding. Japanese two-character queries work. Composed/decomposed text is not promised equivalent.                                            |
| Punctuation      | `%`, `_`, backslash, quotes and apostrophes are literal data. SQL values are bound and LIKE metacharacters escaped. No wildcard, regex, FTS syntax or external metadata query is exposed.                                                                                                   |
| Installation     | Installed means at least one `present` copy across any membership. Not installed is its exact complement, including zero copies and only missing/unknown copies.                                                                                                                            |
| Source           | One selected stable source ID; include a canonical game if any membership has that ID. Installation filtering remains global to the canonical game, including copies attached to another source.                                                                                            |
| Release years    | Optional inclusive lower/upper year, translated to ISO date bounds `YYYY-01-01` / `YYYY-12-31`. Either bound excludes NULL release dates. Current data uses nullable ISO calendar dates; arbitrary externally written malformed date text is outside this schema's validated data baseline. |
| Sorting          | Title uses `(sort_title,id)`; release uses `(release_date,id)`. Both fields follow the selected ascending/descending direction, including ID ties. SQLite NULLs are first ascending and last descending. No relevance sorting or locale collation is implied.                               |
| Row grouping     | One canonical game per row. Source names, entry counts and copy counts continue to summarize the whole canonical game, not just matching memberships.                                                                                                                                       |
| Reset/selection  | Criteria edits clear selection and reset scrolling to zero; unchanged-criteria paging/eviction and navigation retain stable selection and position. Clear search changes only the text; Reset all restores every criterion.                                                                 |

These case rules follow [SQLite LIKE behavior](https://www.sqlite.org/lang_expr.html#like). They are explicitly tested rather than presented as complete international search support.

## Query strategy and FTS evaluation

`storage/query.rs` builds parameterized predicates, uses canonical set membership for source/installation filters, with an indexed copy-presence probe per library entry and materializes the bounded ID page **before** summary aggregates. It shares the M0.2/M0.3 summary projection and `LibraryRow` conversion. Counts and pages use identical predicates. An unfiltered count retains SQLite's direct `count(*)` path. No full result array is transferred to React.

All ORDER BY fragments come from four private enum matches; user text is never concatenated into SQL. Existing `ix_games_sort`, `ix_games_release`, `ix_library_game` and `ix_installations_entry` are reused. Leading-wildcard LIKE is a title scan, not an indexed substring search; ordered page selection still uses the existing order indexes where the planner chooses them. Source sets use the existing source-leading unique index; installed sets scan memberships and probe the existing copy index. NOT installed uses the complement of that non-NULL game-ID set. This avoids repeated game-to-membership table lookups found slow in the first measurement. The query shape was changed in response to measured count latency; no additional index was introduced.

The benchmark-only `search-evaluate` command compares literal LIKE count-plus-100-ID page retrieval with a freshly populated FTS5 trigram TEMP table on one SQLx connection, over an existing read-only benchmark database. This uses the same locked bundled SQLite engine, with 50 retained warm iterations after one discarded warm-up; index creation time is excluded. The comparison does not measure production FTS maintenance, migration, disk space or full summary aggregation. FTS accelerates selective/no-match terms, while common terms can favor the existing scan/order path. Trigram MATCH does not support substrings shorter than three characters, and LIKE with ESCAPE cannot use its trigram optimization; see [SQLite FTS5 trigram limits](https://www.sqlite.org/fts5.html#the_trigram_tokenizer).

Selected M0.4 strategy: literal LIKE, preserving consistent one/two-character and punctuation behavior without a production index/migration or two search paths. This is a measured prototype implementation choice, not abandonment of DSS's eventual FTS direction. A title scan at 25,000 records is explicitly acknowledged. Re-evaluate FTS, Unicode folding and source-selective index/query shapes if later scale, hardware or workloads require them. No FTS production index exists, so insert/update/delete trigger or migration consistency work is not claimed.

## IPC and validation

| Command            | Request                                        | Response                                                              |
| ------------------ | ---------------------------------------------- | --------------------------------------------------------------------- |
| `library_get_info` | Optional `criteria`; omission selects defaults | `{total,libraryTotal,sources:[{id,name}],source,diagnostics,queryMs}` |
| `library_query`    | `{request:{limit,offset,criteria}}`            | Existing `{offset,items:LibraryRow[],queryMs}` window shape           |

`criteria` fields: `search` string, `installed` enum (`all`, `installed`, `notInstalled`), nullable `sourceId`, nullable `yearFrom`/`yearTo`, `sort` enum (`title`, `releaseDate`), `direction` enum (`asc`, `desc`). Defaults are empty text/all installations/all sources/no year bounds/title ascending. Rust rejects unknown fields and enum values. Search is at most 200 Unicode scalar values without NUL; source IDs are nonempty, at most 128 UTF-8 bytes and contain no control characters. Years must be 1–9999 with from <= to. Limit remains 1–200 and offset <= 1,000,000. UI text input additionally limits UTF-16 length to 200. Unknown valid source IDs produce no matches.

`total` is the filtered canonical count; `libraryTotal` distinguishes a genuinely empty database from no matches. Source options are bounded to the first 100 ordered source records; current synthetic datasets have five. Counts are fetched once per criteria generation; pages do not repeat them. The existing `library_get_page` and `library_get_window` commands/services remain available for previous contracts. The new command has explicit main-window capability permissions. No raw SQL, path, shell or arbitrary expression is accepted.

Rust domain errors preserve the structured code/operation/message contract; low-level details stay in local diagnostics. Tauri rejects malformed DTO types before command execution. The frontend validates request years/text and response shapes, counts, bounded source lists, row identity/fields and page bounds. A short page relative to the known count remains a `CHANGED` error. There is still no application writer/importer: count/page consistency across external concurrent writes is not claimed. Refresh/query generations handle frontend staleness, not database snapshot revisions.

## Frontend state, cache and diagnostics

Search input updates immediately and applies after **150 ms** from the last edit. Other criteria apply on the next timer turn; clear/reset involving text use the same search debounce. Old rows and result counts disappear immediately when controls change. TanStack Query retains only bounded metadata as placeholder data so source options remain usable during count requests; placeholder counts/rows are never rendered as results and never enable page requests. Input DOM nodes remain mounted and keep keyboard focus.

Criteria and refresh generation are included in query keys. A criteria change cancels queries, clears that view's cache and queued work, then starts fresh scoped metadata/pages. Within a criterion, the existing six-page cache and 100-row windows remain; arbitrary jumps fetch only viewport pages. Metadata and page requests now share the existing gate, allowing only one native library request in flight. A running Tauri invoke cannot be physically cancelled; its permit remains held until settlement and an aborted result is discarded. Unmount cancels queued work and clears the view cache.

Zustand holds criteria and small UI state only. React owns transient debounce timing; TanStack Query owns backend data. Fixed 38 CSS-pixel rows and eight overscan rows per side remain unchanged. No complete catalog or JavaScript-side filtering/sorting is introduced.

Development diagnostics retain M0.3 query/request/frame/render/cache metrics and add backend count duration, frontend metadata request duration, and criteria-to-usable-commit duration. The latter includes debounce and native queue wait, starts at the latest control edit and ends when visible rows (or a successful zero-result state) are committed. It is not a paint trace. Metadata `queryMs` measures the filtered count only; source enumeration/global counts/IPC are included in frontend metadata duration. Page `queryMs` includes pool/query/decoding/projection, not IPC. These overlapping durations are not additive. Samples remain bounded and diagnostics are disabled in ordinary optimized builds.

The native query driver additionally records up to 4,096 frame intervals and 128 JavaScript long tasks/spikes/action markers across criteria changes. It reports supported/unavailable long-task observation rather than inferring CPU causes from every long interval. No FPS is estimated.

### Plans and FTS experiment

Observed plans use a source-leading existing unique index (`sqlite_autoindex_library_entries_2`) for the source set, covering `ix_installations_entry` for presence probes, and the canonical primary-key index for membership lookup. Broad installed sets can make SQLite choose primary-key candidate lookup plus a temporary order B-tree, rather than streaming the title index. Not-installed/default/deep scans use the covering title/release order indexes where appropriate; release bounds can use `ix_games_release`. The final 100-row projection still uses `ix_library_game` and the copy index for bounded aggregates. Exact plans for count and page are stored for every case. Representative source-plan prefix:

```text
SEARCH g USING COVERING INDEX sqlite_autoindex_games_1 (id=?)
LIST SUBQUERY 1
SEARCH e USING INDEX sqlite_autoindex_library_entries_2 (source_id=?)
CREATE BLOOM FILTER
```

Representative installed count: `SEARCH g USING COVERING INDEX sqlite_autoindex_games_1`, `LIST SUBQUERY`, `SCAN e`, then `SEARCH i EXISTS USING COVERING INDEX ix_installations_entry (entry_id=? AND detection_state=?)`. A temporary B-tree for page ordering can involve the matching ID candidates; it is not claimed that every sorting operation is limited to 100 inputs. Only the summary aggregation and transferred rows are bounded to the page. No new index or forced planner hint is used.

### Earlier failures and final scope

Preliminary failures were not hidden or counted as final passes. SQLx 0.9 API differences in the first compile were corrected. A benchmark-only signed deep-offset calculation initially underflowed when fewer than 100 results matched; it now clamps to zero, with request bounds still enforced. The first FTS evaluation's short Unicode term was damaged by a shell text-rewrite encoding; the escaped-code-point version was rebuilt and all four evaluations rerun, and only corrected results are used above. The initial frontend tests assumed overlapping/synchronous metadata starts; they now wait for the shared gate while preserving stale-response assertions.

Native smoke testing found source options disappearing while a new count was pending; bounded placeholder metadata now preserves controls, while every placeholder count/row is hidden. Search input focus remains mounted across criteria. Native telemetry also exposed a stale virtualizer offset after shrinking deep results; disabling virtualization during pending metadata resets its cached geometry/offset, and a deep-to-five-row regression test passes. An earlier native run's missing visible-time sample is excluded from the final baseline. The slow correlated-count baseline motivated the measured membership rewrite; its remaining stress costs are explicitly retained as limitations.

The final normal production build is performed after the benchmark runs so the default executable has diagnostics/benchmark selection disabled. No commit, push, application process or benchmark listener is left running. M0.5 has not started.

## Known limits and M0.5 recommendation

ASCII-only case folding, exact non-ASCII code points, no normalization/relevance/fuzzy matching, and scan-based infix search are deliberate documented limits. Offset pagination is retained for arbitrary scrollbar positions; deep-window measurements are recorded before considering keysets. Canonical relation summaries are global even under a source filter. Source controls list at most 100 records. Concurrent external mutation needs a real revision/snapshot contract before importer/writer milestones.

Hardware/cache state, short sample counts, idle/automation intervals and process-memory point samples limit performance conclusions. HDD, lower-memory, controlled cold-disk startup, physical Windows scaling, concurrent import load and long-session leak validation remain separate work. Any frame intervals above 50 ms remain open unless measurements establish otherwise; a lack of JavaScript long tasks does not prove GPU/compositor/IPC causes.

Recommended M0.5 scope, only after separate authorization: a bounded synthetic-thumbnail loading prototype, with decode/cache limits, corrupt-image fixtures and search/filter/scroll measurements under artwork load. First review the remaining 25,000-game count costs and long-task markers; covering-index/count-cache alternatives and hardware/long-session measurements need their own evidence. No M0.5, artwork, importer or job implementation is started here.
