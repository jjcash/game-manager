## 3. Exact scope

One deliberate attempt may execute a persisted user-owned standalone profile bound to a manual-source Windows installation. Schema v4, independent IDs, immutable bindings, persisted configuration, existing revisions and exact v2/v3/v4 backup compatibility are retained. There is no migration, new package/version, provider adapter, discovery/scanning, script/shortcut/URL launching, automatic elevation, launch queue, session table, supervision, playtime, mod activation or M1.9 work.

Existing `windows-sys` Foundation/Security/Threading features are enabled for production instead of only development. The locked version remains unchanged. No dependency installation is required.

## 4. Production modules

`src-tauri/src/launch/windows.rs` adapts the proven M1.7 indexed context lookup, configuration/path resolution, Windows argument encoder and Win32 creation boundary. The isolated M1.7 candidate remains available to its original tests; production never imports test support or simulated authorization enums.

## 5. IPC and capability admission

Exactly one production launch command, `standalone_launch`, is registered in both ordinary and benchmark builds. Its request is `{gameId, profileId, expectedProfileRevision, expectedGameRevision}` with Serde unknown-field rejection. Executable paths, command lines, directories, environment maps and authorization booleans are not request fields. Invalid IDs/revisions fail before execution.

The application command manifest opts it into Tauri ACL enforcement. Only `allow-standalone-launch` is added to the existing local `main` capability; no remote origin or general shell/filesystem/opener grant is added. The command additionally rejects a caller label other than `main`. Capability defaults retain local-only admission and existing CSP. Tests verify the schema, caller gate, capability scope and sanitized serialization. Rust independently validates every request; a frontend button/boolean does not prove a human gesture against compromised same-origin code.

## 6. Profile selection and deliberate action

The bounded existing game editor contains a native labelled select and Launch button. A valid supported explicit default may be initially selected. A sole profile never becomes an implicit default. Unsupported saved profiles remain visible with a reason and cannot be selected for execution. One-time selection does not edit the persisted default or profile.

Only the Launch button calls IPC. Startup, game/details navigation, selection, profile/default edits and restore do not call it. A synchronous in-flight ref plus disabled controls prevents repeated submission. Completion permits another deliberate attempt; there is no hidden permanent single-instance rule. Selection state survives unrelated editor refreshes without remounting an active launch control.

## 7. Identity and revision enforcement

The authoritative chain remains `Game -> LibraryEntry -> Installation -> LaunchProfile`. A coherent preparation transaction checks singleton application purpose and a bounded indexed join for the exact game/profile pair. It verifies profile/game revisions, required installation/membership/source, user provenance, standalone kind and Windows/manual context. Saved profiles on provider memberships remain valid metadata but cannot execute.

Final validation acquires `BEGIN IMMEDIATE`, rereads the same context and repeats validation. It compares revisions and the relevant installation, membership, source, configuration and explicit default fields defensively. Detectable unversioned changes, removal or mismatch fail. Group/default/installation changes retain their existing game-revision effects; profiles are never merged or retargeted by name/path/order. No library scan or additional browsing projection is introduced.

## 8. Maintenance admission and lock ordering

Each application database lifecycle owns a permanent-close admission gate with one active permit. Entry uses `try_acquire_owned`, rejects busy rather than queueing and checks closure on both sides of acquisition. Admission precedes pool acquisition, coherent preparation and the final writer reservation.

The blocking operation owns both its permit and writer transaction. Cancelling the IPC waiter cannot detach those resources from native creation. Confirmed restore closes ordinary readiness and launch admission, drains an admitted operation, then closes the pool and continues original snapshot/intent preparation. `Database::close` also closes/drains before pool shutdown. Restart requires the complete maintenance session to be idle, not merely a closed pool: confirmation may still be publishing recovery evidence after pool closure. Restart closes maintenance admission and drops its session guard before invoking Tauri restart.

Ordinary exit closes IPC launch admission through application shutdown state, drains database launch admission, closes/cancels and drains the maintenance session, shuts down synthetic jobs when present, closes the database, then exits. No maintenance session or DB writer reservation is held while waiting for the launch permit. Launch never acquires the maintenance session. A second exit request cannot bypass an unfinished drain. Restart may bypass Tauri exit events on the main thread, but its services/admission are already closed and confirmation has completed.

The ordering is: launch permit -> pool -> writer -> native creation -> rollback/connection release -> permit release. Restore/shutdown: close admission -> drain permit -> drain/complete maintenance as applicable -> close services. Existing pool/job limits are unchanged. Native OS calls cannot be forcibly cancelled or given a guaranteed wall-clock completion deadline; one active worker and no retry/queue bound resource acquisition without pretending to cancel Windows I/O.

## 9. Windows creation behavior

Only explicit `.exe` targets use direct `CreateProcessW`, with non-NULL absolute `lpApplicationName`, separately encoded mutable UTF-16 arguments and explicit CWD. Saved Windows references retain M1.6 lexical grammar. Relative values require a supported saved installation root. Absolute values are not rebased; omitted CWD means the executable's lexical parent. There is no PATH lookup, environment expansion, extension guessing, shell fallback or retry.

Immediately before creation, ordinary file metadata and an attribute-only shared directory handle check observable availability/type/access. The parent token must be unelevated; check failure also refuses execution. Native flags remain `CREATE_NO_WINDOW | CREATE_UNICODE_ENVIRONMENT | EXTENDED_STARTUPINFO_PRESENT`. Windows C/Rust-runtime quoting preserves empty/quoted/backslash/Unicode arguments; the encoded command line must fit 32,767 UTF-16 units including terminator. Custom argument parsers are not certified.

## 10. UI and public errors

Errors distinguish request rejection, resolution failure and native creation failure through stage/code/optional numeric OS code. React renders only fixed concise messages, never backend strings, full paths, arguments or environment. Messages cover missing profile/target/CWD, unsupported context, stale configuration, unavailable database, maintenance/shutdown, access denial, elevation and loader failure. Unknown/lost delivery explicitly reports uncertain outcome and does not retry.

Stale/missing context clears selection, refreshes only the bounded selected-game details and requires another action. A refresh failure directs the user to reopen details. Success says **Launch request sent to Windows.** in an accessible status region and clears after five seconds. Controls retain native keyboard semantics and the editor's existing focus boundary; no indefinitely persistent success toast or gameplay claim is added.

## 11. Lifetime, handles and irreversible point

A newly opened read/write NUL handle is the only inherited handle, supplied to all three standard streams through `STARTUPINFOEXW` and `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`. Scoped ownership releases directory/token/NUL handles, initialized attribute storage and the primary thread handle on success and failure. Production immediately drops the returned process handle and returns only its PID.

Successful `CreateProcessW` is the irreversible point. The writer reservation remains held through that synchronous call. The transaction is read-only and rolls back; no database acknowledgement is committed after creation. Cleanup/reporting failure cannot trigger another creation or silently terminate the child. SQLx queues rollback on an unsuccessful rollback/drop before reuse. PID is diagnostic and reusable, not authority for later attachment or termination. No background waiter, poller or kill-on-close job is introduced. External Windows job policies can still affect child lifetime.

## 14. Security limitations

The executable runs with ordinary user privileges and is not sandboxed. No trust/signature/content-integrity check, adversarial filesystem confinement, executable identity pin or protection against malicious same-user replacement is claimed. Reparses and mapped drives follow Windows resolution; lexical validation and SQLite transactions cannot remove filesystem TOCTOU. Direct same-user database ABA tampering is not prevented.

The child inherits the ordinary parent environment, which may influence runtime/DLL loading or contain secrets. No per-profile environment overrides are added. A selected executable can itself interpret arguments, start other programs or request elevation later. Compromised same-origin frontend/application/OS and privileged attackers remain outside the stated guarantee. Creation proves neither initialization, a visible window, survival nor gameplay. One tested Windows machine does not establish broad compatibility, minimum hardware or release certification.

## 15. Performance observations

Launch adds two bounded indexed selected-profile reads and at most one native blocking worker. It does not alter library browsing queries, row geometry, page/cache sizes, pool size, artwork workers or job limits. It bypasses the frontend browsing request gate, so waiting for creation does not serialize unrelated React details/page requests behind a native call. WAL readers remain available while the short writer reservation prevents cooperating edits; ordinary writes can contend until it ends. Existing five-second SQLite busy and ten-second pool-acquisition policies remain unchanged.

The isolated ordinary-application comparison uses the retained M1.7 ordinary artifact (SHA-256 `9FB7750E79E9C899285A7D5EA8A8BC8408472ADF19451AD14407DB204F393588`) and the final M1.8 ordinary artifact, both schema v4. Two reversed-order passes at 15k/25k preserve exact IDs/rows/counts in all 24 cases, 40 observations per case/artifact. No builds or Rust suites competed during these measurements; ordinary background applications remained uncontrolled.

Results are mixed, not a general launcher speedup. At 15k, first-page query median/p95 changed from 2.691/4.530 ms to 2.681/4.724 ms; deep all-games changed 8.160/11.037 to 8.410/12.036 ms. At 25k, first-page changed 5.937/8.308 to 6.139/7.005 ms; deep all-games changed 8.622/12.176 to 9.387/15.571 ms. The second retained 25k search-position sample improved median 110.748 to 85.486 ms while p95 worsened 144.239 to 192.884 ms. Both search positions are zero for the small match set; they are separate observations, not different SQL. Full faster/worse results remain in ignored `query-comparison/summary.json` rather than selecting only improvements. Existing queries are unchanged and no optimization or budget exception is introduced.

Feature-binary checks pass 18 composed query scenarios and two deep windows at each size. Observed maxima remain 26 mounted rows, six cached pages and one active library request. Ordinary isolation remains empty schema v4, ignores invalid benchmark settings, exposes no synthetic handlers/diagnostics and preserves the frozen source. Native creation timing is not promoted from M1.7's isolated candidate measurements; the production smoke verifies actual behavior rather than claiming a new latency budget. These observations are not numerical performance-budget certification, compositor FPS, physical HDD/lower-memory validation or guarantees against stalled OS I/O. ADR-007 exceptions E1-E5 and all six frozen generator-v1 fixtures remain unchanged.
