# M0.7E — Relationship-heavy and deep-page query cost/benefit investigation

Verification date: 2026-10-27. **M0.7E is complete within the verified synthetic scope; the wider M0 performance gate remains open.** Recommendation: accept the measured query limitation and retain M0.7B production queries.

## Scope and baseline

Initial tree clean at `d966437` on `perf/m0.7E`, merging M0.7D (`04c3976`, PR #11). M0.7B (`9882c24`) and M0.7C (`a07589a`) are ancestors. Reviewed AGENTS, README, PROJECT_STATUS, ROADMAP, PRD performance/grouping requirements, TAS identities/pagination/budgets, DSS identity/storage/query guidance, ADR-004, and the complete M0.7B/C/D evidence. Inspected the actual migration/indexes, SQLx predicates/summary projection/pool, generator/derivatives, frontend criteria generations/request gate/virtualizer/caches and existing query/concurrency tests. Current explicit authorization supersedes historical planning-only wording.

Startup optimization is deliberately deferred. No WPR attempt, privileged trace, WebView refactor, dependency, real import, personal-library access, mod operation, commit, push or subsequent milestone is part of this task. Historical reports remain unchanged.

Current production uses M0.7B's ordered entry-set membership for installed and its exact boolean complement for not-installed. Presence is global to the canonical game, independent of the source filter. A materialized page selects at most 100 canonical IDs in these benchmarks, then projects global source names, membership count, copy count and presence. Four allowlisted orders break ties with canonical ID; null release dates retain SQLite ordering. Literal escaped LIKE is unchanged. Arbitrary OFFSET navigation, six cached pages, one active native request, eight overscan rows per side and title-scoped optional font fallback are preserved.

The two new intermediate recipes select every fifth game at index 1 in canonical-ID order (20%). They add one source membership to each selected game, with one versus four present copies. Their membership and installed-game sets are identical; the second increases copy cardinality without increasing membership/presence. These are deliberately limited hypotheses, **not estimates of real-world prevalence**. Four copies for a minority models a demanding localized multi-version usage pattern; it is not a proposed default.

Both intermediate recipes couple new membership with installed copies. Ownership-only source overlap can add memberships with no additional installation, so even the intermediate distributions should not be called expected averages. Sparse installation controls cover the important many-owned/few-installed direction; no numerical prevalence or frequency ranking is inferred. Twenty percent of 15,000 still means 3,000 games, making four additional copies on each a demanding assumption even though it is much smaller than universal fanout.

The severe recipe adds six memberships and four copies per new membership **for every game**: roughly 7.14 memberships and 24.68 copies per canonical game. Ninety percent of the added copies are marked present; presence therefore rises to 96.45% of canonical games. It combines nearly universal cross-catalog duplication, multiple copies everywhere and almost universal installation. Multi-store overlap and selected parallel versions are supported product use cases, but blanket duplication at this level is a poor default model for a large Windows ownership library. That is a structural plausibility judgment, **not measured population evidence or a numerical probability**. No personal library/provider data was sampled. We cannot establish how many users, games or installations fall into any synthetic distribution.

TAS/DSS distinguish installations from launch/mod profiles: several profiles can refer to an installation. Twenty-four profiles therefore do not automatically imply twenty-four installation records. Future importers must preserve these identities and idempotent source membership rather than generate artificial duplicate copies. This investigation does not validate importer behavior or assume that expected user overlap is zero.

Reference/sparse/dense vary installed fraction; overlap/copies isolate a localized copy increase; fanout supplies an intentionally severe bound. Neither derivative validates real importer cardinalities, long multilingual titles, hundreds of sources, mostly unique artwork, HDD/low-memory behavior or product-wide performance. The source/installation semantics remain valid even for the severe case; low plausibility does not excuse a correctness error.

The additional 25,000-game extreme file was prepared and integrity-checked before narrowing the matrix. It is not timed or used to claim a performance result. The measured extreme remains the existing 15,000-game distribution; reference 25,000 is retained for stress-scale SQL and native validation.

Hardware/OS inventory is saved in `benchmarks/results/m0.7e-environment.json`. Node 26.12.1, pnpm 12.15.0 and Rust/Cargo 1.99.1 Windows MSVC use locked dependencies and optimized release/LTO builds. No new HDD, reduced-RAM, physical-DPI, OS-cold or actual-presentation result is claimed. SQLite retains its four-connection pool, cached statements and configured connection-cache targets; these are configuration, not measured cache occupancy/hit rates.

The benchmark-only CLI opens validated synthetic databases read-only, using locked SQLx 0.9.0 and its bundled SQLite 3.51.3. Python SQLite is used only for fixture backup/generation, integrity checks and index construction. It is not the query timing engine. Actual SQL, bound-criteria descriptions and separate count/page/selection plans are retained in each diagnostic report, along with `dbstat` allocated table/index sizes and every raw timing sample.

Each shape is warmed before collection, strategy order reverses every retained round and dataset order reverses across passes. Every retained group checks exact count and all ten summary fields against the historical strategy, then checks separate bounded-ID projection against the complete page. Count, full-page, sorted-ID selection, projection and pool acquisition are separately timed. The split statements are extra diagnostic queries; **their durations are not additive components of the full-page timer**. SQLx worker delivery, preparation and row decoding are included; this is not SQLite VM-only CPU attribution. Equality/JSON report construction is outside the execution timer.

The original 34 cases cover literal/common/rare/zero-match/Japanese/punctuation searches, source/year, installed/not-installed/all, both directions of title/release sorting, first/deep pages and combined criteria. The new relationship set adds eight source-plus-presence first/deep title/release cases. Every page stays bounded. Deep offsets are based on exact counts. Samples within one process are correlated; nearest-rank p50/p95/max and sample counts describe finite observations, not rare-tail guarantees. OS caches are retained, including preflight hashing. Builds, tests and generation are excluded from timed collection. Normal desktop activity remains uncontrolled.

Native metadata invoke, page invoke, backend filtered-count service, complete page service and pool acquisition use the existing narrow commands. Filtered-count service ends before metadata's additional global-count/source queries, so metadata IPC minus count time is not pure transport. Browser-local target-row arrival and complete overscan-window readiness remain different endpoints. Passive protocol/MutationObserver/geometry reads have overhead; DOM/rAF observations do not measure physical input, compositor presentation or displayed FPS. Independently measured percentiles are never added/subtracted to reconstruct causal totals.

## Bounded candidates and maintenance costs

The new `--strategies relationships` CLI set compares historical pre-M0.7B behavior, current ordered entry sets, **PageMembership** (current count plus historical ordered membership for pages), and **PageCorrelated** (current count plus canonical correlated EXISTS for pages). The two page-only candidates isolate sorted-ID access from count improvements. They are experiments inside the feature-gated diagnostic module, never exposed through IPC. The original `all` and `finalists` sets keep their behavior and scenario counts.

PageMembership is also prepared as a temporary native candidate: only `QueryRequest` page construction selects the historical ordered predicate; counts keep M0.7B. No runtime override, new IPC or production setting is added. Its exact source diff and original query file are retained under ignored results so the experiment can be reproduced and reverted. A prepared candidate is not an adoption decision.

A single covering-index experiment prepares `library_entries(game_id,id)` on new SQLite backup copies of reference/copies/fanout at 15,000. Timed screening pairs indexed/unindexed **reference and copies** in both orders. The fanout indexed backup is preparation only; further extreme index timing is pruned after the representative screen does not establish a worthwhile broad benefit. It tests whether avoiding membership-table lookups changes the correlated-page tradeoff. No original database, production migration or index definition is changed. Same-engine `dbstat` reports 1,200,128 / 1,458,176 additional index bytes for reference/copies. The prepared fanout backup grows by 9,154,560 bytes using Python page-count accounting, without a query-performance claim. Existing freelist reuse can make file growth differ from index allocation.

The index requires an additional B-tree entry per membership and maintenance on insertion, deletion and game-ID reassignment. Installation presence changes alone would not update it. A production adoption would need a migration/backfill, extra disk during upgrades, changed write costs and planner regression coverage. No measured production write-cost claim is inferred from index byte size. Page-only predicates add another query-shape contract and repeat canonical membership probes; they do not add importer-maintained state. Planner choices remain specific to the bundled engine and data distribution.

The existing read-only benchmark validation expects the current migration version. A production index migration also entails upgraded disposable benchmark fixtures and preserved schema-1 artifacts for before/after comparisons. The screen deliberately adds an index to new schema-1 backups; it does not validate an application upgrade, migration duration, write amplification or a replacement for the existing game-membership index. Those costs cannot be called zero simply because experimental DDL is short.

Reusable count caching, denormalized presence flags and maintained sorted-ID/rank structures would introduce revision/invalidation contracts across external connections, membership/copy/presence changes, deletes, rollback and restart. Keyset-only navigation would lose arbitrary scrollbar jumps. Reversing a tail query using an exact count needs correct residual length, reversed null/tie ordering and one snapshot; it still constructs membership sets and does not solve middle jumps. These mechanisms are not assumed worthwhile merely because a provisional target is missed. FTS would alter the already validated literal-search problem and does not address relationship cardinality. Pool/worker/default changes do not follow from a low acquisition timer.

Alternative bounded summary aggregation is considered but not implemented: representative isolated projection is small, while a fused join must avoid multiplying membership counts by copies and preserve sorted/distinct global source names, zero-copy memberships and presence semantics. The severe case increases projection work, but selection remains much larger. These observations do not justify another aggregation candidate. They are not an additive decomposition or a formal upper bound on every possible optimizer interaction.

Existing plans already use the canonical title/release and installation indexes. Hard-coded `INDEXED BY` hints would add plan coupling without an established missing-index mechanism; no hint is shipped. A reverse-tail scheme that recounts inside each page request can add the count work that ordinary scrolling currently avoids. A reusable total or sparse anchor map instead needs a library revision/snapshot contract; stale reverse offsets can silently select the wrong full-length window. These are rejected design alternatives, not measured optimizations.

## Query-plan interpretation

The clean 15,000-game reference capture confirms these distinct mechanisms (complete SQL/plans remain in raw JSON):

```text
Current title ID selection:
SCAN g USING COVERING INDEX ix_games_sort
LIST SUBQUERY: SEARCH e USING INDEX sqlite_autoindex_library_entries_1 (id=?)
  LIST SUBQUERY: SCAN i USING COVERING INDEX ix_installations_entry
CREATE BLOOM FILTER (entry and game sets)

PageMembership:
SCAN g USING COVERING INDEX ix_games_sort
LIST SUBQUERY: SCAN e
  SEARCH i EXISTS USING COVERING INDEX ix_installations_entry

PageCorrelated:
SCAN g USING COVERING INDEX ix_games_sort
CORRELATED SCALAR SUBQUERY
  SEARCH e USING INDEX ix_library_game (game_id=?)
  SEARCH i USING COVERING INDEX ix_installations_entry
```

Current count scans the canonical ID index and constructs the same nested membership sets. Historical count instead drives canonical ID probes from entry membership. Historical unordered installed pages also use a temporary sort over the matching canonical set. `IS TRUE` allows current and PageMembership ordered scans; release ordering uses the existing release index when selected by the planner. Source/year/text composition can choose other plans and temporary sorting, so this is not a guarantee for every criterion.

The current query pays statement-local membership construction even for a short first page, then scans ordered candidates up to the requested matching offset. Correlated selection can stop after finding enough first-page matches, but repeats membership/copy probes for candidates skipped on deep pages. The covering experiment can remove an entry-table lookup without removing those probes. These mechanisms follow from SQL and captured plans; the timing comparisons test their practical effect. No VM-opcode/CPU profile or exact SQLite cache hit/miss attribution is claimed.

Full-page plans materialize the bounded ID page, look up each game, and perform indexed global summaries only for that page. Source-name DISTINCT and the final sort use bounded temporary structures. Summary work increases with the relationships of those bounded games; it is not a full-library aggregate. The metadata command separately calls the four-table `counts()` query to retrieve `library_total`, plus source options, after its filtered-count timer ends. This repeated global metadata work is acknowledged rather than labelled IPC transport. A narrower metadata query could avoid unnecessary table counts, but needs its own measured absolute benefit; it does not remove page membership/offset work.

## Covering-index screen and stop rule

The completed screen comprises **4,032 exact diagnostic groups**: two datasets × indexed/unindexed × two process orders × 42 cases × four strategies × three rounds. Each dataset/strategy/shape has n=6; p95 equals maximum and is not a rare-tail estimate. `m0.7e-index-paired` retains the first four completed reports; `m0.7e-index-repeat` reverses those pairs. The partially started unindexed-fanout screen is excluded after pruning the index candidate, with a stop-rule marker; no timed indexed-fanout result is claimed.
