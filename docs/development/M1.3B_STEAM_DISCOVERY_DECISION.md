# M1.3B — Steam discovery security and usability decision

Date: 2026-10-28. Status: **Proposed decision; explicit user approval required for the policy change below.** This review changes no accepted security contract or production behavior. M1.3 remains incomplete; M1.3A did not establish a production reader.

## Recommendation

Prefer explicit user-selected Steam installation/library roots with narrowly scoped metadata enumeration **only if the user accepts threat model B below**. It is a proportionate candidate for a normal, non-elevated local desktop application, not a demonstrated implementation. Root approval must authorize a restricted namespace operation rather than promise that every readable object has exclusively in-root provenance. Malicious metadata remains in scope; deliberate filesystem manipulation by another same-user process to substitute sensitive objects is outside that model's confidentiality guarantee.

Until that change is explicitly approved, **defer local Steam discovery under the existing contract**. Do not resume M1.3, substitute a weaker path-based scanner, or treat this recommendation as approval. If strong isolation against hostile same-user filesystem substitution remains required, the current evidence does not justify further scanner implementation for this limited benefit. This is not proof that stronger confinement is impossible.

Do not make individual manifest selection the default. It sacrifices the main convenience benefit without resolving object provenance or selection/open races. Later optional account connections may address a different need, but are neither implemented nor a credentials-free offline substitute.

M1.2 section 8 requires native identity, handle-relative/no-reparse access, rejection of hard-linked metadata whose provenance cannot be confined, and compatibility with Steam's concurrent read/write/delete access. M1.3A states the stronger property as no content outside the approved native directory identity being opened for reading, including attacks by a local actor who can rename/replace entries. Model B changes that property and its attacker assumptions; it is not merely an implementation clarification.

The working tree already contained three untracked M1.3/M1.3A report/probe files at the start of this review. They are evidence inputs and remain unchanged. Current production Rust source and capabilities contain no Steam discovery endpoint. Schema v2 and existing application behavior remain unchanged.

## Separate security goals

| Goal | Required boundary and qualification |
| --- | --- |
| Hostile metadata cannot request arbitrary reads | Backend chooses fixed relative directory/leaf operations. AppID, title, `installdir`, includes and other manifest fields never become filesystem paths. A folder-index path is an untrusted candidate needing a separate native selection and grant. |
| No credential/session/account access | No operations targeting login/config/userdata/auth stores, cookies, tokens, account registry values, processes or binary caches. This prevents intentional credential-store access; under B it cannot promise that an allowed leaf never contains sensitive bytes planted there by another process. |
| Deliberate authorization | Native selection, disclosure of the limited scope, then confirmation bound to the opened root identity. A frontend path or boolean is not authority. No scan on startup or merely because Steam is detected. |
| Read-only behavior | Existing-file reads and directory listing only; no Steam writes, repairs, attribute changes, locks intended to block Steam, execution or database import. Ordinary OS access-time bookkeeping is not a promised byte-for-byte disk invariance property. |
| No unrestricted traversal | Only the selected root's direct `steamapps` directory and allowlisted metadata leaves; no recursive walk, arbitrary ancestor fallback or automatic additional-root grant. |
| Concurrent-process behavior | Ordinary Steam updates must yield bounded retries, warnings or incomplete results. Protection against an intentionally hostile same-user filesystem writer must be chosen explicitly, not inferred from a successful ordinary race test. |
| Hard-link authorization | Decide whether authority concerns accessible names or exclusive object provenance. Hard links are aliases to one object, not reparse traversal. Neither a filename nor parser validation establishes where that object originated. |

## Explicit threat-model alternatives

| Model | Attacks in scope | Hard links and approval meaning | Assessment |
| --- | --- | --- | --- |
| **A — retain existing confinement** | Malicious metadata and deliberate concurrent local rename/replacement/link attacks, including a same-user process attempting to redirect reads. Trusted OS/kernel/filesystem; privileged compromise excluded. | Approval does not authorize externally aliased metadata of uncertain provenance. Prevent prohibited read-capable opens, not just reject bytes after opening. | Current contract. No complete native argument or production-reader tests establish it. Preserve the stop. |
| **B — restricted local metadata capability** | Malicious metadata, malformed names/paths, unsupported objects, accidental misconfiguration and ordinary concurrent Steam changes. Enforce native no-reparse access and identity rules. Deliberate same-user planting/copying/linking of sensitive objects or attacking the consent/open boundary is outside the confidentiality guarantee. Process injection, compromised application/OS and privileged attackers also excluded. | Approval authorizes eligible names under the selected native root; it does not establish exclusive provenance of the objects behind those names. An object with another hard-link name elsewhere falls within that namespace authority in principle. Reject observed multiple links as conservative hardening, not as proof of A. | Recommended only with explicit approval and a separate native feasibility gate. Not a sandbox against other same-user applications. |
| **C — stronger isolated reader** | Keep A's adversarial goal and investigate a broker/OS-enforced capability or isolation boundary. No assumption that merely adding a helper process provides one. | Requires an independently justified object/consent policy; sandboxing alone does not prove hard-link provenance. | Separate architecture work, substantial cost, no established design. Not proportionate to this preview on current evidence. |

Model B still requires rejecting static junctions, symbolic links, unsupported objects and detected replacements. Excluding a hostile same-user attacker does not justify unchecked path opens or accepting arbitrary metadata paths. Conversely, sharing a Windows user account is not a proof of safety: Game Manager could become a confused deputy even if another process already has access. The exclusion is an explicit product risk choice, not a claim that all such attacks are harmless.

**Hard-link consequence:** rejecting `NumberOfLinks > 1` is useful but cannot prove a file was never linked/copied from elsewhere, or prevent an adversary from changing links around checks. A read-capable open followed by link-count rejection already fails A's stronger open prohibition. Model B permits such an open through an eligible name but requires rejecting an observed multiple-link file before reading its content. A future design may inspect attributes first; reopening/upgrading access must not be represented as an atomic provenance proof. No global hard-link search is proposed.

## Workflow options and practical utility

| Option | Expected usability and coverage | Security and maintenance cost | Disposition |
| --- | --- | --- | --- |
| Explicit installation/library root selection | One selection/confirmation per root, potentially hundreds of manifest records per root. No login, Steam launch or internet needed. Unsupported linked/network roots are refused with an explanation; a separate ordinary local library can be selected deliberately. | Native acquisition, identity, no-reparse traversal, bounded enumeration, concurrent updates, privacy, cancellation and OS/filesystem testing. Moderate ongoing cost if B is accepted; A remains unestablished. | Best fit for the stated convenience goal, conditional on B and native verification. |
| Individual metadata-file selection | Native multi-select can reduce clicks, so one confirmation per file is not inherently required. Still makes users locate/filter hundreds of manifests across libraries and repeat selection on refresh; no automatic discovery of new leaves. | Removes directory enumeration/index traversal, but retains selection/open identity, reparse, hard-link, size/type, concurrency and parser issues. A picker returning paths is not an object capability. | Possible separately designed diagnostic/manual workflow; poor default and no automatic escape from A. Not implemented. |
| Defer local scanning; consider later optional authorized account connections | Preserves manual local use today. Later account inventory could cover uninstalled games where the provider permits it; requires network, explicit account context and an approved authorization method. | Avoids local-reader cost now, adds future auth/key handling, privacy, permissions, rate limits, availability and provider API maintenance. No guaranteed suitable connection method has been selected. | Default while A remains binding; not permission to begin account work. |

The first preview offers **client-reported installed applications**, not a complete owned library. It cannot verify payloads, launchability, current account, family access or entitlement. It may include tools/soundtracks and stale manifests; it supplies useful AppIDs and optional names without inspecting game content. Valve independently distinguishes installed status from ownership in [ISteamApps](https://partner.steamgames.com/doc/api/ISteamApps#BIsAppInstalled). This source supports the distinction, not the private manifest format.

This can meaningfully reduce manual catalog entry for many installed apps. A preview alone saves no persistent entry work until a separately authorized importer exists; it also cannot automatically select executables for launching. No user measurement establishes adoption or time saved. For a largely uninstalled 12,320-game library, coverage could be a small fraction and must not be marketed as full Steam-library import. [GetOwnedGames](https://partner.steamgames.com/doc/webapi/IPlayerService#GetOwnedGames) is a separate key-based, visibility-dependent API, not approval to extract local Steam sessions.

Assessment: that limited benefit justifies a **small, capped feasibility slice under B**, not a bespoke high-assurance filesystem sandbox. If the real priority is complete account inventory, or B is unacceptable, defer local scanning. Manual entry remains available and offline core functionality stays independent of future accounts. Steam's established integration priority is unchanged; deferral does not authorize skipping to another storefront or milestone.

## Auditable root access design proposed under B

This is an access policy and exit checklist, not a scanner implementation or approval to build one.

1. **Consent and acquisition.** Run unelevated. User chooses an installation root or library root with a native picker, receiving an untrusted selection request. Before any metadata content read, Rust acquires directory handles through a reviewed local-volume anchor/component procedure, validates the opened volume/directory, presents that acquired root for confirmation and binds an in-memory grant to it. Display the selected location and the scope: installed metadata only, ownership unknown, no account files/game payloads, cancel available. A picker path alone never binds identity. Do not use registry auto-detection in the first slice; no prior grant, ancestor search, fallback root or persisted authorization.
2. **Native identity.** Retain root and `steamapps` handles for the session, with volume identity plus file identity. Identity is attached to live handles; IDs are not permanent security tokens across deletion/restart. Reject drive-relative, UNC/mapped/substituted-drive, device namespace, remote, reparse-backed and unsupported filesystem roots. Initial feasibility scope is local fixed NTFS only, pending proof of volume/device resolution. Drive letters or filesystem name alone are insufficient. Acquiring a trusted local anchor and refusing redirected ancestors is still an engineering gate, even under B.
3. **Controlled traversal.** Acquire the literal single child `steamapps` relative to the held root, enumerate that directory only, and open accepted direct leaves relative to its handle. Reject reparses at root ancestors, root, `steamapps` and leaves using a reviewed no-reparse native operation. Do not traverse `common`, `music`, `workshop`, `shadercache`, `userdata`, `config`, `appcache`, caches or game directories. Enumeration may observe other entry names, but must not open their contents or descend into them.
4. **Exact names.** Accept only ASCII `appmanifest_([1-9][0-9]{0,9})\.acf`, anchored to the entire enumerated leaf name, with parsed AppID in `1..=4294967295`. Require exact lowercase literal prefix/suffix and filename/body AppID agreement. Reject leading zeros, signs, Unicode lookalikes, separators, colons/ADS, traversal, trailing dots/spaces, extra suffixes and alternative short-name interpretations. No glob expansion or path normalization can widen this allowlist. Reject ambiguous case/alias entries rather than select one silently. Compatibility exclusions produce warnings.
5. **Optional index.** The only other content leaf is literal `steamapps/libraryfolders.vdf`, when the user has approved its metadata scope for an installation root. Parse within M1.2 limits. Report library candidates without probing/statting/opening them; a candidate can prefill a subsequent native selection but cannot grant itself authority. Each additional root goes through the same acquisition and confirmation. No recursive library-index graph walk. Omit index reading from the first feasibility slice if unnecessary to establish the root policy.
6. **No data-driven I/O.** Manifest fields are parsed values only. `installdir` may be validated for display; it never triggers existence checks, directory opens or executable searches. Unknown fields are discarded, not logged/returned. Includes/directives are rejected. Folder-index candidate text cannot become an open request without new user authorization. AppIDs only validate records; no network lookup is allowed.
7. **Conservative object handling.** Existing regular disk files only, no directory/device/pipe/remote/reparse leaves; reject delete-pending, unsupported attribute combinations and observed link counts other than one. Pin the opened file handle for validation and reads. Never silently rebind a root when a path now identifies a replacement. A detected root/`steamapps` replacement invalidates the grant and requires a fresh selection. Relative access must continue to refer to held objects rather than reconstructed absolute paths. A hostile rename escaping detection is not covered by B's confidentiality promise; stable reads do not prove an unchanged namespace history.
8. **Bounded reads and changes.** Use existing-file opens with only required read/attribute/directory rights, compatible read/write/delete sharing, no mutation access and no elevation. Reuse M1.2 bounds: 64 KiB manifest, 2 MiB index, 32 roots, parser depth 16, token 4,096 bytes and 32,768 pairs. Keep proposed session bounds: one active scan, 25,000 records, 128 MiB aggregate input, 100-row pages. Also cap directory entries examined, attempts and elapsed work; a directory full of nonmatching names must not bypass budgets. Charge retries and both byte observations to I/O budgets. Enforce streaming byte limits even if initial size is small. Compare identity/size/time and two bounded byte observations; at most one retry, then warning/incomplete. Equal observations are not an atomic Steam snapshot or adversarial ABA defense. No absence/deletion inference from partial/cancelled work.
9. **Backend/IPC/privacy.** Rust owns handles, grants, parsing and bounded session state. Future typed operations may start an authorized session, fetch a bounded page and cancel using opaque, window/session-bound identifiers. No frontend-supplied arbitrary read path, raw handle, arbitrary SQL or raw-file endpoint. Return only validated AppID/name, qualified installation evidence and bounded structured warnings. No LastOwner/account IDs, raw VDF/ACF, unknown values or full paths in logs/events. Escape title text in presentation. Path context is local consent UI only. No asset-protocol exposure of Steam directories. No credentials, network, SDK/internal client calls, executable reads or launches.
10. **Cancellation and cleanup.** Check cancellation between enumeration batches, opens, bounded read chunks and parsing stages; stop accepting new work immediately. Bound worker/handle counts and invalidate session IDs on cancel/close. Release all handles/buffers on success, failure, panic/unwind and window closure using owned native resources. Blocking native calls need a reviewed cancellable I/O or bounded-worker strategy; a timeout alone does not terminate I/O. Never leak abandoned scans into an unlimited worker pool. Do not announce cleanup finished until outstanding operations have completed and resources are released. No persistent catalog writes or grant persistence in this slice.

A direct Windows binding/dependency, if needed, requires separately reviewed scope; this review adds none. No API experiment can upgrade B into A without a new argument and approval.

## Required native verification and maintenance cost

Use only disposable synthetic roots and sentinels, never personal Steam data or real installations. A production candidate must pass these gates before any app-facing discovery endpoint:

| Test family | Required evidence |
| --- | --- |
| Consent and identity | No content read before confirmation; cancelled/forged/expired/cross-window grants denied; each extra root separately authorized; replacement before/after confirmation rejected; duplicates bound to native identities. |
| Access allowlist | Instrument attempted opens and reads, not just output rows. Assert exact allowed leaves and no payload/account/cache/executable access. Test malformed and overflow IDs, case/short-name aliases, ADS, namespaces, separators, Unicode, index-supplied hostile paths, includes and unsupported roots. |
| Reparse and hard links | Root ancestor/root/`steamapps`/leaf junctions, symlinks and other reparse tags refused; static multiple-link metadata rejected before content reads. Required symlink coverage needs a capable test environment; unavailable fixtures are a gap, not a pass. Test unlocked as well as exclusively held synthetic outside sentinels. Distinguish metadata-only opens, read-capable opens and content reads. |
| Concurrent changes | Replacement/rename/reparse conversion at acquisition, enumeration, open and read boundaries; ordinary Steam-style atomic replacements and in-place truncation/growth. Demonstrate no path-based fallback/rebinding, bounded retries and incomplete reporting. Deliberate hostile schedules are defense-in-depth evidence under B, never proof of A or a reason to waive an allowlist escape. |
| Bounds and cleanup | Huge/nonmatching directories, oversized/growing files, duplicates, malformed parser inputs, inaccessible/offline roots, cancellation at every stage and repeated failure loops. Measure handles, workers, memory and cleanup completion; no Steam-blocking locks. |
| Isolation and scale | No Steam or catalog writes; verify narrow command/capability surface and absence of raw content/log leaks. Before preview integration, test bounded paging and the applicable 500/2,000/5,000/12,320/15,000/25,000 synthetic scales on SSD/HDD and lower-memory configurations. No benchmark target is assumed achieved. |

Maintain a small centralized access module with explicit flag rationale, owned handles, reviewed unsafe FFI, error classification and tests against the supported Windows/NTFS matrix. Re-run targeted security tests after Windows-binding, filesystem-access, picker or supported-OS changes; retain Steam-format fixtures for parser changes. Native symlink privileges, CI coverage, read auditing, cancellation and share compatibility are continuing costs, beyond parser maintenance. No numerical effort estimate is substantiated. Do not expand into caches, account hints, automatic watchers or a general filesystem framework to improve coverage.

## Proposed architectural decision — approval text

The following is a concrete proposal for the user to accept or reject; **it has not been accepted**:

> For credentials-free local Steam installed-app discovery only, replace M1.2 section 8/M1.3A's strong object-provenance confinement requirement with threat model B in this review. Approval binds a restricted metadata namespace capability to a live native root identity. It does not certify exclusive in-root provenance or protect confidentiality against deliberate sensitive-file substitution by another same-user process. Objects accessible through eligible names are within that authority even if they have aliases elsewhere; observed multiple hard links must nevertheless be rejected before content reads as hardening. No credential/account stores are targeted, but absolute exclusion of sensitive bytes planted at eligible names is not promised. Retain explicit consent, native no-reparse acquisition/access, read-only operations, exact allowlists, no manifest-derived I/O, typed IPC, bounded reads, privacy, cancellation and fail-closed handling of unsupported cases. This exception grants no authority for mod deployment, account access, payload traversal or other integrations.

Acceptance must be explicit about **both** the same-user attacker exclusion and the hard-link/sensitive-byte limitation. Ordinary root selection at runtime is not architectural policy approval. Following approval, record an accepted ADR and the precise superseded requirements with cross-references; preserve historical stop reports and all unrelated security rules. Do not mark the old guarantee demonstrated. If the user retains A, record deferral instead of adding a warning to a weaker scanner.

## Recommended next slice and stop boundary

**Now:** deliver this decision and stop. No milestone is started by it.

**Only after explicit policy approval and separate engineering authorization:** build an isolated Rust native access candidate over disposable fixtures, initially one selected synthetic library root, its `steamapps` directory and exact bounded manifest leaves. No production registration, frontend preview, index-driven expansion, importer, migration, account authentication or real Steam access. Resolve root acquisition/no-reparse API support, identity, hard-link handling and cancellation; produce the native access/test evidence above. If that remains disproportionate or fails the chosen contract, stop and defer. Passing that gate would justify a separate request to resume M1.3, not complete it automatically.

**Without approval, or if full ownership inventory is the necessary benefit:** defer local scanning. Later optional account integration needs its own feasibility/security/product decision. Preserve manual offline workflows and existing integration priorities.
