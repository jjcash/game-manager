## Query investigation and candidate method

`library-bench query-diagnose` uses the locked SQLx/bundled SQLite engine, actual production builders and unchanged bound arguments. It captures SQL and `EXPLAIN QUERY PLAN` separately for count, complete page and ID selection. The criteria are synthetic and recorded in each request; SQL values remain bound. The parameter order is escaped LIKE text, source ID, inclusive ISO year bounds when present, then limit/offset. No personal query text is logged or accepted through new IPC.

Each shape is warmed once, then candidate order alternates forward/reverse on each retained round. Timers isolate acquisition, count execution, full-page execution, sorted ID selection and projection of those bounded IDs. Split selection/projection are extra diagnostic queries, not additive components of the separately timed full statement. Execution includes SQLx preparation/worker delivery/decoding. Pool waits and native IPC remain separate instruments. Every candidate must match the baseline count and all ten summary columns; split projection must match the complete statement too.

The diagnostic execution timer ends at raw-row delivery; typed equality checks/JSON conversion run outside it. Its extra split queries and candidate prepared statements change cache pressure compared with the ordinary typed service. Do not interchange these distributions with the original 14-case service driver or native IPC. Acquisition is sampled once per diagnostic count/page/split group; native probes separately record each real count and page acquisition. Percentiles in diagnostics/native summaries use nearest rank; the original CLI's `medianMs` averages the central pair.

The 34 scenarios include common/rare/zero-match/Unicode/punctuation searches, source and inclusive years, all/installed/not-installed × both title/release directions × first/tail pages, and fully composed installed/not-installed criteria. Rows stay bounded at 100. No complete library is loaded into frontend state.

Exploratory results are retained in `m0.7b-exploration` and `m0.7b-index-exploration`. The initial exploratory Unicode case had an encoding error in the new benchmark source; it was corrected to Rust Unicode escapes and the final matrix uses the intended Japanese term. Those preliminary Unicode observations are excluded. New diagnostic integration tests verify every strategy and split projection against the edge-case fixture.

Compared strategies:

- Historical canonical membership with entry-to-copy `EXISTS`.
- Installation-driven joins, with and without a boolean membership boundary that allows indexed canonical ordering.
- Correlated canonical `EXISTS`: improves selective combinations but substantially regresses broad installed counts; not a general replacement.
- Ordered historical membership.
- Entry-ID set membership, with and without ordered canonical membership.
- Two isolated covering-index experiments: `library_entries(game_id,id)` and `library_entries(source_id,game_id,id)`. SQLite's backup API created new disposable copies, preserving original datasets/migration history. Python SQLite 3.50.4 performed backup/index creation only; all query comparisons used SQLx's bundled engine. No production index or migration is implied by these experiments.

Exact filtered counts already run once per frontend criteria/refresh generation; page retrieval does not repeat them. Sort changes currently create another generation. A reusable cross-generation count cache would need a real library revision/invalidation contract, including external-connection writes, membership/presence changes, rollback and restart. The prototype has no such production writer/revision contract. A cache is not justified merely to avoid a now-cheaper count, and none is introduced. M0.4's literal LIKE/FTS5 trigram findings remain applicable: short/punctuation/Unicode semantics and common-term costs preclude treating FTS as a drop-in optimization. No FTS change is made.

## Final implementation and plans

Selected the ordered entry-ID set predicate for the full verification run:

```sql
(g.id IN (
  SELECT e.game_id FROM library_entries e
  WHERE e.id IN (
    SELECT i.entry_id FROM game_installations i
    WHERE i.detection_state='present'
  )
)) IS TRUE
```

Installed uses this predicate; not-installed negates the entire boolean. Canonical and relationship IDs are NOT NULL, so the complement retains the original semantics. Presence is independent of the separate source predicate. Inner membership eliminates duplicate installation IDs/entries naturally, and the outer query still returns canonical games. Search, inclusive dates, four order clauses, bounded materialized pages and global summary projection are unchanged.

The existing `(entry_id,detection_state)` index covers scanning present entry IDs. SQLite materializes this entry set and probes entries by their unique ID in set order, rather than performing an indexed presence probe for every full entry row. The boolean boundary permits canonical sort-index scans instead of turning installed membership into a game-primary-key driving loop followed by a full-match sort. These are measured choices for bundled SQLite **3.51.3**, not guarantees about every future planner version.

Both experimental covering indexes add roughly a megabyte at 15,000, and their incremental gains are mixed. The selected index-free shape improves broad presence costs more directly. No schema/index/constraint, WAL/synchronous/busy-timeout/pool, job scheduler, frontend or artwork policy changes. There is no extra insert/update/delete maintenance, revision state, startup rebuild or crash recovery work. Database/index file sizes remain unchanged; ephemeral membership sets and page materialization remain SQLite query-local work. Future imports still require bounded transactions and deliberate cross-request revision/snapshot behavior, as before.

Actual installed/title-ascending ID-selection plans (the complete SQL and every other plan remain in raw diagnostic JSON):

```text
Baseline:
SEARCH g USING INDEX sqlite_autoindex_games_1 (id=?)
LIST SUBQUERY 2
SCAN e
SEARCH i EXISTS USING COVERING INDEX ix_installations_entry (entry_id=? AND detection_state=?)
CREATE BLOOM FILTER
USE TEMP B-TREE FOR ORDER BY

Selected:
SCAN g USING COVERING INDEX ix_games_sort
LIST SUBQUERY 2
SEARCH e USING INDEX sqlite_autoindex_library_entries_1 (id=?)
LIST SUBQUERY 1
SCAN i USING COVERING INDEX ix_installations_entry
CREATE BLOOM FILTER
CREATE BLOOM FILTER
```

Installed counts change from game-ID probes to a covering canonical ID-index scan with the same nested membership sets. Release pages use `ix_games_release` in either direction where appropriate. Source/year/search combinations can still select another plan and use temporary sorting; the optimization does not assert that every criteria combination avoids sorting. The final outer sort is bounded by the materialized page, and source-name DISTINCT remains bounded to those games. The summary projection's correlated joins are intentionally retained after the page limit.

Work still grows with data: the present-entry set scans installations, looks up present memberships and constructs canonical membership; ordered pages scan canonical IDs up to the requested offset/filter matches. Source sets grow with that source's entries; literal substring matching still scans candidate titles. Deep OFFSET remains linear, supporting arbitrary virtualizer jumps without introducing cursor/revision machinery. No constant-time or library-size-independent latency is claimed.

The fixtures contain 15,000 games / 17,143 entries / 10,233 installations (8,994 distinct present entries), and 25,000 / 28,572 / 17,054 (14,988 distinct present entries). This favors scanning installations rather than probing every membership. Many more copies per entry, a very different installed fraction or future real-import source distributions can change that tradeoff; do not extrapolate this result without those fixtures. SQLite alone maintains existing indexes under writes; no denormalized presence flag or synchronization trigger is introduced.

## Correctness, concurrency and production costs

The new tests cover multiple present copies on a single entry, missing/unknown/present transitions, source combinations, global presence across source memberships, search/count/window equality, reassignment/deletion and page boundaries. It does not claim that separate IPC count/page statements share one cross-request snapshot.
