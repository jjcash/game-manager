## Trusted source and public-repository boundary

This is a **public, personally owned repository**, confirmed read-only through GitHub. GitHub warns that public self-hosted runners can execute hostile PR code and recommends almost never using them. Environment approval does not isolate execution. See [GitHub secure-use guidance](https://docs.github.com/en/actions/reference/security/secure-use). Standard-user permissions protect privilege boundaries but do not make malicious same-user code safe.

The proposal is therefore a supervised, disposable CI VM, never an always-online developer machine. Before runner registration, require approval for **all outside-collaborator fork workflow runs** in repository Actions settings. Review the exact current workflow revision and all executed source/dependency changes before approving any external run. Do not approve an external workflow for this runner. A fork can edit workflow conditions or omit an environment; labels and checks inside mutable YAML are not an authorization boundary.

The hosted job's final policy step allows only this repository's current M1.7 branch, same-repository `ci/native/` PR branches, pushes to `main`, or manual runs on `main`/those reviewed branches. It fails for forks and other refs **after** ordinary hosted checks provide feedback. The native job has no source-based skip-success path: its hosted prerequisite fails on unsupported sources. Transfer reviewed contributions to a maintainer-controlled `ci/native/` branch for native validation; require a new reviewed run after every change. Restrict writes to those branches to trusted maintainers under a separately authorized policy. Retire the temporary M1.7 branch exception after PR #22 merges.

Before making any runner available, create `m17-native-tests` with a maintainer required reviewer, no protection-rule bypass, no secrets, and selected deployment branch rules `main`, `ci/native/*`, the temporary M1.7 branch, and `refs/pull/*/merge`. The latter allows PR merge refs; it does not approve fork code. Enable prevent-self-review when a separate reviewer is available; a sole maintainer must still explicitly inspect the full revision before approval. GitHub matches environment branch rules against the event ref; see [environment protection semantics](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments).

Keep the VM offline until the intended run has passed hosted checks, its exact merge/head SHA has been reviewed, and its environment approval is ready. Check that no other approved jobs target this runner. Register a fresh one-job ephemeral runner, supervise the assignment, and reset it afterward. New workflow files or changes removing the trust/environment gates require explicit review. Cancel and destroy the VM on an unexpected assignment. This depends on repository-wide fork approval and trusted writers; the job's environment alone cannot enforce those controls for other workflows.

Personal repositories do not provide organization runner-group workflow restrictions. If unattended operation or stronger server-enforced workflow routing is needed, stop and separately design an organization runner group restricted to this repository and selected trusted workflow refs, or a private control repository. Do not silently deploy either. A future group must restrict actual workflows, not merely labels; see [runner access controls](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/manage-access). Until the supervised controls are accepted and verified, runner deployment remains blocked.

## Credentials, isolation and cleanup

Keep registration/admin credentials on the control machine; only the short-lived registration token enters the disposable guest for registration. Do not bake registered runner credentials into the base snapshot or store tokens in Git, reusable scripts, shell history, logs, screenshots or artifacts. Treat runner credential/config files and the job's short-lived read-only `GITHUB_TOKEN` as exposed to executed code. `contents: read` and `persist-credentials: false` remain; no PAT, SSH key, signing key, cloud credentials, repository/environment secrets or personal accounts belong in the VM. Snapshot before registration, after removing maintenance credentials.

Disable host shared folders/clipboard, drive redirection and access to developer/LAN services or cloud metadata. Allow outbound access only for the runner/GitHub and required Rust, Node and pnpm dependency endpoints; no inbound listener is needed for the runner. Use one isolated VM per run and never share writable Cargo caches, build outputs or user profiles across trust boundaries. No self-hosted dependency cache is added by this proposal.

Normal tests retain their TempDir/ACL cleanup and bounded child waits/watchdogs. The workflow adds no broad process kills, kill-on-close job or deletion of uncertain paths; child-survival assertions must stay meaningful. Do not assume a successful or canceled Actions job removed all descendants or that an ephemeral registration erases the disk. After success, failure, cancellation, timeout, crash or disconnection, a trusted operator/control-plane process outside the guest must collect reviewed logs, stop the VM, remove any surviving registration and revert its **entire disposable disk** to the clean unregistered snapshot or rebuild it. Never reuse a failed VM after merely cleaning the checkout. Suspicious activity requires fresh-image rebuild and rotation/revocation of any exposed credentials. Refresh and revalidate the clean image for OS/toolchain/runner updates. Do not add a guest cleanup script that can race children or falsely certify guest integrity.

Retain external runner diagnostic logs and Actions run/job URLs, event revision, OS/build, tool versions, token diagnostics, all 12 outer results and exact handle recovery before reset. Preserve failure logs as failures. Avoid archiving entire scratch directories or process environments that could contain credentials. Registration is ephemeral, VM reset is external, and neither is implemented here.
