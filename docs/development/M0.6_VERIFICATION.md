# M0.6 — Synthetic background load and responsiveness

Verification date: 2026-10-26 (local reference system date). This report covers synthetic background work only. M0.7, real importing, providers, personal files and mod management are outside this change. No commit or push was performed.

## Baseline and architecture

Reviewed AGENTS, README, PROJECT_STATUS, ROADMAP, relevant PRD/TAS/DSS and ADR-004 sections, M0.3/M0.4/M0.5 reports, storage/IPC/artwork/frontend/benchmark code. The implementation branch is `feat/m0.6-background-load`, based on merged M0.5 `da431f3`. M0.5 implementation is `fc75946`. The initial branch was still M0.4; the user's explicit M0.5 baseline and subsequent merge were incorporated before implementation. The existing library query predicates, indexes, schema migration, row identity, page gate and artwork cache policy are preserved.

Rust owns the scheduler, synthetic data, filesystem and SQL. React receives typed snapshots and renders controls. The `benchmarks` Cargo feature must be compiled and `GAME_MANAGER_SYNTHETIC_ROOT` explicitly selected before the scheduler exists. Only that configuration grants the main window the three narrow commands `synthetic_start`, `synthetic_list`, `synthetic_cancel` through a dynamic Tauri capability. No path, SQL or command execution arguments are accepted. Ordinary native builds omit the job module, handlers and scheduler initialization; they ignore all new benchmark environment variables. No default capability grants job access. Frontend controls appear only when Rust reports `syntheticJobs: true`.

Request flow: validated predefined request → bounded admission → synthetic ledger reservation → Tokio job slot → cancellable shared resource permit → `spawn_blocking` parsing/hashing/optional resize → release CPU permit → optional short SQL transaction → bounded progress snapshot → yield → next batch. Foreground SQL enters an independent activity/timing guard and never waits for the CPU semaphore. Artwork and jobs do not share the frontend's one-request library gate.

States: `queued → running → finalizing → completed/failed/cancelled`; cancellation records `cancelRequested` first. A queued job can cancel before doing any work. `finalizing` means worker/transaction cleanup and terminal checkpointing are in progress; cancellation is no longer accepted there. Terminal status is published after cleanup and slot release. On restart, persisted in-flight states become `interrupted`; there is no automatic replay. A new request creates a new job ID. A failed/cancelled partial import is never shown as completed.

## Bounds and scheduling

| Resource | Enforced policy |
| --- | --- |
| Jobs | One active, two waiting; fourth outstanding request rejected |
| History | Eight retained snapshots/ledger runs; old terminal ledger details cascade-delete |
| Workload | 1–100,000 records, typed kind/intensity/fault and u32 seed; unknown fields rejected |
| Batch | At most 64 records in memory and one transaction; no transaction spans hashing or resizing |
| CPU | Two total resource permits shared by artwork and the single background job |
| Artwork | Experimental 0/1/2 worker limit; normal default stays two; M0.5 source/cache/queue limits unchanged |
| Hashing | One owned 256-KiB file, 16-KiB stack buffer; cancellation between chunks and records |
| Parsing | Bounded generated JSON, 16 rounds gentle/slow or 64 saturated per record |
| Optional resize | One procedural 320×180 → 64×36 image per mixed batch |
| SQLite | Existing four-connection pool, foreign keys, WAL, FULL sync, 2-MiB connection cache, 64 statements |
| Writer | One async writer lock; 25-ms busy timeout; four attempts, 2-ms retry pause; 250-ms batch pool wait |
| Progress | At most once per 64-record unit; serial UI polling every 500 ms; no event flood |
| Diagnostics | Last 64 transaction/pool samples per job; last 1,024 foreground/worker-wait samples; eight jobs |
| Shutdown | Stop admission, request cancellation, await safe cleanup/task handles; five-second cooperative deadline |

The default experimental scheduling policy is `unthrottled`. Optional `foreground` admission backs off while foreground commands are active or a request began less than 8 ms ago, checking every 2 ms. This is cooperative admission, not OS thread priority, preemption or a deadline guarantee. Already running work finishes its current safe unit. No pool size or total CPU-worker increase was made. Normal artwork policy is unchanged pending the comparisons below.

The synthetic ledger is deliberately not a durable production queue. Job handles are retained until completion, pruned on admission and drained on shutdown. An exclusive OS file lease prevents two schedulers/cleanup tools owning the same root simultaneously. Temporary hashing handles and worker permits use scoped cleanup. Checkpoint IO failure produces failure; the persisted in-flight state is reconciled on the next open.

## Reproducible synthetic fixtures and isolation

`job-fixtures ROOT GAMES SEED` independently generates an M0.2-compatible synthetic library plus benchmark-only `simulation_runs` and `simulation_items` tables. IDs/FKs refer to the generated canonical games. Database writes update only `developer` and `updated_at_ms`, which are absent from the Details summary/filter contract, plus an auditable per-job item ledger. This deliberately provides contention without invalidating expected query results. It is not a simulation of inserting real discovered library entries.

The root must be an explicit absolute local `.../benchmarks/data/jobs-NAME` directory. New generation refuses an existing root, writes the completion marker last, and creates no normal application database. The fixed hash fixture and generated metadata derive deterministically from seed/ordinal. Synthetic digest uses FNV, not a security hash. `mixed` includes hashing, parsing, SQL writes and optional procedural resize. `slow` inserts controlled 1-ms pauses between hash chunks; `gentle` yields 4 ms between batches. Fault modes inject parsing, resource rejection or second-batch rollback.

Original M0.2 databases remain read-only references. The runner checks their SHA-256 before/after. Each condition gets a fresh independently generated writable job database and fresh derived-art cache. Known synthetic original `.img` files are NTFS hardlinks to the pre-existing synthetic fixture source; code never writes those originals. Cache cold here means empty derived thumbnails/new WebView profile, not purged OS filesystem caches. No artwork download occurs.

From repository root (Cargo/pnpm on PATH):

```powershell
# Build the optimized feature-gated application and fixture CLI.
Push-Location apps/desktop
pnpm tauri build --no-bundle --features benchmarks -- --locked
Pop-Location
$jobs = './apps/desktop/src-tauri/target/release/job-fixtures.exe'
& $jobs E:\dev\game-manager\benchmarks\data\jobs-example 15000 42
& $jobs verify E:\dev\game-manager\benchmarks\data\jobs-example
# Close every owner first. Cleans only a marked, validated disposable root.
& $jobs clean E:\dev\game-manager\benchmarks\data\jobs-example

./benchmarks/background.ps1 `
  -DatabaseDirectory E:\dev\game-manager\benchmarks\data\m0.2-2026-10-25-01 `
  -ArtworkDirectory E:\dev\game-manager\benchmarks\data `
  -ResultsDirectory E:\dev\game-manager\benchmarks\results\m0.6-new-run
```

Generate the four artwork roots with M0.5's documented `artwork-fixtures` commands first. The new runner supports `-Sizes`, `-Cases idle,cpu,hash,write,art1,art2,mixed0,mixed1,mixed2,priority`, `-Iterations` (20 default), `-Cycles` (one default), `-SampleMemory`, `-Trace`, and `-ShutdownJob -RestartCheck`. Use new output directories. `mixed0` runs the identical mixed workload with real thumbnail workers disabled; its procedural resize remains part of the synthetic job. `-TraceSort` captures only the sort transition, and `-ClosedDiagnostics` hides the diagnostics layout for an observer control. Memory sampling and tracing are separate observer runs, not the primary latency matrix. `verify` checks integrity, foreign keys, history bounds and exact committed/item counts; cleanup refuses unknown content/redirected files and never targets source artwork. Generated databases, profiles, images and large results are ignored.

Cancellation rolls back the current uncommitted batch and keeps valid committed prefixes. The ledger commit and each 64-record update share a transaction. `processed` may exceed `committed` on cancellation/failure. A restarted job is a fresh deterministic workload, not a continuation. In-memory elapsed/cancel latency includes final cleanup; restored elapsed is the last persisted checkpoint, and runtime diagnostics are not reconstructed. The fixture is disposable; full reconstruction means generating a new root. Interrupted generation is preserved for inspection rather than auto-erased.

## Measurement method

Windows 11 Pro 10.0.26200, Ryzen 5 4500, 64 GB, PNY CS1031 NVMe on E:, Node 26.12.1, pnpm 12.15.0, Rust 1.99.1 Windows MSVC; locked SQLx/SQLite/image versions. Rust release level 3/LTO/one codegen unit and bundled production React. Viewport 1120×760 CSS pixels, DPR 1. No lower-memory, HDD, physical display-scaling or controlled OS-cold test. Normal Windows/IDE activity is uncontrolled. No competing builds/tests run during final captures.

The final benchmark executable SHA-256 is `F0E92807E81D07255750F6F4D0F45299DE7CB498636679150C1796695723DB58`. Primary evidence is under ignored `benchmarks/results/m0.6-final-matrix/`; preliminary smoke/matrix directories are excluded. The four independently generated libraries use generator v1/seed 42; workload seed is 20261026. Every policy has a new writable database, profile and derived cache. Iterations retain OS caches. Conditions run sequentially, not randomized.

Each of the ten conditions retains 20 samples for each of four unchanged criteria: default, installed, not installed, and `chron` + installed + archive + 1990–2020/release descending at the tail. Metadata and bounded windows are serial; counts and complete row DTOs must remain equal on every iteration. Foreground CPU parsing, fixture hashing, SQLite writes and mixed work have explicit active-duty samples. Continuous ordinal artwork IPC uses zero/one/two awaiting loops, never an unbounded invocation queue. The loops stop before UI probes, which use the ordinary visible/near-visible thumbnail queue under the continuing job workload.

The UI then remounts Library under load, tests actual text input, composed filters, installed/not installed, sorting, rapid distant jumps and loaded End selection. Startup `firstUsableMs` starts at Library component creation before synthetic jobs begin, not process creation. The separate remount value represents library reconstruction while jobs run; it is not OS-cold startup. Artwork readiness records terminal visible placeholders/image loads, not compositor presentation. `criteriaToVisibleMs` includes debounce and prior uncancellable SQL work, starts at the latest control edit, and is a commit rather than paint metric. Search's 150-ms debounce alone can exceed the provisional 150-ms end-to-end budget.

IPC durations include transport/backend work. Rust count and page timings include their pool acquisition, SQLx execution/projection; metadata count excludes source enumeration/global summaries. Explicit pool waits cover the filtered-count/window acquisition only. Frontend gate waits are separate from SQLx waits. These overlapping durations are not additive except the explicitly paired count+page and IPC metadata+window observations. Native decode/resize/cache counters, browser artwork load, job throughput and frame/input timing remain separate instruments. Percentiles use nearest rank; p50 at 20 samples is the tenth sorted sample, not an interpolated median. A compact derivation tool is `node benchmarks/summarize-background.mjs RESULTS...`; raw arrays are authoritative.

The bounded rAF observer stores recent samples plus phase totals/maxima for IPC, UI and later safety work. Long-task records and input-to-next-rAF are browser measures; they do not measure hardware input latency or achieved FPS. Production React exposes no Profiler render-duration samples. A renderer trace is a separate instrumented run. Final process-tree private bytes are sampled after frame capture; periodic WMI sampling is optional and excluded from the primary matrix.

## Limits and remaining work

- Synthetic parsing/hash/write/resize work is a controlled simulator, not real discovery or importer correctness. The 256-KiB hash input fits OS caches; these runs do not establish large-file HDD performance. No account/provider/game/personal/mod paths are accessed.
- Workload transactions contain at most 64 records. Ledger reservations, terminal checkpoints and history retirement are separate statements; retiring one terminal run can cascade-delete up to the 100,000-record job cap. That cleanup is bounded but is not a 64-row workload transaction, and its worst-case duration was not isolated as a separate distribution. No CPU/hash operation holds a transaction. Slow-storage pruning/checkpoint behavior remains a future validation target.
- This is an eight-entry synthetic ledger, not durable production queue history. Earlier terminal details expire; updated synthetic metadata stays valid. Restored timing/batch/retry/progress-revision diagnostics are not reconstructed. There is no auto-resume or promise of full-job rollback.
- Foreground backoff is cooperative admission, not OS thread priority or starvation freedom. Backoff counters count deferred polls, not distinct jobs. Existing work is not preempted; blocked filesystem operations can exceed observed cancellation latency.
- The 150-ms overall filter/sort and small-page goals are not generally met. Stress query costs, higher tails in some current native browsing observations, expensive document Layout and the 235-ms outlier remain explicit. No attribution of unprofiled events or achieved FPS is made.
- Application caches/jobs are bounded, but complete process memory has no proven hard bound. Twenty cycles are not a long-session or lower-memory leak test. Source reuse in synthetic artwork limits representativeness for mostly unique real libraries.
- HDD/lower-RAM systems, physical Windows scaling, controlled OS-cold process startup, native ETW/GPU/compositor profiling, real power loss and real disk exhaustion were not performed. They are not counted as passes. Remote GitHub CI/branch protection is unchanged and unverified here.

Keep the next milestone focused on the remaining performance gate: isolate the sort-transition full-document Layout with targeted CSS/DOM/layout profiling and observer controls; separately propose/measure count-query optimization before changing indexes/SQL/FTS/count caches; compare one/two artwork workers with foreground fairness and throughput across cache/hardware states; extend memory/HDD/lower-memory and controlled startup evidence. Retain 15,000 as release scale and 25,000 as stress. Preserve all bounded queue/cache, cancellation, partial-state and production-isolation tests. No real imports, providers or M0.7 implementation begins automatically.
