## Storage and backup contract

Application schema v5 adds `artwork_assets` and `game_artwork`. The asset table stores a generated immutable ID, format, byte count, dimensions and an ordinary corruption-detection fingerprint; image bytes remain outside SQLite. Assignment writes reserve a writer, recheck the manual game and expected revision, then atomically update assignment and game revision. Overrides, identities, memberships, groups, profiles and defaults retain their existing semantics. Clearing and game metadata removal discard assignments only; asset metadata and originals remain.

Originals live beside the database under the configured installed data root at `database/artwork/originals/<asset-id>.img`. Validated bytes are written to a unique temporary file, flushed, published with a create-if-absent hard link, and reread for exact byte verification before the database reference is committed. No existing original is overwritten. Failed commits can leave preserved unreferenced originals; process interruption can leave preserved temporary files or additional links. Startup neither scans nor garbage-collects originals. There is no cross-filesystem/SQLite atomicity or arbitrary physical-power-loss guarantee.

**Backups are database-only.** Exact v2/v3/v4/v5 snapshots are validated read-only against their original schema and migration checksums. Only an owned active copy is upgraded. V5 snapshots include asset metadata and assignments, **not image files**. Preserve `database/artwork/originals/` separately with database backups. Restoring replaces assignment metadata without restoring or deleting originals. Missing, inaccessible or corrupt originals remain safe placeholders, even if an older derived thumbnail survives. UI explanations appear in the artwork editor, backup panel, selected-backup review and replacement confirmation. No full-content backup is claimed.

## Native access, lifecycle and resource bounds

IPC accepts game IDs and expected revisions only, with unknown request fields rejected. Choose/clear are explicitly registered, local-main-window capability commands; no frontend filesystem/dialog/shell grants are added. Native selection provides the source path privately. Local ordinary drive paths are required; accepted separator spellings are normalized without following links, after validating the original path for traversal; UNC/device/alternate-stream syntax, reserved aliases, parent traversal, trailing dots/spaces and excessive parent paths are refused. Parent paths are limited to 2,048 UTF-16 units and 256 components. Fixed/removable drive types are accepted; this is not broader removable-filesystem certification.

Retained no-reparse directory handles exclude parent rename/deletion during file work. Opened source/original/cache leaves are verified regular files with no observed hard links or reparses before reads, and exclude concurrent writes/deletion while open. Eviction rereads and verifies a derived record through its exclusively held handle before deleting that same file object. Unknown cache objects are preserved. These checks do not establish exclusive historical provenance or protection against privileged/compromised same-user application/OS manipulation. Fingerprints are not cryptographic integrity or authenticity checks.

Imports have one active admission and no import queue; thumbnail admission is two. Both acquire the existing shared two-worker budget before blocking image work. Detached operation owners retain admission through native selection, blocking work and commit; dropped IPC waiters cannot release resources early. Restore closes readiness and artwork admission, drains admitted operations, then closes SQLite. Shutdown drains before service teardown. A cancelled native picker is distinct from losing delivery of an operation result.

Input limits remain 8 MiB, 4096 per dimension, 4,194,304 pixels and the existing 64 MiB decoder allocation limit. Thumbnails remain 64×36 with at most 16 KiB PNG bytes and the existing bounded data-URL IPC envelope. The frontend queue retains two active requests, at most 32 waiting and 128 cached results. Native memory cache is 128 entries. The derived disk cache uses 256 fixed versioned slots, each containing an asset ID and bounded PNG. Slot collisions replace verified derived content only; originals are retained. Native disk statistics describe slots observed in this process, without a startup scan; preserved uncertain crash debris is not claimed to have a universal disk bound.

Queue generations prevent obsolete completion from repopulating a refreshed cache or notifying new subscribers. Active work keeps its capacity until settlement. Replace/clear refresh bounded selected-game details, retaining unrelated drafts. If the mutation succeeds but detail refresh fails, stale controls/preview disappear and the user is directed to reopen. Restart resets in-memory state; restore requires restart. Library queries, 100-row frontend pages, six cached pages, virtualization, single library request gate and viewport-driven artwork loading are retained.

### Preserved failures and corrections

Initial backend fixture failures were corrected: release the prior database owner before simulated restart, remove fixture-dependent overrides before deleting its game, and scope a borrowed restore future before dropping the database. A remaining historical current-schema expectation was advanced to v5. A frontend test caught and corrected an ellipsis encoding error. Final review added a regression that hides stale previews after successful mutation followed by failed detail refresh, and normalized accepted separator spellings after original-path validation.

The first native UI session was interrupted before the picker workflow finished; fresh complete runs are retained. Early activity harnesses counted CORS preflight requests as artwork operations and could lose the short-lived driver's exit code in Windows PowerShell. The corrected recorder filters POST requests and ends service intervals at response headers; the runner retains its process handle and records successful assertion markers. Both earlier failures and corrected runs are preserved under `artwork-activity*`. No application worker/cache limit, native launch assertion or benchmark fixture was loosened to pass these checks.
