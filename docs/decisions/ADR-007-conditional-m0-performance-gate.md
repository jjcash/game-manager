# ADR-007: Conditional M0 performance gate disposition

Status: **Proposed — explicit user approval required.** Prepared 2026-10-27. This proposal does not close M0, change an accepted target, authorize M1 implementation or approve a release.

## Context

The synthetic prototype validates the chosen local-first stack and bounded data/resource architecture. M0.7D/E completed their investigations but did not meet every original numerical target. More speculative startup/query optimization has poor demonstrated return. The [M0.8 disposition](../development/M0.8_GATE_DISPOSITION.md) consolidates original targets, finite passes, failures, hardware gaps, acquisition controls and cost-benefit evidence.

## Proposed decision for review

Permit **conditional M0 closure with documented exceptions**, only after explicit user approval. Keep the original PRD/TAS/DSS/ADR-004 budgets unchanged and retain M0.7B production queries, bounded virtualization/artwork and M0.7A title-scoped fallback.

- E1: accept measured warm-startup variability for progression, without claiming the exact window-creation endpoint or cold-start target passed.
- E2: retain tested literal scan-based search; defer indexing pending real data. Indexed-search certification and 100-ms input-to-result claims remain unsupported.
- E3: accept known native pressure/deep-page filter/page misses and defer extreme relationship workloads pending actual distributions. Preserve arbitrary navigation and canonical semantics.
- E4: retain residual long-task findings; defer further attribution without a reproducible consequential failure and credible remedy. Displayed FPS remains unverified.
- E5: accept finite memory stabilization evidence for progression, without claiming a universal bound, leak freedom or lower-memory support.

The unexplained historical writer-acquisition guard failure remains a preserved incident. Bounded tests establish safe forced-failure/recovery behavior but do not establish its cause. Reopen on recurrent representative failures, invalid prefixes or unreleased resources. Never increase pool size/deadlines or silently retry to manufacture a pass.

Actual/assigned 8–16-GB Windows, controlled OS-cold startup and credible compositor/displayed-frame measurements remain unverified release-validation obligations. Physical scaling and real NVMe/HDD scope are recorded precisely in M0.8. Feature-specific cached-details, real-import, backup and deployment criteria are carried into the milestones that implement them. Local checks do not substitute for documented GitHub CI.

## Consequences and reopening

Approval would change **milestone exit policy**, not technical results: a documented manageable miss may cease blocking core product development while remaining a failed/unverified requirement. It would not waive release acceptance, future safety tests or separate task authorization. Do not mark this ADR Accepted or M0 closed without recording the user's approval.

Reopen for a reproducible consequential representative 15k responsiveness defect with a supported cost-effective remedy; identity/query/staleness errors; unbounded resources; sustained unreclaimed growth/paging; failed job recovery/ledger invariants; or real relationship/artwork distributions materially changing the cost-benefit assessment. Preserve exact workloads/builds/endpoints and use fresh-process controls. An already documented synthetic miss alone is not a new optimization mandate.

No implementation beyond the authorized M0.8 investigation is selected by this proposal.
