# ADR-010: Installation grouping and LaunchProfile identity

Status: M1.5 implementation decision under explicit user authorization on 2026-10-29. The [verification report](../development/M1.5_INSTALLATION_GROUPING_VERIFICATION.md) governs completion claims. No launching is implemented or authorized.

## Existing identities and ownership

PRD requires configurable multiple-installation grouping; TAS section 4 and DSS sections 3/4.3 define `Game → LibraryEntry → GameInstallation → LaunchProfile`. Preserve that chain. DSS reference SQL is a design sketch, not an existing launch schema. M1.1 independent 128-bit random text IDs remain the implementation convention; IDs never come from a title, path, executable basename, display name or provider ID alone.

1. One canonical game may have several memberships, including several sources. One membership may have several installations. Every installation keeps its own stable ID.
2. Recording, grouping or changing a location string does not create, merge, rename or reidentify a canonical game. Equal titles do not establish identity. Membership and installation parent identities are immutable through this editor; future reassociation requires a separate reviewed contract.
3. Manual and provider memberships retain source identity and external IDs. Existing `state_origin` describes presence provenance, not physical verification or file ownership. Grouping never changes it. User grouping may organize read-only provider records without granting permission to edit or delete those records.
4. Explicit user metadata overrides remain authoritative, including a SQL NULL row. Group actions do not write overrides or the effective metadata projection.
5. Deletion remains metadata-only. Existing restrictions on last memberships, legacy/provider deletion and manual canonical removal remain. No game directory is accessed, validated, scanned, opened, moved or deleted.

## Grouping decision

A group belongs to exactly one canonical game. It can organize installations across that game's memberships. An installation belongs to zero or one group. Groups are flat; there is no global taxonomy, nested group, graph or cross-game membership.

Groups have independent random IDs and nonblank names of at most 80 Unicode scalar values; duplicate names are allowed. The UI includes an ID prefix to distinguish equal names. Renaming preserves the ID and assignments. Names and location strings are never keys. Groups may be empty and survive removal of their last installation or a membership. Removing a group explicitly confirms that its installations become ungrouped; it does not delete installations. Removing an installation cascades only its assignment. Permitted canonical deletion cascades its groups. Grouping does not change `present`, `missing` or `unknown`, ownership, playtime, mod context, launchability or verification.

Schema v3 adds `installation_groups` and `installation_group_members`, indexed by game and group respectively. Foreign keys remove only organizational relationships. Insert/update triggers require the same canonical game; group game identity is immutable. Existing tables and migrations remain unchanged. Narrow actions extend the existing revision-checked manual command; `BEGIN IMMEDIATE` and the game's expected revision serialize all editor changes. A stale request fails atomically. Reads load at most 100 memberships, 100 installations and 100 groups for one selected game. No group data is added to browsing projections, count/search/source queries or caches.

## Backup compatibility extension to ADR-009

Accept exact application schemas v2 and v3, each with its exact successful embedded migration prefix/checksums and exact schema SQL. V1, newer/modified schemas, benchmark purpose, extra objects, corrupt relationships and invalid override projections remain refused. V3 additionally validates group relationships. Validation remains bounded, immutable and read-only on a private copy; selected files are never migrated.

New snapshots use v3. A selected v2 candidate stays v2 in staging and preserved recovery storage. Only the copied active database is upgraded by normal transactional startup migration, before readiness and completion. Existing record IDs, metadata, revisions, timestamps and explicit NULLs are preserved; its new group tables start empty. Failure follows ADR-009 original recovery, including when active-copy migration has already occurred. A preserved v2 original can likewise be copied and upgraded during recovery. Completion history still cannot replay a snapshot over later edits. Recovery assets and original selected bytes remain preserved.

M1.4 builds cannot read new v3 backups; retain old backups and use a compatible new build. No downgrade migration or backwards-readable new format is claimed. Frozen generator-v1 benchmark migrations remain isolated at v1.

## Future LaunchProfile contract (separately reviewable, not persistent functionality)

No current grouping feature requires persistent profiles. Do not add a production launch table, engine, process calls, executable discovery or speculative launch UI in M1.5. The test-only model in `launch_profile_contract.rs` validates the following associations and lifecycle; it is not a production migration or engine.

| Field / relationship                                | Contract for the launch milestone                                                                                                                                                                                                                                                                                                                                    |
| --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                                                | Independent stable opaque LaunchProfile ID; creation allocates a new ID even for duplicate names or targets. Copying a profile creates another ID.                                                                                                                                                                                                                   |
| `gameId`                                            | Required canonical identity, derived from the bound installation's membership; any submitted value must match.                                                                                                                                                                                                                                                       |
| `installationId`                                    | Required, preserving TAS/DSS's installation-bound model. Manual/standalone use first records installation metadata; that record need not be verified present.                                                                                                                                                                                                        |
| Membership                                          | Derived through installation; no separate conflicting membership binding. Moving a profile between installations is not a rename or a path edit: initial scope requires a new profile with explicit user choice.                                                                                                                                                     |
| Provenance                                          | `user` or future `provider`. A provider association needs a namespaced source ID plus external profile ID and must match the installation's membership source. User profiles have neither provider field. Provider updates must not overwrite future explicit user configuration overrides. No provider import is implemented.                                       |
| `displayName`                                       | Editable label, never unique identity. Several profiles may share a label for one installation or game.                                                                                                                                                                                                                                                              |
| `launcherKind`                                      | Future explicit adapter/standalone target kind; a stored target does not itself authorize execution.                                                                                                                                                                                                                                                                 |
| `executableRef`, `arguments`, `workingDirectoryRef` | Future target reference, ordered array of literal argument strings, and optional working-directory reference. Their validation/resolution, quoting, process safety and permitted adapter kinds belong to the separately authorized launch milestone. Do not concatenate a stored shell command.                                                                      |
| `revision`                                          | Nonnegative profile revision. Save/delete require an exact expected revision and increment on configuration change. Installation changes independently increment the canonical game's revision as today. Future prepared launch requests must check both profile revision and current installation/game context; stored profile identity does not certify readiness. |

Installation location/platform/version/presence edits preserve profile IDs, bindings and explicit target references. They invalidate any future prepared readiness decision; no silent target rewriting or executable rebasing is allowed. Removing an organizational group has no effect on profiles, bindings or defaults.

Future installation deletion must first refuse while profiles reference it, or offer one explicit reviewed transaction deleting the enumerated profiles and clearing their defaults before deleting installation metadata. Membership deletion applies this same rule to all its installations; canonical deletion applies it to all descendants and preserves the existing manual/provenance gate. Never silently orphan, retarget or choose another installation. Source/provider deletion cannot authorize deleting a user profile implicitly. Session/mod-history retention may add further restrictions when those features are designed; this contract grants no filesystem deletion.

There may be many profiles per installation and thus per game. A future default is an optional, explicitly selected per-game profile ID that must belong to that game. No alphabetical, oldest, provider-priority or path-based implicit default. Selecting/replacing/clearing it requires the game's expected revision, validates the chosen profile revision and advances the game's revision in the same transaction. A reviewed profile deletion clears its default without selecting a replacement. A group neither owns nor chooses defaults. Profile and default persistence, user/provider override mechanics and launch validation need their own migration/backup/native verification in the launch milestone.
